## 0. Audit — what exists today, and what it means for an AI layer

### 0.1 The one fact that reframes the whole mission

**There is no multi-tenant "workspace" concept, and no AI/LLM integration of any kind, anywhere in this codebase.** Confirmed by direct inspection, not inference:

- `grep`-ing both `frontend/src` and `backend/src` for `openai|anthropic|claude|chatbot|ai-chat` returns nothing. Neither `package.json` lists any LLM SDK.
- `Business { ownerId → User, onDelete: Cascade }` — one owner, full stop (`backend/prisma/schema.prisma:537`). No `Team`, `Member`, `Role`-on-`Business`, or `Workspace` model exists. `ROADMAP.md §0.1` already documents this: *"a Business belongs to exactly one `User.ownerId`, full stop."*
- The mission's vocabulary (§53–54: "tenant", "workspace") maps onto exactly one real boundary in this codebase: **`Business.ownerId === request.user.id`**, checked per-controller via a `findOwned(businessId, ownerId)`-style method (see `WebsitesService.getDraft`, and the identical pattern in `products.service.ts`/`orders.service.ts`/etc.). There is no separate "tenant" entity to isolate against — the AI layer's tenant-isolation requirement (§53/§142) is really "every tool call must re-derive and enforce `ownerId` server-side, never trust a client-supplied `businessId` alone." That's a narrower, more tractable problem than the mission's language implies, and the existing controllers already do it correctly today — the AI tool layer needs to reuse that pattern, not invent a new one.

### 0.2 What already exists that the AI layer can build directly on top of

- **A declarative, typed block-tree** (`WebsiteBlock { id, type, props, style?, hidden?, children? }`, `frontend/src/entities/website/model/types.ts`) — this is *already* the "flat, AI-generatable" shape the mission asks for in §7/§45/§49, down to the doc-comment on `WebsiteBlock` explicitly calling out AI-generation as the reason for the flat shape. `ROADMAP.md §3.13` ("AI-readiness") independently reached the same conclusion and deliberately deferred writing AI code until now.
- **A real component-schema registry** (`registry.ts`, `BlockDefinition<P>` + `FieldSchema` union: `text/textarea/richtext/number/select/color/toggle/image/url/link/dataSource/list`, each with a `key`/`label`/optional `responsive`) — this is mission §49's `ComponentDefinition` almost verbatim, already shipped, already covers most of §7's tool surface (`set_style` → `style` field, `bind_data` → the `dataSource` control, `set_visibility_condition` → `hidden`). A `create_component`/`update_component_props`/`set_style` tool set can be built as a thin, validated wrapper around the *existing* Zustand builder store actions (`insertBlock`, `moveBlock`, `updateBlockProps`, etc. in `website-store.ts`) rather than a new execution path.
- **A capability system** (`Business.capabilities: String[]`, e.g. `"commerce"`) already gates which Dashboard sections and Builder blocks a business sees — a real precedent for scoping what an AI tool is *allowed* to do per business, though today it's a feature flag, not a permission/capability-token system in the mission's sense (§22–23). Extending it into the widget-capability model (§22) is additive, not a rewrite.
- **A provider-abstraction pattern already proven twice**: `PaymentProvider` (abstract class, `StripeAdapter` the only implementation, `backend/src/modules/payments/payment-provider.ts`) and `DomainVerificationProvider` (`modules/domains`). This is exactly the shape the mission asks for Web3/RPC/crypto-price providers in §24/§26 — copy this pattern, don't invent a new one.
- **A real security substrate, already in production use**: `SessionAuthGuard` (resolves opaque Redis session tokens, attaches `role`/`isBanned`/`isSuperAdmin` to every request), per-route `@Throttle()` rate limits (already applied to every anonymous write endpoint — orders, appointments, form submissions), `sanitize-html` already a backend dependency (used on `Post.text`), ownership checks returning 403/404 rather than leaking existence. This is the raw material for the mission's "policy engine" (§99–100) — there is no policy engine as a distinct abstraction yet, but the primitives it would compose exist and are already battle-tested (`ROADMAP.md §13` documents a real crash-testing pass against exactly these paths).

### 0.3 The real gaps — confirmed, not assumed

1. **No LLM integration exists at all.** No provider chosen, no API key configured, no SDK installed, no streaming infrastructure, no chat UI. Everything in mission §35–46 (chat UX, streaming, live canvas updates) starts from zero.
2. **Backend validation of website documents is deliberately shallow** (`UpdateWebsiteDocumentDto`: `pages: unknown[]`, `theme: object`, `settings: object` — no per-block-type schema check). The doc-comment explains this is intentional: adding a block type shouldn't require a backend deploy. This is a *reasonable* tradeoff when the only writer is a human in the Builder UI clicking pre-built inspector controls that can only ever produce valid `props` shapes. **It stops being reasonable the moment an AI tool call becomes a write path**, because AI-generated `props`/`style` is untrusted input by the mission's own §20/§97 principle, and the shallow DTO would let a malformed or malicious block tree straight into the database with no server-side shape check. This is the single most concrete, immediate security gap the AI layer introduces — see §3 below for the fix (validate at the tool layer, using the same `BlockDefinition.fields` schema the Builder inspector already reads, before calling the existing shallow-validated save endpoint).
3. **No widget "authoring" system — only a developer-maintained component registry.** Every block type (`registry-index.ts` → `blocks/{layout,typography,media,actions,business,navigation,content,commerce,booking,blog,forms,utility}`) is a hand-written React component, compiled into the frontend bundle at build time. There is no concept of a *stored*, *dynamically loaded*, *business-scoped* widget (mission §16–19, §55–56). This is the biggest architectural decision the mission requires and the codebase doesn't have a shape for yet — see §4 below for the recommended design (a constrained declarative widget schema, not arbitrary runtime code).
4. **No sandboxing infrastructure of any kind** — no VM/isolate/worker execution environment, nothing resembling "custom business logic" (§13–15) beyond what a developer hand-writes into a NestJS service. Mission §15's "advanced custom logic... sandboxed, isolated, resource-limited" has zero starting infrastructure.
5. **No Web3/blockchain code, dependency, or abstraction anywhere.** A clean slate — no wrong assumptions to unwind, but also nothing to reuse beyond the `PaymentProvider` pattern shape.
6. **No audit log table.** `AnalyticsEvent` exists (`backend/prisma/schema.prisma:1019`) but it's a product-analytics table (page views, form submits), not a security/action audit trail (§102). A distinct `AuditLog` model is needed before any AI tool executes a real mutation.
7. **No `backend/AGENTS.md` or `backend/PROJECT_CONTEXT.md`.** `frontend/PROJECT_CONTEXT.md` repeatedly references "`AGENTS.md` backend" for auth/realtime/DB details that must live somewhere backend-side, but no such file exists in this repo today (`find backend -iname "AGENTS.md"` — nothing). This is a pre-existing gap, not something the AI mission created, but the AI layer's backend module will need backend-side conventions documented somewhere — worth flagging to the owner, not silently fixing by inventing a new doc format.
8. **The "Create Business" flow is a single static form** (`widgets/businesses/ui/CreateBusinessForm.tsx`), not conversational — confirmed by the file existing and no `onboarding`/`chat` slice existing anywhere in `frontend/src`. Mission §29–34's "Create Business with AI" is 0% built, but the form's fields (name, category, description) map cleanly onto the first few turns of a conversational onboarding — nothing about the current form needs to be destroyed, only supplemented with an AI-driven alternative entry point (mission §125's own instruction: audit before replacing).

### 0.4 What this means for scope

The mission (150 sections) describes a destination, not a sprint. Given this codebase's actual size (a working, tested, single-owner-per-business builder with Commerce/Booking/Content already live) and the owner's instruction to avoid endless non-terminating iteration, the right posture is: **build the AI orchestration substrate first — tool registry, policy/validation layer, one real LLM-backed chat that can safely call a handful of LOW/MEDIUM-risk tools end-to-end** — and prove the whole pipe (chat → intent → tool call → validated write → live canvas update) before expanding tool coverage. This mirrors exactly how `ROADMAP.md` itself was built (Commerce first, proven, then Booking reused the same shape) rather than trying to stand up all 150 sections' worth of subsystems simultaneously.

## 2. Concrete gap analysis against the mission's own sections, grouped

### 2.1 AI orchestration layer & tool registry (mission §6–9, §58–62)
**Status: 0%.** Needs: a new `backend/src/modules/ai` NestJS module; an LLM provider abstraction (see §2.3); a tool registry (plain object/array of typed tool definitions, each with a Zod input schema, a risk level, and a handler that calls into an *existing* domain service); a planner/orchestration loop (call model → get tool_calls → execute → feed results back → repeat until the model returns a final message, with a max-iteration guard against runaway loops — mission has no explicit iteration cap language but §61/§103 imply one is needed for safety).

### 2.2 AI ↔ frontend / AI ↔ backend / AI ↔ database tool surfaces (mission §7–10)
**Status: substrate exists, tools don't.** The website block-tree + registry (§0.2) covers most of §7's list already at the *data model* level; what's missing is the actual typed tool functions (`create_page`, `update_component_props`, etc.) as callable, validated units, plus a small number of genuinely new ones (`create_entity`/`add_field` for the custom-database-builder use case in mission §10, which has **no equivalent today** — Product/Service/Order/etc. are all hand-coded Prisma models, not a dynamic user-defined-entity system). Recommend: don't build a generic dynamic-entity engine in the first iteration — it's the highest-complexity, highest-risk item in the whole mission (arbitrary user-defined schema + migrations, mission §11 "migration safety"). Sequence it after the tool-registry substrate and the widget engine are proven.

### 2.3 LLM provider choice — **open decision, needs the owner**
No provider is configured. The mission is provider-agnostic in spirit (§24 "approved connectors", not naming a vendor) but a real key is needed to write and test any of this. This blocks all further work in this initiative until decided — flagging per mission §137's own stop condition ("нужны credentials/secrets/external configuration"). Needs from the owner: which provider (Anthropic/OpenAI/other), an API key set as a backend env var (never committed, added to `env.validation.ts` the same way `STRIPE_SECRET_KEY` already is), and a rough cost-tolerance signal for §123's model-routing tiers.

### 2.4 Custom widget engine (mission §16–23, §55–57)
**Status: 0%, and the highest architectural-decision item in this whole initiative.** Recommend against arbitrary-JS widgets entirely, in favor of a **constrained declarative widget schema**: a widget is a JSON document (layout of existing primitive blocks + a typed `dataBindings` array pointing at approved data sources + a typed `capabilities` array from a fixed enum) rather than executable code. This satisfies mission §21's "allowlist > blocklist" and §14's "prefer structured rules over arbitrary code" directly, and reuses the *exact* `WebsiteBlock`/`BlockDefinition` machinery that already exists — a "custom widget" becomes a saved, business-scoped **composition** of existing blocks plus data bindings, stored as a new `CustomWidget` Prisma model (`id, businessId, name, schema: Json, status: WidgetStatus, ...`), not a new rendering/execution engine. A crypto-price widget or a loyalty-dashboard widget becomes: existing card/stat blocks + a `dataSource` binding to a new approved connector (§2.6) — no new sandbox needed for the common case. True arbitrary-code widgets (mission §15's "advanced custom logic") should stay explicitly out of scope until there's a real user request for something the declarative system can't express — same anti-speculation discipline `ROADMAP.md §6` already applies to Marketplace/multi-vendor.

### 2.5 Business logic engine (mission §13–15)
**Status: 0%.** Recommend a `Rule { trigger: DomainEvent, condition: JsonLogic-style expression, actions: TypedAction[] }` model, evaluated by a NestJS listener on the *existing* domain events this codebase already has natural hook points for (`OrdersController` already emits after `OrdersService.create` completes — the same "Controller decides, Service doesn't know" pattern documented in `frontend/PROJECT_CONTEXT.md`'s real-time section applies here too: emit a `RuleEngineService.evaluate('order.completed', order)` call from controllers, after the service call, not inside services). No arbitrary code execution — actions are a small, versioned enum (`addLoyaltyPoints`, `setMembershipTier`, `sendNotification`, ...), each its own tiny typed handler, composable per mission §59.

### 2.6 Web3 (mission §25–28)
**Status: 0%, clean slate.** Follow the `PaymentProvider` pattern exactly: `Web3Provider` abstract class (wallet connection, balance read, NFT read, tx status — all read/display operations first), one real adapter (a public RPC provider or a service like Alchemy/Infura), financial transactions always require an explicit client-side wallet-signed confirmation (never AI-initiated signing, mission §27) — this is a UI/UX flow (`wagmi`/`viem` on the frontend talking to the user's own wallet extension), not something the backend or the AI tool layer can or should perform on the user's behalf. Sequence this after Commerce-equivalent tool coverage is proven, since it's genuinely new infrastructure with no existing analog in this codebase (unlike Commerce/Booking's price-in-cents pattern, which Web3 can't reuse).

### 2.7 Conversational onboarding (mission §29–34)
**Status: 0% as AI, but the target UI shell exists.** `CreateBusinessForm.tsx` already collects name/category/description — the AI onboarding is a superset (more turns, dynamic questions) that should **replace the entry point**, not sit beside it as a second disconnected flow (mission §124's "must be one system"). Concretely: `/businesses/new` becomes a chat surface; on completion, the AI's structured output (name, category, capabilities, starter content) gets fed through the *same* `createBusiness`/`saveWebsiteDraft` calls the current form already uses — so the manual form's code isn't wasted, it becomes the deterministic "fallback"/"advanced" path for a user who skips the chat (mission §127's progressive disclosure).

### 2.8 Security policy engine, risk levels, audit log (mission §99–103)
**Status: primitives exist (§0.2), the composed engine doesn't.** First iteration needs: an `AuditLog` Prisma model (`actorId, businessId, tool, riskLevel, argsSummary (no secrets), result, createdAt`); a `RiskLevel` enum used by every tool definition; a rule that any `HIGH`/`CRITICAL` tool call returns a "confirm?" step to the chat UI instead of executing immediately (mission §100, §43's change-preview). This is small, well-scoped, and should ship in the very first AI iteration — retrofitting audit logging after tools already exist is exactly the kind of rework the mission's own "quality gate before publish" discipline (§67) warns against.

## 3. Immediate, codebase-specific security note (not hypothetical — verified above)

`UpdateWebsiteDocumentDto` (`backend/src/modules/websites/dto/update-website-document.dto.ts`) validates only `pages: unknown[]` / `theme: object` / `settings: object` — no per-block shape check, by design, for a human-only Builder. **Any AI tool that writes to a website document must run its own validation against `BlockDefinition.fields` (the frontend registry) before the payload reaches this endpoint** — either by porting the field-schema validation to a shared/backend-callable form, or by having the tool layer construct blocks only through a small set of pre-validated helper functions per block type, never by handing the model's raw JSON straight to `saveDraft`. This is the concrete instance of mission §97 ("generated schema... untrusted input") for this specific codebase, not a generic warning — call it out explicitly in the first AI-tools implementation PR.

## 6. What actually shipped in AI-1 (2026-08-29/30) — verified, not assumed

Everything below was tested against the real, running dev stack (Docker Compose: `backend`, `postgres`, `redis`) and the real Gemini API with the owner's own key — no mocks, per mission §115.

**Backend — `backend/src/modules/ai/`:**
- `LlmProvider` abstract class (`llm-provider.ts`) — the same provider-abstraction shape already proven in this codebase by `PaymentProvider`. `AiService` depends only on this abstraction.
- `GeminiAdapter` (`providers/gemini-adapter.service.ts`) — implements `LlmProvider` via direct REST calls to `generateContent` (no SDK dependency added). Handles Gemini's `thoughtSignature` requirement for multi-turn function calling on Gemini 3.x "thinking" models — **this was not in the original plan and was only discovered by testing against the real API**: the first real request failed with `400 "missing thought_signature"`, which is undocumented behavior discovered live, not predictable from the API reference alone. Fixed via a provider-agnostic `LlmToolCall.providerMetadata` escape hatch (opaque to `AiService`, round-tripped verbatim) rather than leaking Gemini-specific concepts into the shared types.

### 10.1 Backend — `POST /businesses/:businessId/ai/chat/stream`

- `AiService`'s tool loop was refactored into a private `runToolLoop` **async generator** (`AiStreamEvent` — `tool_start`/`tool_result`/`message`, new type in `ai.types.ts`) shared by both entry points: `chat()` (existing, non-streaming — now just drains the generator into the same `ChatResult` shape as before, zero behavior change, still passes all 55 pre-existing backend tests unmodified) and the new `chatStream()`, which maps the same events onto Nest's SSE `MessageEvent` via `rxjs`'s `from()`.
- `AiController.chatStream` — `@Sse('chat/stream', { [METHOD_METADATA]: RequestMethod.POST })` (Nest 11.2.3 supports POST-bodied SSE via this override; used because the user's message belongs in the request body, not a query string, for consistency with `ChatRequestDto` and to not cap message length via URL limits).

### 10.2 A real bug found and fixed during verification, not left as a known issue

Initial design put the `isConfigured()`/ownership checks inside `AiService.chatStream()` itself, before constructing the `Observable` — mirroring `chat()`'s existing, already-verified pattern, on the (wrong) assumption that this would keep 403/404/503 as clean HTTP responses. **Verified live via curl that this was false**: Nest's `@Sse()` machinery commits response headers (200, `Content-Type: text/event-stream`) on an internal `setTimeout(…, 0)` scheduled immediately after subscribing to the returned `Observable` — it does **not** wait for the controller method's own promise (or the ownership check's real DB round-trip inside it) to settle first. Since a real Prisma query is essentially always slower than a `setTimeout(fn, 0)` macrotask, the header-commit timer fires first every time in practice, so an ownership/config failure ended up as an `event: error` frame inside an already-`200`'d, already-SSE-headered response instead of a clean `403`/`404`/`503` — reproduced with a second real user hitting a first user's business (`curl` showed `HTTP/1.1 201 Created` + `Content-Type: text/event-stream`, with `data: Это не ваш бизнес` only inside the stream body).

**Fix**: moved these checks into a new `AiAvailabilityGuard` (`backend/src/modules/ai/guards/ai-availability.guard.ts`), applied via `@UseGuards(SessionAuthGuard, AiAvailabilityGuard)` at the controller level (covers both `chat` and `chatStream`). Guards are fully awaited by Nest **before** it even determines a handler is SSE, so there's no race regardless of how slow the check is — confirmed by re-running the exact same curl reproduction after the fix: `403`/`404`/`400`/`401` all came back as clean JSON HTTP responses again, for both endpoints. `AiService.assertOwnership` (the old private method) was deleted — the guard is now the single source of truth for this check, removing what would otherwise be a duplicate DB query per request. This is the same category of finding as AI-1's `thoughtSignature` discovery and AI-2's 429-hides-mutation bug: real framework behavior, only discoverable by testing against the running stack, not by reading the code or docs.

### 10.3 Frontend — `app/api/ai-chat/route.ts` + `features/ai-chat/api/stream-ai-chat.ts`

- The project's normal backend-access path (Server Actions calling `backendFetch`) can't stream a progressively-read response back to a client component — a Server Action returns one serialized result. Parses raw SSE framing by hand (`event:`/`data:`-lines split on `\n\n`) since Nest's frames are simple enough not to need a library. The old `send-ai-chat-message.ts` Server Action (§9) is deleted — fully superseded, nothing else referenced it.
- **Verified the SSE parser's correctness without a live successful Gemini call** (see §10.4 for why): wrote a throwaway Node script (not committed — scratch verification only) that feeds the exact byte-for-byte real backend output (captured via curl) through the same parsing algorithm, split at multiple chunk sizes including 1 byte at a time, to simulate worst-case TCP fragmentation splitting frames mid-line/mid-JSON. ### 11.1 Why onboarding is its own orchestration loop, not a call into `AiService`

Every existing AI tool (`ToolContext` in `ai.types.ts`) assumes a `businessId: string` that already exists — `AiService.runToolLoop` derives it once (`AiController`'s `AiOwnershipGuard`) and threads it through every tool call. Onboarding has no business yet — that's what the conversation produces — so reusing `ToolContext`/`ToolRegistryService` as-is was not an option without either (a) making `businessId` optional everywhere (weakens every *existing* tool's type-level guarantee that it always has one) or (b) building a second, narrower context/registry pair. Went with (b):

- `backend/src/modules/ai/onboarding/onboarding.types.ts` — `OnboardingToolContext` (`actorId` only, no `businessId`), `OnboardingToolDefinition`, and `OnboardingStreamEvent` (the same `tool_start`/`tool_result`/`message` shape as `AiStreamEvent`, plus one onboarding-specific variant, `business_created`, see §11.2).
- `onboarding-tool-registry.service.ts` — a second, separate `Map`-backed registry, deliberately not a generic parameterization shared with `ToolRegistryService`. This isn't just type hygiene: it's a real scope boundary — business-editing tools (`add_block`, `set_style`...) are structurally unreachable from the onboarding conversation, not just unlisted by convention.
- `onboarding.service.ts` (`AiOnboardingService`) — a second copy of the "model asks for tool → execute → feed result back" loop (~90 lines, same shape as `AiService.runToolLoop`, including the §7-flagged "tool already committed, follow-up LLM call failed" graceful-degradation branch). Duplicated deliberately, not out of oversight — see the class-level comment in `onboarding.service.ts` for the tradeoff reasoning. Only SSE, no synchronous `chat()` variant (unlike `AiController`, which has both for historical reasons — see the comment on `OnboardingController`): the frontend was always going to use the already-proven streaming path, so a synchronous twin nothing would call wasn't built.

### 11.5 AI-4 follow-up (2026-08-30, continued) — richer starter content via template selection, not free-form generation

`create_business` originally mirrored only the manual form's fields (name/category/description/currency), leaving every new AI-onboarded business with an empty home page — a real gap flagged in §11.4's closing note, filled here. Deliberately **not** solved by letting the model author `WebsiteBlock` content directly: that would reopen exactly the untrusted-input gap §3 already flagged (AI-generated `props`/`style` needs the still-unbuilt shared backend validator) for no real gain, since the project already has a curated, hand-designed starter-template system (`STARTER_TEMPLATES` in `frontend/src/entities/website/templates/index.ts` — `restaurant`/`agency`/`local-business`, each a real `WebsiteBlock[]` tree plus capability/seed-product/seed-service metadata) that a human already uses via `StarterTemplatePicker` on every empty site. **Backend — `create_business` gains a `templateId` parameter:**
- `backend/src/modules/ai/onboarding/tools/create-business.tool.ts` — new optional `templateId` arg, enum `'restaurant' | 'agency' | 'local-business' | 'blank'` (a hand-kept copy of `STARTER_TEMPLATES`'s ids plus `'blank'` for "none fit" — same two-independent-copies pattern as `currencies.ts`/`ai-chat` model types elsewhere in this project). Unlike `name`/`category`/`currency`, an invalid or missing `templateId` does **not** throw — it's a cosmetic hint, not identifying data, so it silently falls back to `'blank'` rather than blocking business creation over a UX nicety. The parameter's description explicitly tells the model not to force a bad fit ("финтех/крипто/чисто онлайн-продукт → blank"), which is exactly the scenario the onboarding chat's own example now demonstrates (§10's crypto-exchange example) — a good real test that the honest "no template fits" path works, not just the happy path.

- Backend never touches template *content* — no block trees, no seed-product data — only validates the model's choice of id. Keeps the "tool layer is a new caller of old code" principle intact instead of duplicating hand-authored block trees into a second language runtime, which would drift out of sync the moment someone edits a template on the frontend.

**Frontend — reused, not duplicated, template-application logic:**

### 15.2 OR/nested conditions

`RuleCondition` (the leaf shape — `field`/`operator`/`value`) is unchanged. New `RuleConditionGroup = { any: RuleConditionNode[] } | { all: RuleConditionNode[] }` (exactly one key), and `RuleConditionNode = RuleCondition | RuleConditionGroup` — a node is a leaf or a group, and a group's children are themselves nodes, so nesting depth is unbounded by the type, not by a hardcoded limit. The top level of `Rule.condition` stays an array evaluated with implicit AND, exactly as before — **every rule saved under the first AND-only slice is already a valid `RuleConditionNode[]`, with identical evaluation semantics, no data migration needed**: a flat array of leaves is just the degenerate case of the new format.

`parseRuleCondition` (`rules.types.ts`) validates recursively (`parseConditionNode`), producing path-qualified error messages for nested failures (e.g. `condition[0].any[1].field должен быть непустой строкой`) rather than a generic top-level error — a nested validation failure should point at exactly which branch is malformed. `evaluateConditions`/`evaluateNode` (`rule-condition.lib.ts`) mirror the same recursion: a group's `any` is `.some(...)`, `all` is `.every(...)`. Both are pure functions, tested without Postgres (same discipline as the rest of this module) — 7 new tests in `rule-condition.lib.test.ts` (flat OR, flat AND-group, nested-inside-nested, top-level leaf combined with a group) and 6 in the new `rules.types.test.ts` (parsing/rejecting groups: missing both keys falls through to leaf validation and fails there — not a special-cased error, since an object with neither `any`/`all` nor a valid leaf shape *is* a malformed leaf; both keys present is rejected explicitly; empty group array is rejected).

**Verified live, not just unit-tested**: the §15.1 nested-condition rule above (`[leaf, { any: [...] }]`) is the real proof — a real HTTP `POST` created it, a real anonymous booking evaluated it correctly against real `RuleExecutionLog` output, exercising both the parse path and the evaluate path for a genuinely nested condition, not a synthetic example confined to a unit test.

## 25. AI-12 — arbitrary pixel spacing, slice 3 of the Universal Builder Expansion track (2026-08-31, continued)

Third narrow slice of the same brief (§23). §24 explicitly flagged this as the harder of the two remaining candidates and picked Google Fonts first for exactly that reason: `SpacingSize` (the 5-preset padding/margin scale) is read in **8 places** — `paddingY`/`paddingX`/`marginTop`/`marginBottom` (the "Просто" tab) plus `paddingTop`/`paddingRight`/`paddingBottom`/`paddingLeft` (the "Дополнительно" per-side tab, each also `| null` for "inherit from the pair") — not 1 (`background`) or 2 (`fonts.heading`/`.body`) like the prior two slices. Naively adding a `'custom'` sentinel to the shared `SPACING_SIZE_OPTIONS` array (reused by all 8 fields) would have leaked an unsupported option into 7 fields with no companion UI built for them.

### 25.1 Design: widen the value slot itself, not the enum

Instead of a sentinel + companion field (the AI-10/AI-11 pattern), this slice widens what the padding/margin *slots themselves* can hold: a new type in `types.ts`,

```ts
export type SpacingValue = SpacingSize | number;
```

A `number` means literal pixels (`18` → `18px`), distinguishable from a preset by `typeof` alone — no separate toggle, no second field. `BlockStyle`'s 8 fields all changed from `StyleValue<SpacingSize>`/`StyleValue<SpacingSize | null>` to `StyleValue<SpacingValue>`/`StyleValue<SpacingValue | null>`. Resolution is one shared helper in `block-style.ts`:

```ts
function spacingToPx(value: SpacingValue | undefined): string | undefined {
  if (value === undefined) return undefined;
  return typeof value === 'number' ? `${value}px` : SPACING_PX[value];
}
```

`resolveSide` (the "Дополнительно" per-side inherit-from-pair logic) and the 4 basic `readResponsiveProp` reads widened from `SpacingSize` to `SpacingValue` generically — no field-specific branching needed, since `readResponsiveProp`/`writeResponsiveProp` were already fully generic over `T`.

**A real bug caught before it shipped, not after**: the pre-existing code computed padding/margin as `top ? SPACING_PX[top] : undefined` — a truthy check that happened to work only because every `SpacingSize` member is a non-empty string (`'none'` included). The moment `number` became a valid value, `0` (a legitimate "zero custom padding") is falsy in JavaScript and would have silently collapsed to `undefined` — the exact same class of bug §23.2 found and fixed for `contrastOverrides`, this time caught during implementation rather than by a live test surfacing it. Fixed by making `spacingToPx` the single point of truth (`value === undefined` is the only early-return condition), replacing all 6 `? SPACING_PX[x] : undefined` call sites in `computeBlockWrapperStyle`. Locked in with a dedicated unit test (`renders a custom 0px spacing, not the same as "no value set"`) and a live browser check.

### 25.2 UI: one new control, not 8 bespoke ones

A new `FieldSchema` variant, `{ control: 'spacing'; options: SelectOption[] }` (`registry.ts`), reuses the same `options` shape as `'select'` — `LayoutSection.tsx`'s `BASIC_FIELDS` (4 fields) and `PADDING_SIDE_FIELDS` (4 fields) just changed `control: 'select'` → `control: 'spacing'`, no other changes needed there. `FieldControl.tsx` renders it as a `<select>` (the field's normal preset options plus one synthetic "Свой (px)" option) paired with a conditionally-shown `<input type="number">` — visually the same two-part row pattern AI-10 already established for `customBackgroundColor`, just reusing `typeof value === 'number'` as the switch instead of a separate boolean flag. Picking "Свой (px)" calls `onChange(0)` to enter custom mode (a sane, visible starting value, not an empty/invalid state); typing in the number input calls `onChange(Number(...))` directly — the select and number input are simultaneously visible and interactive, so switching back to a preset at any time is just picking a different select option, no separate "cancel custom mode" affordance needed.

### 25.3 Backend: `set_style` tool widened, bounded

`block-style-schema.ts`'s `buildValidatedStyle` gained a numeric branch for exactly the 4 basic fields this tool already scoped itself to (`paddingY`/`paddingX`/`marginTop`/`marginBottom` — the per-side "Дополнительно" fields were already explicitly out of this tool's scope before this slice, per its own doc-comment, and stay out now). A number is accepted only if `Number.isFinite` and within `0–400` — AI-authored input is untrusted (§3), and an unbounded value could push a block's spacing far enough to visibly break the page layout. `set-style.tool.ts`'s parameter description updated to mention the numeric option and its bound.

## 27. AI-14 — gradient backgrounds, slice 4 of the style-engine track (2026-08-31, continued)

Fourth slice of the AI-10/11/12 style-engine track (AI-13 was a one-off widget-library detour in between). Closes the original brief's §1.7 "Background Engine" ask for gradients — specifically **linear, two-stop gradients**, a deliberately narrow v1: not radial/conic, not 3+ color stops, not multiple background layers, matching the same "one concrete piece at a time" discipline as every prior slice in this track.

### 27.1 Design: same shape as AI-10's custom color, one field wider

`Background` gained `'gradient'` alongside the existing `'custom'`. `BlockStyle` gained three new optional fields:

```ts
gradientFrom?: string;   // #rrggbb
gradientTo?: string;     // #rrggbb
gradientAngle?: number;  // 0-360, defaults to 135 if unset
```

`backgroundValue()` (`block-style.ts`) renders `linear-gradient(${angle}deg, ${from}, ${to})` — returns `undefined` (no background) if either stop is still unset, the same "an incomplete custom choice fails safe to nothing, not a broken CSS value" principle `customBackgroundColor` already established. `LayoutSection.tsx`'s inspector shows all three fields spliced in right after "Фон", only when `background === 'gradient'` — literally the same `basicItems.splice(1, 0, ...)` pattern AI-10 wrote for `customBackgroundColor`, just with three items instead of one; no new mechanism needed.

**Contrast rule, extended deliberately conservatively**: `contrastOverrides()` already decided light-vs-dark text via `isDarkColor()` for `'custom'`. For `'gradient'`, light text now applies only when **both** `gradientFrom` and `gradientTo` are dark. A gradient that's dark on one end and light on the other has no single text color that reads correctly across its whole surface — rather than guess (average the two colors' luminance, pick based on the midpoint, etc.), the conservative choice is the same one already used for an unset/malformed custom color: don't override, leave the default dark text, which is at least correct on the lighter portion. A real design limitation for a genuinely half-and-half gradient, not silently glossed over — noted here rather than solved with a heuristic likely to be wrong as often as right.

### 27.2 Backend: `set_style` widened, same bounding discipline as AI-12

`block-style-schema.ts`: `background`'s enum gained `'gradient'`; `gradientFrom`/`gradientTo` validate via the same `HEX_COLOR_RE` branch `customBackgroundColor` already used (now one shared branch keyed on `key === 'customBackgroundColor' || key === 'gradientFrom' || key === 'gradientTo'`); `gradientAngle` is a new numeric branch bounded to `0–360`, the same "untrusted AI input needs a sane bound, not just a type check" reasoning as AI-12's `0–400px` spacing cap. A minor implementation note worth recording: the first attempt used `HEX_COLOR_FIELD_KEYS.has(key)` (a `Set` lookup) instead of literal `key === '...'` equality checks for the three-way hex-field branch — this compiles fine at the call site but does **not** narrow TypeScript's type for `key` on subsequent branches the way a literal comparison inside an `if` does before a `continue`, so the later `ENUM_STYLE_FIELDS[key]` lookup stopped type-checking. Caught immediately by `tsc --noEmit` before it ever reached a build or commit — fixed by reverting to literal equality checks, the same style the file already used for `customBackgroundColor`.

### 27.3 A real infrastructure issue hit mid-slice, not a code bug

After the owner asked to stop the dev server (`localhost:3000`), restarting it for this slice's live verification silently came up on **port 3001** instead, with Next.js logging *"Port 3000 is in use by an unknown process"*. `ss -ltnp` showed the actual culprit: a `next-server` worker process from an *earlier* `npm run dev` in this same session was still `LISTEN`-ing on port 3000, despite `pkill -f "next dev"` having reported success. Root cause: `pkill -f "next dev"` matches the command line of the `sh -c "next dev"` wrapper and the `node .../next/dist/bin/next dev` process, but Next.js's dev server sometimes forks a separate `next-server` child process whose command line doesn't contain the string `"next dev"` at all — that child survives the pattern-matched kill and keeps holding the port. This is the same underlying class of issue §22 first documented (a stray, hard-to-explain process squatting on port 3000), recurring for a now-understood, not mysterious, reason. Fixed by finding the actual `LISTEN`-ing PIDs directly (`ss -ltnp | grep :3000`) and killing those, rather than trusting a command-line pattern match. **Worth remembering for any future session**: after `pkill -f "next dev"`, verify with `ss -ltnp` (or `lsof -i :3000`) that the port is actually free before assuming the next `npm run dev` will land on 3000 — a silent fallback to 3001 means every subsequent `curl`/browser check against port 3000 is silently talking to a stale process, not the one just started.

## 32. AI-17 — per-block border and shadow (2026-09-01, continued)

Seventh slice of the AI-10 track, picked by the owner from §31.3's four candidates as the most directly continuous with the proven per-block-override mechanism (background → spacing → gradient → text color → **border/shadow**).

### 32.1 Design: distinct from the existing theme-level card border/shadow

borderWidth?: 'none' | 'thin' | 'medium' | 'thick';  // 0/1/2/4px

### 32.2 Backend

`block-style-schema.ts`: `borderWidth`/`shadow` joined `ENUM_STYLE_FIELDS` (closed value sets, validated the same way as `background`/`textAlign`); `borderColor` joined the existing hex-color literal-equality branch alongside `customBackgroundColor`/`gradientFrom`/`gradientTo`/`textColor`. `set_style`'s description text and `STYLE_FIELD_KEYS` updated to match.

## 33. AI-18 — live visual spacing box-model diagram (2026-09-01, continued)

Second of §31.3's four candidate slices, picked to continue after the owner's bare "продолжай" — no re-ask needed since all four are legitimate, roughly-comparable-priority options and this one carries the least risk (pure UI, zero data model changes). Directly answers the original brief's §7 complaint, quoted almost exactly: *"Пользователь не должен видеть просто набор непонятных input полей... должен визуально понимать, что он редактирует"* — with the brief's own nested margin/padding/content ASCII diagram as the literal target shape.

### 33.1 Design: a visualization layer, not a second editor

The brief's mockup implies an editable diagram (numbers directly adjustable in the boxes). A fully editable version would need to either reimplement the existing `control: 'spacing'` select+number interaction a second time inside the diagram (real risk of the two surfaces drifting out of sync) or make the diagram the *only* way to edit spacing (a much bigger, riskier redesign of an already-working control). Chose a narrower, safer shape instead: `SpacingBoxModel` (`widgets/website-builder/inspector/SpacingBoxModel.tsx`) is **read-only** — it renders the block's current resolved `paddingY`/`paddingX`/`marginTop`/`marginBottom` values as live numbers inside nested boxes, sitting directly above the existing (unchanged) spacing controls in `LayoutSection.tsx`'s "Просто" tab. One source of truth (the existing controls) stays the only way to change a value; the diagram is a reactive preview that re-renders from the same component state on every keystroke/selection, so it can never itself go stale.

Deliberately scoped to the "Просто" tab only — the "Дополнительно" tab (independent per-side padding) already shows each side's value directly in its own field labels (Сверху/Справа/Снизу/Слева), so a second visual diagram there would be redundant, not additive.

**A real, structural difference from generic CSS worth noting**: this system's `BlockStyle` has no `marginLeft`/`marginRight` at all — blocks are always full-width in a vertical page flow, so horizontal margin has no meaning here the way it does in general CSS. The diagram reflects this honestly (the margin ring shows only top/bottom values) rather than inventing fields that don't exist just to match a generic 4-sided mockup.

A small helper, `toPx()`, converts whatever a resolved field value currently is (`SpacingSize` preset string, a custom `number`, or `undefined`) into a plain px number for display, reusing the already-exported `SPACING_PX` lookup table — no new resolution logic, just a display-format conversion of values `LayoutSection.tsx` was already computing for the controls themselves.

### 33.2 Visual design

Devtools-style colors deliberately, not Tavern's own `--tavern-*` palette: orange for the margin ring, green for padding, blue (Tavern's own `--tavern-accent`, for consistency with the rest of the app) for the content placeholder — the same convention every browser's own devtools box-model inspector already uses, chosen specifically so it reads as immediately familiar rather than needing new visual language invented from scratch.

### 33.3 Verified

`frontend/npm run check` (52 tests, unchanged — this slice added a new presentational component with no independent logic worth a dedicated unit test beyond what `toPx`'s trivial, already-tested `SPACING_PX` dependency covers) clean, plus a real `npm run build` (port 3000 checked via `ss -ltnp` first — this time it was just this session's own leftover `next dev` from AI-17's verification, not a new stray-process occurrence; stopped and rebuilt normally). Live-verified against CryptoVault's Hero-adjacent Section block: the diagram rendered real values (96px padding top/bottom, 0px left/right, 0px margin) matching the block's actual configured spacing; selected "Отступы сверху/снизу" and changed it from the `xl` preset to `sm`, confirmed the diagram's numbers updated to 16px in the same interaction (no separate refresh needed) and the canvas's own rendered block visibly shrank to match; reverted to `xl` and confirmed the diagram showed 96px again. Also confirmed the diagram does not appear on the "Дополнительно" tab, as designed.

### 33.4 What remains

Two candidates from §31.3 are still open: Simple/Advanced UI mode split, and the AI introspection API (`getWidget`/`getWidgetSchema`/etc.). A fully editable version of this diagram (numbers directly adjustable in-place) remains a real, larger follow-up if the read-only preview turns out not to be enough — not attempted this slice given the sync-risk reasoning in §33.1.

Different in kind from AI-10 through AI-18 (all style-engine/widget-UI work) — this one closes a gap in what the AI itself can *see*, not what a human can customize, directly answering the second brief's §15A ("AI CONTEXT & BUILDER INTROSPECTION API").

### 34.1 The real gap, confirmed by reading the code, not assumed

`get_project_tree` (AI-1, §6) — the project's first-ever AI tool — returns exactly this per page: `{ id, slug, title, blockCount }`. No block ids. No block types. No content. No style. Every subsequent tool that operates on an *existing* block (`update_block_props`, `set_style`) takes a `blockId` as a required argument, with no tool anywhere in the registry that could tell the model what a valid `blockId` even *is* for a page it didn't just create in the same conversation turn. In practice this meant the model's only source of block ids was its own short-term memory of tool results earlier in the same conversation — completely blind to blocks the human user created or edited in the visual builder, or to any turn further back than the model's own context window reaches. This is precisely the failure mode the brief's §11 names: *"AI НЕ должен... придумывать ID... выполнять изменения без проверки context."*

### 34.2 Two tools, not one, mirroring the brief's own two-level shape

**`get_page_blocks(pageId)`** — brief's `getWidgetTree()`/`getPageStructure()`. Returns a lightweight recursive tree: `{ id, type, hidden?, children? }` per block — deliberately no `props`/`style`, matching the brief's own §3/§9 principle of graduated context levels (a full page's block tree with every block's full content and style would be a lot of tokens for a question that's often just "what's the id of the pricing block"). `hidden` is a plain boolean here (collapsed from the real `Partial<Record<Viewport, boolean>>`) — "is this hidden on any viewport" is enough signal for the model to notice and ask, without spending tokens on the full per-viewport shape.

**`get_block(blockId)`** — brief's `getWidget(widgetId)`. Returns one block's actual current `props`, `style`, `hidden`, and whether it has children, found anywhere in the document (not just top-level) via `findBlockInPages` — the exact same tree-search utility `set_style`/`update_block_props` (AI-2) already use to *write*, now reused to *read*. No new tree-walking logic, no risk of the read and write paths disagreeing about what "the block with this id" means.

Both `low` risk (read-only, same classification as `get_project_tree`), registered in `ai.module.ts` following the file's own documented convention exactly: one new provider file, one new line in the module's `providers` array, no changes to `AiService`/`ToolRegistryService` themselves.

### 34.3 Deliberately not built this slice

The brief's fuller API (§15A) also names `getSiteStructure()`, `getWidgetSchema(widgetType)`, `getWidgetCapabilities(widgetType)`, `getCurrentEditorContext()`, `getAvailableWidgets()`, revision numbers for conflict detection, batch operations, and screenshot-based visual context. None of these are built this slice. `get_project_tree` + `get_page_blocks` + `get_block` together already cover the two things that matter most in practice — "what pages/blocks exist" and "what does this specific block currently contain" — which is what actually blocked real usage; the rest are real, legitimate future slices once (or if) a concrete need for them shows up, not built speculatively ahead of one.

### 34.4 Verified

`backend/npm run check` (176 tests, unchanged — both new tools are thin wrappers around already-tested `WebsitesService.getDraft`/`findBlockInPages`, matching this project's own established precedent of verifying this class of tool live rather than with new unit tests, same as `get_project_tree`/`get_wallet_info` before it) clean. Confirmed the backend container hot-reloaded with no DI errors after adding the two new providers (`docker compose logs` showing a clean `Nest application successfully started`). **Live-verified through two real, separate multi-turn Gemini conversations, not curl and not mocked**: first asked "какие блоки есть на главной странице" — after one transient Gemini `503` (high-demand, not this project's own quota limiter — a legitimate one-time retry, not a repeated hammer against a rate limit) the model correctly chained `get_project_tree` → `get_page_blocks` and listed all 9 real blocks on CryptoVault's home page with their real types (`businessheader`, `hero`, `servicegrid`, `openinghours`, `location`, `reviews`, `contact`, `footer`, `web3wallet`); then asked "какой сейчас текст заголовка и подзаголовка у блока hero" as a follow-up (deliberately not reusing any id from the first answer, to force a fresh lookup) — the model re-ran `get_project_tree` → `get_page_blocks` → `get_block` and reported the Hero block's exact real content (`CryptoVault` / `Рядом с вами` / `Проверенный местный сервис, которому доверяют соседи.`), matching what was actually visible on screen, not a guess.

### 34.5 What this closes

This is the last of the four candidate slices §31.3 presented after the second, larger "rewrite the builder" brief was scoped down. All four are now shipped: border/shadow (AI-17), the visual spacing diagram (AI-18), and now the introspection API's first real slice (AI-19) — Simple/Advanced UI mode is the one candidate from that original list not yet built. §29's consolidated open-items list remains the reference for what's next across the whole project.

## 35. AI-20 — `web3wallet` joins the AI's curated block allowlist (2026-09-01, continued)

Picked up from §29.5's suggested next step ("AI-6's `dataBindings`/`capabilities` for `CustomWidget`" — binding a widget to Web3/Custom Entity data), after §31.3's fourth candidate (Simple/Advanced UI mode split) turned out, on inspection, not to decompose into a bounded slice: most blocks in the registry have only 4–10 props (checked directly, `grep -c "key:"` across `blocks/*/index.tsx`), so there's no real "too many fields" problem to solve, and building the split anyway would mean touching field declarations across all ~13 block-category files for speculative benefit — the exact "don't build for hypothetical future need" anti-pattern this project's own `AGENTS.md` warns against. Declined, not silently dropped — flagging it here so a future agent doesn't waste a slice re-discovering the same thing.

### 35.1 What the §29.5 candidate actually required, once inspected

Sent an `Explore` subagent to check the real current shape of `CustomWidget`/`add_block` before scoping anything. Findings that reshaped the slice:

- **`CustomWidget.schema` composition is scoped to `ALLOWED_BLOCK_TYPES`** — the exact same 6-type curated allowlist `add_block` uses (`heading`/`text`/`quote`/`spacer`/`image`/`button`), not the full ~50-type frontend block registry. `productgrid`/`servicegrid`/`web3wallet` were never composable into a widget, or addable by the AI at all — a real, previously-undocumented gap distinct from the "dataBindings" framing.

### 36.2 A real bug, caught live, not by `npm run check`

First implementation put the exchange-and-cookie logic in `app/auth/callback/page.tsx`, calling the `'use server'`-marked `exchangeGoogleCode` directly from the page's render. `npm run check` and a real `npm run build` both passed clean — TypeScript has no way to know that `cookies().set()` is only permitted inside a genuine Server Action *invocation* (a form submit, programmatic action dispatch) or a Route Handler, not inside a plain function call made during a Server Component's render, even when that function happens to live in a `'use server'` file. Only surfaced doing a real live end-to-end run through actual Google consent in the browser: the backend's own `/auth/exchange` call visibly succeeded in the container logs (a plain `LOG` line, not the `WARN` a real 401 produces — confirmed by deliberately reproducing both to compare), yet the browser still landed on `/auth?error=oauth_failed` with no session cookie set. Root cause: the cookie-write silently threw inside the try block, was swallowed by the local `catch { redirect(...) }`, and never surfaced as a visible server error anywhere `npm run check`/`build` would catch. Fixed by moving the whole exchange to `app/auth/callback/route.ts` (mirrors the project's own pre-existing `app/auth/clear/route.ts`, which already does the equivalent `response.cookies.delete()` — the working pattern was already in the codebase, just not followed for this new path). `SESSION_COOKIE_OPTIONS`/`SESSION_MAX_AGE_SECONDS` moved to `shared/config/session.ts` so both the Route Handler and the existing `loginToAccount`/`registerAccount` Server Actions share one definition instead of two copies drifting apart.

### 36.5 Post-login redirect now returns to the origin the login started from (2026-09-02, continued)

The owner ran a real production build (`next start`) and hit it from their machine's LAN address (`http://192.168.x.x:3000`, visible alongside `http://localhost:3000` in Next's own startup banner), then asked: *"нужно чтобы после авторизации через гугл редирект происходил на origin"* — the post-login redirect always landed on the configured `FRONTEND_URL` (`http://localhost:3000` by default) regardless of which address the login actually started from.

**Why this needed care, not a one-line fix**: Google's callback only ever returns `code`/`state` — the original request's origin has to be carried through the whole round trip (browser → frontend → backend → Google → backend → frontend) some other way. The natural carrier is the same one-shot `state` value already used for CSRF protection (`OAuthStateService`) — its Redis value changed from a placeholder `'1'` to the actual resolved origin string, so `consume(state)` now returns the origin to redirect back to (or `null` if the state itself is invalid/expired, same as before).

**The real risk this creates, and how it's closed**: naively trusting a client-supplied `?origin=` query param and redirecting to it after login would be a textbook open-redirect — a crafted link (`/auth/google?origin=https://evil.example`) would hand the one-shot exchange code (which converts to a real session token via `POST /auth/exchange`) to an attacker's domain, a real account-takeover path, not just a cosmetic bug. `AuthService.resolveOAuthOrigin` never redirects to a client-supplied value directly: it's accepted only if it matches `FRONTEND_URL` exactly or appears in a new explicit allowlist (`ALLOWED_OAUTH_ORIGINS`, comma-separated, empty by default — unset means *only* `FRONTEND_URL` works, identical to the pre-existing behavior); anything else — an unlisted origin, a malformed string that fails `new URL()` parsing, no origin at all — silently falls back to `FRONTEND_URL`, the same safe default as before this change, never an error.

**What shipped**: `app/auth/google/route.ts` (frontend) now appends its own real `request.nextUrl.origin` as `?origin=` when proxying to the backend. `AuthController.googleLogin` reads it and passes it to `AuthService.buildOAuthAuthorizationUrl`... (named `buildGoogleAuthorizationUrl` in the current, post-Facebook-revert codebase — see 36.4's note above), which resolves and validates it before issuing `state`. `completeGoogleLogin` builds the final `/auth/callback` redirect against the origin recovered from `state`, not the fixed config value.

**Verified**: `backend` 183 tests, lint/format/typecheck clean; `frontend` 52 tests, lint/format/typecheck clean, a real `npm run build` showing `/auth/google` unchanged in the route list. Live against the real backend (not curl fakery for the security-relevant part — inspected the actual Redis value each `state` resolved to): no `origin` param → stored value is `FRONTEND_URL`; `origin` exactly equal to `FRONTEND_URL` → itself; `origin` set to the owner's real LAN address *before* adding it to `ALLOWED_OAUTH_ORIGINS` → safely fell back to `FRONTEND_URL` (proves the allowlist actually gates, not just documents); same LAN address *after* adding it to `.env` and restarting → correctly stored and would be used verbatim; a syntactically invalid `origin` string → safely fell back, no crash. Not re-verified through an actual live Google consent screen this slice — the owner's own `next start` process in their own terminal was serving a build from before this fix (Next.js loads its build into memory at boot, a later `next build` on disk doesn't hot-swap it), so a live click-through would have exercised stale client code; the owner needs to restart their `next start` (or switch to `next dev`) to pick up the fix before the very last mile (an actual browser round trip from a non-`localhost` address) can be confirmed end to end.
