## What shipped this batch (context, not gaps)

- Real device-preview: switching to "Десктоп" on a phone now renders an actual ~1280px layout scaled to fit, not a squashed mobile column. (§37.1)
- Style controls reworked: sliders (`scale`) and icon rows (`segmented`) replace plain dropdowns for ordinal/categorical style fields. (§37.2)
- Universal layout system: any container block (`section`/`container`/`columns`) can now be flex or grid, with gap/direction/justify/align — and any block as a child can be `sticky`, fixed-width, or grow. Usable by hand (inspector) and by the AI (`set_style`). (§37.3)
- AI chat accepts image/file attachments (button + clipboard paste), piped to Gemini as multimodal `inlineData`. (§38)
- `add_block` grew from 7 hardcoded block types to the full 48-type registry, with real parent/child nesting (`parentId`) and real capability gating (not just a hidden picker option). New `get_block_schema` introspection tool so the AI doesn't need every field description inlined. (§39)
- `delete_block` and `move_block` — the AI can now fix its own structural mistakes (wrong nesting, wrong order), not just edit props/style on what's already there. Found and fixed a real, independent latent bug along the way: moving a container into its own descendant used to silently delete it, in both the new backend tool and the frontend's own drag-and-drop `moveBlock` — both throw/no-op cleanly now, with regression tests. (§42)
- Orphaned chat-attachment files now get swept automatically — a new background job deletes anything in `uploads/messages/` that's both old (24h+) and never referenced by a sent message, which also incidentally covers the same leak from any other route, not just abandoned AI-chat uploads. (§43)
- **"Builder for a first-time user," phase 1/2 of 5 (owner-approved, presentation-only — no capability removed)**: real inline rich-text editing on the canvas (click text, type, select, Bold/Italic/Link via a floating toolbar — reuses the same Tiptap+sanitize-html pair already proven for posts) for `heading`/`text`/`richtext`/`quote`, and live visual thumbnails in the block library (43 types render a real scaled-down preview of themselves; 5 empty structural types and capability-gated/self-fetching types get a small hand-drawn diagram instead of a blank or network-triggering preview). Found and fixed two real bugs live: invalid nested `<button>` markup from embedding blocks-with-their-own-buttons (e.g. `faq`) inside the library card's own button, and the formatting toolbar rendering behind other canvas chrome for lack of a `z-index`. (§45)
- **Phase 3/5**: one-click ready-made layout patterns ("Готовые макеты", shown first in the block library) — Sidebar+content, Two columns, Three columns — each a real `section > columns > column` tree built from the existing universal layout system (§37.3, no new data-model fields), pre-filled with real instructive placeholder copy, with a live-rendered preview card showing the actual composed proportions (narrow fixed sidebar vs. wide growing column), not a generic icon. (§46)
- **Phase 4/5**: the "Раскладка" tab's display/direction choice is now icon buttons (reusing the same icons already on the `section`/`columns`/`container` library cards), not a text dropdown; the color control now shows the site's own real theme palette as clickable swatches first, with the raw hex input demoted to an explicit "Свой цвет" step (same preset-first pattern already used by spacing/scale controls) instead of always being the only, always-visible option. (§47)
- **Phase 5/5, the plan's last part**: larger bottom-tab icons/text on mobile; and a genuinely broken touch interaction fixed, not just polished — the always-visible "you can add something here" guide line sat on top of a "+" button that was `display:none` until the block was already selected, so a first-time user's most natural action (tapping the inviting line directly) did *nothing at all*. Fixed by making the button always present but dim at rest, full brightness only when its block is selected — live-verified on a real iPhone viewport against Зёрна's actual content: 76 genuinely tappable insertion points visible without selecting anything, confirmed one actually opens the add-block modal. **All 5 parts of the "builder for a first-time user" plan are now shipped.** (§48)
- A real drop-position indicator for drag-and-drop: a thin line now shows exactly where a block (new from the library, or an existing one being moved/reordered, including across container boundaries) will land as you drag, not just at the moment you drop. Settings tab got a labeled section divider and icons on its three tabs. Mobile field editing switched from a two-step "pick a property from a dropdown, then edit it" pattern (an earlier deliberate decision, explicitly reversed by the owner) to a plain always-visible scrolling list, matching Wix/Framer/Webflow/Notion — the component actually got simpler (one render path instead of two). Live-verified with real multi-step `dragover` cycles against Зёрна's real content, not instant drops. (§49)

## Open items, ranked by what to do next

### 1. Never actually tested: "attach a design, get a matching site"
The owner's original ask for this whole work stream. Every piece up to the Gemini call is live-verified; the model side is untested because the Gemini API key's prepayment credit is depleted (confirmed by calling `generateContent` directly — not this app's own rate limiter). **Needs the owner to add credit at [ai.studio/projects](https://ai.studio/projects).** This is the single highest-value next test — it exercises layout, attachments, and the new block allowlist together, for the first time, in one real conversation. (§38.4, §41.2)

### 2. `MAX_TOOL_ITERATIONS = 15` is a paper estimate, not load-tested
Raised from 5 because nesting via `parentId` is inherently sequential (child needs the parent's id from a prior round). Reasoned to need 6–10 rounds for a realistic nested page. Never observed against a real multi-round Gemini conversation — same blocker as item 1. (§39.7, §41.2)

### 3. A real bug found but not fixed everywhere it might matter
Moving a block into its own descendant used to silently delete it (§42.3). Fixed in both the new backend `move_block` tool and the frontend's own `moveBlock`. **Not investigated**: whether this was ever actually reachable by a human through the drag-and-drop UI (dnd-kit's own collision/sortable-context rules might already prevent the drop physically) — worth a quick check before assuming it was a live user-facing bug, not just a latent one only a scripted call could trigger. (§42.3)

### 4. Named non-scope, restated so nothing is silently dropped
- **Bento/asymmetric grids** — no per-child grid-column/row span control yet; `gridColumns` only produces equal-width tracks. (§37.3)
- **Responsive `display`** — only `direction` is per-viewport; can't switch a block from `grid` to `block` per breakpoint today. (§37.3)

### 5. Pre-existing infra flakiness (not root-caused, not new this batch)
- Stray process on `localhost:3000` recurred again in §46's session too (8th+ occurrence total across sessions) — found already running at the start of the slice, left alone since dev was already correctly running on port 3001 from §45. Still unidentified; a JetBrains/WebStorm run configuration remains the leading (still unconfirmed) suspect.
- Backend dev container (`nodemon`+`tsc --watch`) has a reproducible race under rapid consecutive edits — crashes with "Cannot find module dist/main.js" and doesn't self-recover. Workaround: `docker restart tavern-backend-1`. Hit again this batch. Worth 15 minutes of root-cause work if it keeps recurring, not urgent. (§41.2)

### 6. Now that the plan is fully shipped — natural next candidates, not promised, not scoped
Inline rich-text editing (§45) covers only 4 of 48 block types (`heading`/`text`/`richtext`/`quote`) — extending `EditableText`/`EditableRichText` to more content blocks (card titles, button labels, testimonial text) is a real, bounded, likely-valuable next slice using components that already exist. More ready-made layout patterns (§46) — only 3 exist today (sidebar, two-column, three-column); a promo/split-hero pattern was discussed but not built. Neither is scoped or agreed with the owner — listed here only so a future session doesn't have to re-derive them from scratch.
