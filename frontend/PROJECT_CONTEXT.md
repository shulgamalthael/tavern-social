# Project Context

Этот документ описывает **текущее состояние** проекта Tavern Frontend — что здесь
есть и как оно устроено. Он не история изменений: не дописывайте сюда датированные
записи, а обновляйте описание существующего раздела. Правила _как работать_ с
проектом (стиль кода, FSD, BEM, Zustand, auth, git-гигиена) — в [`AGENTS.md`](./AGENTS.md).

## Обзор проекта

«Таверна» — тёмная тематическая социальная сеть (лента, диалоги, друзья,
сообщества, группы, своя страница, настройки, глобальный поиск). Один маршрут
за экраном входа — `/` (`src/app/page.tsx`): разделы переключаются на клиенте
через store `section-navigation`, а не через отдельные Next.js-маршруты.
**Backend подключён и реально используется** (NestJS + Prisma + PostgreSQL +
Redis, `../backend`, порт 4000 по умолчанию): посты (лента, лайки, репосты,
комментарии), диалоги, друзья, сообщества, группы и поиск — всё это реальные
запросы через `backendFetch` (`shared/lib/backend-client.ts`), а не пустые
заглушки. `EmptyState` по-прежнему используется — но как честное отображение
пустого ответа backend, а не признак отсутствия backend. Пользователь входит
через `POST /auth/register`/`/auth/login` (см. «Auth и защита маршрутов»
ниже) — без входа приложение недоступно.

## Архитектура

- **FSD**: `app → widgets → features → entities → shared`. Направление
  зависимостей и запрет на глубокие импорты внутрь чужого слайса частично
  проверяются ESLint-правилом `no-restricted-imports` (`eslint.config.mjs`,
  блоки `fsdBoundaryConfigs`). Подробные правила — в `AGENTS.md`, раздел 3.
- **Состояние**: Zustand-store — только для данных, общих для нескольких
  независимых widgets/features (`entities/post`, `entities/thread`,
  `features/section-navigation`). Данные текущего пользователя — **не**
  Zustand, а React Context (`entities/user`) — см. «Важные решения».
- **Загрузка данных**: единый статус `AsyncStatus` (`idle/loading/success/error`,
  `shared/lib/async-status.ts`) и хук `useAsyncData` (`shared/lib/use-async-data.ts`)
  для данных, не завязанных на общий store. Источники (`entities/*/api/get-*.ts`)
  вызывают реальный backend через `backendFetch` — никаких mock-данных и
  захардкоженных списков. Подробности — `AGENTS.md`, раздел 4.
- **Auth**: `features/auth` (Server Actions + httpOnly cookie) вызывает
  реальный backend (`POST /auth/register`/`/auth/login`), кладёт выданный им
  opaque-токен в cookie `tavern_session`, дальше все запросы к backend несут
  его как `Authorization: Bearer`; `src/proxy.ts` — защита маршрутов.
  Подробности — `AGENTS.md`, раздел 5, и «Auth и защита маршрутов» ниже.
- **Стили**: SCSS Modules + BEM для тематизированных компонентов, Tailwind —
  для утилитарной вёрстки (сейчас почти не используется: весь UI построен на
  компонентах с собственной темой). Общая палитра/токены — CSS-переменные
  `--tavern-*` в `src/app/globals.css`, доступны из любого модуля через `var()`.
- **Шрифты**: Lora (display), Golos Text (UI), JetBrains Mono (mono) —
  `src/shared/config/fonts.ts` (`next/font/google`), подключены в
  `src/app/layout.tsx` как CSS-переменные `--font-display/--font-ui/--font-mono`.

## Auth и защита маршрутов

Backend-аутентификация реальная (см. `AGENTS.md` backend): opaque-токены в
Redis, без JWT.

- **Вход/регистрация — одна форма с двумя вкладками**
  (`features/auth/ui/AuthForm.tsx` на `/auth`, вкладки «Войти»/«Создать
  аккаунт»): email + пароль. `loginToAccount`/`registerAccount`
  (`features/auth/api/actions.ts`) вызывают `POST /auth/login`/`/auth/register`
  через `backendFetch`, получают `{ token, user }`, кладут `token` как есть в
  httpOnly cookie `tavern_session` и редиректят на `/`.
- **OAuth-вход** (2026-09-02, backend `AI_PLATFORM_ROADMAP.md` §36) — кнопки
  «Войти через Google»/«Войти через Facebook» в `AuthForm.tsx`
  (`OAUTH_PROVIDERS`, новый провайдер — одна строка), рендерятся `next/link`
  `<Link>` (не голый `<a>` — ESLint `no-html-link-for-pages` требует это для
  внутренней навигации), реальная полноценная навигация, не Server Action.
  Через тонкий динамический Route Handler `app/auth/[provider]/route.ts`
  (302 на backend — браузер никогда не видит адрес backend напрямую, тот же
  принцип, что у `proxy.ts`; список известных провайдеров здесь — не
  источник истины, реальную проверку делает backend'ый `OAuthConfiguredGuard`).
  Landing-точка после любого провайдера — одна и та же `app/auth/callback/
route.ts` (backend уже знает, какой провайдер выпустил код обмена),
  **обязательно Route Handler, не
  `page.tsx`**: `cookies().set()` можно вызывать только в Server
  Action/Route Handler, не в рендере обычного Server Component — вызов
  `'use server'`-функции напрямую из рендера страницы молча проглатывает
  ошибку установки cookie (реальный баг, пойманный только живым прогоном
  через настоящий Google, не `npm run check`/`build` — см. roadmap §36.2 за
  подробностями). `SESSION_COOKIE_OPTIONS` вынесен в `shared/config/session.ts`,
  общий для этого Route Handler и `loginToAccount`/`registerAccount`.
- **Сессия** — cookie хранит только opaque-токен, выданный backend (не JSON с
  данными пользователя и не JWT). Смысл токена известен только backend
  (`SessionsService` в Redis, TTL). DAL `getSessionUser()`
  (`features/auth/api/session.server.ts`, `server-only`) — резолвит токен в
  профиль через `GET /users/me` (кэш на рендер через React `cache()`),
  единственное место, которое читает cookie напрямую.
- **Текущий пользователь на клиенте** — `CurrentUserProvider`
  (`entities/user/model/current-user-context.tsx`), React Context, а не
  Zustand: инициализируется пропом из `app/(protected)/layout.tsx` (общий для
  всех защищённых маршрутов Server Component), поэтому безопасен относительно
  параллельных запросов на сервере (Zustand-синглтон для персональных данных
  так делать нельзя — см. «Важные решения»).
- **Защита маршрутов** — два рубежа: `proxy.ts` (оптимистичная edge-проверка
  наличия cookie, редиректит в обе стороны без риска цикла) и авторитетная
  проверка сессии в `app/(protected)/layout.tsx` (`getSessionUser()` +
  `redirect('/auth/clear')`) — общая для всех защищённых маршрутов (`/` и
  `/admin`, см. «Админка» ниже). Роут `/admin` поверх неё добавляет свой,
  более узкий рубеж — проверку `role === 'admin'` прямо в
  `app/(protected)/admin/page.tsx`.
- **Забаненный аккаунт** — `SessionAuthGuard` на backend отвечает 403 на
  КАЖДЫЙ защищённый запрос забаненного пользователя (не только на входе), с
  причиной бана в тексте ошибки, если админ её указал. `getSessionUser()`
  различает это explicit-ошибкой `BannedError` (а не молча отдаёт `null`,
  как для «сессии нет» — иначе `(protected)/layout.tsx` просто редиректил бы
  на `/auth`, где тот же аккаунт тут же входит и снова упирается в ту же
  стену без единого объяснения): `layout.tsx` ловит её и рендерит
  `BannedNotice` (`features/auth/ui/`) прямо вместо `children` — отдельного
  роута нет, cookie не трогается, только кнопка «Выйти».
- **Своя страница/профиль** (`widgets/profile`, `features/edit-profile`) —
  имя/подпись/о себе/город/теги и аватар/обложка редактируются там, инлайн
  (`ProfileEditForm`), не в настройках. В `widgets/settings` остались только
  тумблеры приватности и выход из сессии — карточку с именем/подписью оттуда
  убрали как дублирующую редактирование профиля.
  Кнопка «Выйти из зала» — `endSession` (чистит cookie, редирект на `/auth`).

## Features / Domains

### Навигация — `features/section-navigation`

Хранит текущий раздел (`SectionId`). Используется `header`, `navigation-dock`
и корневым `app/home-app.tsx` (решает, какой widget-раздел рендерить). Конфиг
пунктов меню и маппинг раздел → иконка — там же (`config/nav-items.ts`,
`config/section-icons.tsx`); `NavItem.short` — компактная подпись для дока
(см. `widgets/navigation-dock` ниже), `label` — полное название для попапа
«Ещё» и заголовков страниц.

Единственный виджет навигации — `navigation-dock`: один и тот же плавающий
док внизу экрана на мобилке, планшете и десктопе (раньше был отдельный
Instagram-style таб-бар для мобилки — убран в пользу единого стиля).
`PRIMARY_NAV_COUNT` пунктов показываются прямо в доке (иконка + `short`),
остальные — под пунктом «Ещё» в анкорном попапе (тот же паттерн
outside-click-закрытия, что у дропдаунов `header`), без переноса на второй
ряд (`flex-wrap: nowrap`) — лишние пункты всегда уходят в попап, а не ломают
раскладку. До ширины `$bp-tablet` (1024px, `@include mobileOrTablet` в
`shared/styles/_mixins.scss`) текстовая подпись у пункта дока не просто
уменьшается, а прячется совсем (`sr-only`, доступна только скринридерам) —
кнопка становится большой круглой сенсорной целью ≥48px (иконка крупнее,
`aria-label`/`title` вместо видимого текста), а не узкой полоской с
обрезанным словом. Набор пунктов и сам механизм (что показывается в доке, а
что — под «Ещё») от этого не меняется, меняется только то, как выглядит
сама кнопка.

Док сам по себе занимает ровно столько места, сколько нужно его содержимому
(не растянут на всю ширину, не имеет фиксированной высоты). Раньше запас
под него в `.app` был захардкожен (фиксированные 148px «с потолка») — при
любом изменении реального размера дока (брейкпоинт, новый пункт) это число
переставало совпадать с реальностью, и контент либо утыкался в док, либо
под ним оставалась пустая полоса. Теперь сам док меряет свою настоящую
высоту в рантайме (`ResizeObserver` в `NavigationDock.tsx`) и кладёт её в
CSS-переменную `--tavern-dock-h` на `:root`; `.app` (`page.module.scss`)
резервирует снизу ровно `--tavern-dock-h` + `--tavern-dock-gap` (общий
токен зазора «док-до-края», `globals.css`) дважды — вниз до края экрана и
вверх до контента. Меняется размер дока — пересчитывается само, без
отдельной правки под каждый брейкпоинт (как раньше было у
`widgets/messenger` — этих вычислений там больше нет, `.messenger-page`
просто получает от `.app` уже правильно посчитанное место).

### Поиск — `features/global-search`

Поисковое поле в `header` (`⌘K`/`Ctrl+K` фокусирует его) с debounce 300 мс
(`shared/lib/use-debounced-value.ts`) и хуком `useGlobalSearch`
(`model/use-global-search.ts`, не `useAsyncData` — пустой запрос не должен
ничего запрашивать, а `loading` выводится сравнением текущего debounced-
запроса с последним завершённым, а не отдельным `setState` внутри эффекта).
Backend (`GET /search?q=`) ищет по трём сущностям параллельно:

- **люди** — по `User.name`, публичный профиль (имя/подпись/город);
- **сообщества** — по `name`/`about` среди всех сообществ (тот же публичный
  каталог, что и `widgets/communities`);
- **группы** — только среди групп, в которых состоит текущий пользователь
  (группы закрытые, «только по приглашению», без публичного каталога — см.
  `AGENTS.md` backend), иначе поиск находил бы группы, вступить в которые
  всё равно нельзя.

`SearchDropdown` группирует результаты по типу; клик по строке разворачивает
короткую деталь **внутри дропдауна** (не переход на отдельную страницу
сущности — таких страниц в приложении нет, см. «Важные решения»). Единственное
исключение — у сообщества есть кнопка «Перейти к сообществам»
(`goToSection('communities')`), потому что этот раздел уже показывает полный
публичный каталог.

### Лента — `widgets/feed`

**Раскладка.** От `$bp-desktop` (1440px, `@include wide`) у ленты своя,
более широкая полоса — `max-width: 1440px` вместо обычных 1140px
`SectionContainer` (селектор `main.feed`, специально с более высокой
специфичностью, чем у `.section-container`, — оба класса висят на одном
`<main>`, иначе результат зависел бы от порядка подключения стилей).
Колонка (`~700px`) центрируется в этой полосе по-настоящему (`margin: 0
auto`), а не «центр минус место под сайдбар»: сайдбар (`Сейчас в
зале`/`Ближайшие сборы`/`Доска объявлений`) на этой ширине выходит из
потока (`position: absolute`) и докуется правее колонки, не влияя на её
центровку — с небольшой намеренной ступенькой вниз (`top: 30px`, равно
padding-top `SectionContainer` на этой ширине), а не строго вровень с
колонкой. Ниже 1440px — обычная раскладка колонка+сайдбар рядом
(`@include desktop`) или друг под другом (мобилка). Приветствия над лентой
больше нет — колонка начинается сразу с композера.

Композер поста (`features/publish-post`, вариант `feed`), фильтр по табам
(Всё/Друзья/Сообщества/Сборы — локальный `useState`), список постов
(`entities/post`, статус `loading/error/success`, `EmptyState` и для «постов
вообще нет», и отдельно для «нет постов по этому фильтру» с кнопкой сброса).
Вкладка «Сборы» лишь фильтрует существующие посты по `kind: 'events'` —
самой сущности «сбор» (в смысле события/кампании) в проекте нет, см.
«Известные пробелы» ниже. Сайдбар («сейчас в зале», «ближайшие сборы», «доска
объявлений») — три честных `EmptyState`, источника данных для них пока нет
(тот же известный пробел).

**Репосты.** Кнопка «Передать дальше» на карточке (`entities/post/ui/PostCard.tsx`)
переключает репост — backend хранит его как отдельную запись `Post` со
ссылкой `repostOfId` на оригинал (не копию текста), поэтому репост — это
обычная запись ленты, которая просто рендерится с «цитатой» оригинала
(`post.repostOf`), если это поле задано. Лайк/ответ/повторный репост на
карточке репоста всегда применяются к `post.repostOf.id`, а не к id самой
обёрточной записи — так статистика не расходится между «оригиналом» и
«репостом репоста». `usePostStore.repostedPostIds` — карта «репостнул ли я»,
параллельная `likedPostIds`, ключ — всегда id того поста, на который смотрит
интерактив (см. `matchesTarget` в `post-store.ts`). Цитата репоста рендерит
`repostOf.text` тем же способом, что и обычный пост (санитизированный HTML,
см. ниже) — картинки/ссылки оригинала показываются автоматически, без
отдельного кода.

**Реакции.** `toggleLike`/`toggleDislike` (`post-store.ts`) — optimistic
update → запрос → перезапись состояния из ответа backend (актуальные
`likesCount`/`dislikesCount`/`isLikedByMe`/`isDislikedByMe`), rollback в
catch. `pendingReactionByPostId` — лок на пост на время запроса: повторный
клик (лайк/дизлайк, они делят один лок) во время уже летящего запроса
просто игнорируется, а не улетает гонкой параллельных запросов.

**Комментарии.** Кнопка «Ответить · N» разворачивает `CommentList` +
`CommentComposer` (`entities/post/ui/`) прямо под карточкой — локальное
состояние открытия (`useState` в `PostCard`), сами комментарии — в отдельном
`useCommentStore` (`entities/post/model/comment-store.ts`), карта по `postId`,
т.к. один и тот же пост может одновременно быть виден и в ленте, и на стене
профиля. Курсорная пагинация верхнеуровневых комментариев (лимит 3, кнопка
«Показать ещё», `nextCursorByPostId`/`loadMoreComments`) — ответы (replies)
приходят вместе со своим верхнеуровневым комментарием на той же странице.
Создание и ответы есть, редактирования/удаления отдельного комментария нет
(не запрошено).

**Создание и редактирование поста.** Один компонент —
`features/publish-post/ui/PostEditor.tsx` (Tiptap, `mode: 'create' | 'edit'`)
— используется и в композере ленты (`PostComposer`, вариант `feed`,
инлайн), и в модалке редактирования (`features/publish-post/ui/
EditPostModal.tsx`, открывается из «···» на `PostCard`, только для своих
записей, не для карточек репоста). Поддерживает жирный/курсив/подчёркивание/
заголовки/списки, ссылки с кастомным текстом (свой попап, не `prompt()`) и
позиционируемые в тексте картинки (до 10 на пост, лимит `MAX_POST_IMAGES`).
Контент — санитизированный на backend HTML (`Post.text`), рендерится на
frontend через `dangerouslySetInnerHTML` — безопасно, потому что источник
уже прошёл `sanitizePostContent` на сервере, а не потому что frontend его
дополнительно чистит. Картинки грузятся одним multipart-запросом вместе с
публикацией/сохранением (не раньше) — orphaned-файлов не возникает. Ссылки,
для которых backend получил метаданные, показывают карточку превью
(`LinkPreviewCard`) под текстом.

### Мессенджер — `widgets/messenger`

Полноэкранный раздел (не боксовая карточка на странице — `flex: 1` в
`.app`, см. `page.module.scss`): список диалогов + чат занимают всю высоту,
которую `.app` им оставляет — включая динамический запас под плавающий док
(см. «Навигация» выше, `--tavern-dock-h`), без отдельных вычислений под
него специально для мессенджера. На десктопе — под шапкой сайта; на
мобильном/планшете (`@include mobileOrTablet`, до 1024px)
у раздела «Диалоги» шапки нет вовсе — `HomeApp` оборачивает `AdminBar`+
`Header` в `.app__top`, который на этой ширине схлопывается (`display:
none`) именно для секции `messages` (`hideHeaderOnNarrowScreens` в
`home-app.tsx`), и мессенджер занимает весь экран целиком: там и так тесно,
а шапка отъедала заметную долю чата, тогда как на десктопе места достаточно
и её не трогаем. Список диалогов + чат — `entities/thread`. Пустой список
диалогов не рендерит панель чата вовсе (раньше было потенциальное падение
на `threads[0]` — исправлено), вместо этого — `EmptyState` с кнопкой
«Перейти к друзьям». Какой диалог открыт (`activeThreadId`) и раскрыт ли
чат на мобильном (`isChatOpen`) — состояние в `useThreadStore`/локальное
состояние виджета соответственно; см. также `draftTarget` там же —
черновик переписки до первого сообщения, отдельно от реальных `Thread`
(раздел «Заявки в друзья»/сообщения без дружбы ниже). Счётчик
непрочитанных — селектор `selectUnreadThreadCount` (`entities/thread`); в
`header` сейчас не отображается (кнопка «Сообщения» с бейджем убрана из
шапки), но остаётся в панели навигации.

**Переписка не требует дружбы.** Backend никогда не проверял дружбу для
сообщений (`ThreadsService` — только участие в `Thread`), но раньше фронт
создавал сам `Thread` в БД в момент открытия чата, ещё до первого
сообщения — у случайного собеседника в списке диалогов тихо появлялась
пустая запись. Теперь `openDirectThreadWith` (клик «Написать» на карточке
друга/в чужом профиле) для существующего диалога работает как раньше, а
для нового — только выставляет `draftTarget` (открывает пустой чат в UI),
ничего не создавая на backend; `Thread` заводится в `sendMessage`, вместе с
первым реально отправленным сообщением. `receiveMessage` от совсем нового
собеседника (диалога ещё нет в сторе) не пытается собрать `Thread` из
одного socket-сигнала, а честно перечитывает список через REST — тот же
приём, что и `receiveParticipantAdded`.

**Содержимое сообщения.** `ChatMessage.senderId` (не только `mine`) —
кластеризация подряд идущих сообщений в `buildChatRows`
(`MessengerWidget.tsx`) идёт по нему, а не по `mine`: в групповом чате все
чужие сообщения формально `mine: false`, но у разных собеседников разный
`senderId`, и их сообщения не должны слипаться в один визуальный блок под
одной подписью. В группе (`isGroup`) над первым сообщением чужого кластера
показывается `ClusterSenderLabel` — аватар + имя отправителя (в 1:1 не
нужно, собеседник и так один, виден в шапке чата). Текст сообщения проходит
через `linkifyText` (`shared/lib/linkify-text.tsx`) — голые `http(s)://`/
`www.` превращаются в кликабельные ссылки; функция всегда возвращает
React-узлы (никогда HTML-строку и никакого `dangerouslySetInnerHTML`), а
`href` дополнительно проверяется на схему (только `http`/`https`) — так
текст сообщения в принципе не может стать вектором для `javascript:`-ссылок
или другой инъекции через «ссылку».

**Групповые диалоги.** `Thread.participants` — join-таблица на N
участников с самого начала (см. `backend/prisma/schema.prisma`), поэтому
группа — обычный `Thread`, без отдельной сущности. Кнопка в хедере чата
(`AddParticipantDropdown`, поиск через `features/global-search`) добавляет
участника через `POST /threads/:id/participants/:userId`
(`ThreadsService.addParticipant`), но по-разному в зависимости от того,
что за диалог сейчас открыт:

- **Личная переписка (1:1) не превращается в групповую.** Добавление
  участника создаёт НОВЫЙ `Thread` с текущими собеседниками + новым, а
  исходный диалог остаётся как есть, нетронутым, со своей историей — если
  после этого захочется снова написать один на один, переписка на месте.
  Фронт получает от backend другой `thread.id`, чем передавал в запросе, и
  по этому признаку понимает, что диалог новый: добавляет его в начало
  списка (не заменяет исходный) и переключает `activeThreadId` на него
  (`useThreadStore.addParticipant`).
- **Уже групповой диалог (3+) просто дополняется на месте** — тот же
  `threadId`, без создания дубликата. Так повторные добавления в открытую
  группу никогда не плодят новые `Thread`.

Имя/аватар группы синтезируются на фронте из имён участников
(`displayNameFor` в `entities/thread/api/map-thread.ts`) — отдельного поля
«название» у диалога нет.

**Расширенные действия с сообщением.** `Message` в схеме несёт `editedAt`,
`pinnedAt`, `forwardedFromId` и `replyToId` (оба — self-relation с
`onDelete: SetNull`, тот же приём, что `Post.repostOfId`: пересланная копия
или ответ не ломаются, если оригинал удалят — `deleteMessage` ниже) и
`attachments: MessageAttachment[]` (тот же паттерн, что `PostImage`).
`MessageBubble.tsx` — общее меню на каждом сообщении: «Ответить» (на любом),
«Редактировать»/«Удалить» (только на своих), «Переслать», «Закрепить»/
«Открепить» (зависит от `pinnedAt`) — один компонент, а не отдельный проход
по файлу на каждый экшен. Открывается кликом по «···», правым кликом
(десктоп, `onContextMenu` + `preventDefault`) или долгим нажатием (тач,
`onTouchStart` с таймером ~500мс, отменяется по `onTouchMove`/`onTouchEnd`)
— все три ведут к одному и тому же уже существующему попапу у бабла, а не к
отдельному плавающему меню за курсором: так проще и не требует своей логики
позиционирования у экрана.

- **Редактирование** — `useThreadStore.editingMessage`
  (`{ threadId, messageId, text }` или `null`). `MessageComposer.tsx` в этом
  режиме показывает баннер-отмену и предзаполняет поле текстом сообщения —
  синхронизация без эффекта (`setState` прямо в теле рендера при смене
  `editingMessage.messageId`, «adjust state during render» из React-доков,
  не `useEffect` — react-hooks/set-state-in-effect не даёт вызывать
  `setState` синхронно в эффекте). Отредактированное сообщение получает
  пометку «изменено» рядом со временем.
- **Пересылка** — `ForwardMessageModal.tsx` (`widgets/messenger/ui`), пикер
  по уже загруженным диалогам (`useThreadStore.threads`) с локальным
  фильтром по имени — не отдельный REST-поиск, как у
  `AddParticipantDropdown` (там ищут людей, а не диалоги). Пересланное
  сообщение — новая запись с `forwardedFromId`, в бабле — плашка «Переслано
  от {имя}» (клик ведёт на профиль автора оригинала).
- **Вложения** — картинки и файлы до 5 МБ (`common/lib/upload.ts`,
  `createChatAttachmentMulterOptions`, `uploads/messages/`). Текст сообщения
  стал `@IsOptional()` в `SendMessageDto` — можно отправить только
  вложение(я) без текста, но не пустое сообщение вовсе (проверка «текст ИЛИ
  файл» — в `ThreadsService.sendMessage`). `entities/thread/api/send-message.ts`
  всегда шлёт multipart через `backendUpload`, даже без файлов — один код
  пути вместо двух веток JSON/multipart. Одна картинка в бабле — без кропа,
  держит те пропорции, в которых её загрузили (`max-height: 320px`,
  `object-fit: contain`, без `aspect-ratio`); 2+ картинок — по-прежнему
  сетка с квадратным кропом (единой раскладке нескольких превью разной формы
  иначе не за что зацепиться, а у одной картинки в этом компромиссе смысла
  нет). Клик по картинке открывает уже существующий `ImageLightbox`; файлы —
  чип с иконкой/именем/размером и прямой ссылкой на скачивание.
  `MessageComposer.tsx` показывает превью прикреплённых файлов (blob-URL
  через `URL.createObjectURL`, освобождается в cleanup эффекта — иначе живёт
  до закрытия вкладки) с клиентской проверкой размера/количества до
  отправки; backend всё равно перепроверяет сам как последний рубеж. Если
  последнее сообщение диалога — вложение без текста, список диалогов слева
  показывает «📷 Фото»/«📎 Файл» вместо пустой строки (`threadPreviewText`
  в `MessengerWidget.tsx`).
- **Ответ** — `SendMessageDto.replyToId` (опционален, должен указывать на
  сообщение из ТОГО ЖЕ треда — проверяет `ThreadsService.sendMessage` через
  `assertMessageInThread`), это не копия, а обычное сообщение с
  дополнительной ссылкой (в отличие от пересылки). `ReplyToDto`/`ReplyTo` —
  живая цитата (`text`/`senderName` отражают текущее состояние оригинала на
  момент запроса, не снимок на момент ответа, как у пересылки — редактируют
  оригинал, меняется и цитата) плюс флаг `hasAttachment` для плашки
  «Вложение» вместо пустого текста, без подгрузки самих вложений оригинала.
  `useThreadStore.replyingTo` — взаимоисключающе с `editingMessage` (начало
  одного отменяет другое, обе стороны, как в большинстве чатов).
  `MessageComposer.tsx` показывает баннер-цитату над полем ввода;
  `MessageBubble.tsx` — цитату с полосой слева внутри бабла, клик скроллит к
  оригиналу.
- **Удаление** — только своё сообщение, необратимо, без плейсхолдера
  «сообщение удалено» (тот же выбор, что `PostsService.remove`) —
  `ThreadsService.deleteMessage`, `DELETE /threads/:id/messages/:messageId`.
  Вложения на диске подчищаются отдельно от каскада БД (каскад стирает
  только строки `MessageAttachment`, не сами файлы — `deleteUploadedFile` в
  цикле после `prisma.message.delete`). Ответы/пересылки на удалённое
  сообщение не пропадают — `onDelete: SetNull` в схеме просто обнуляет
  ссылку, они остаются в своей истории без цитаты/источника.
  `useThreadStore.deleteMessage` убирает сообщение из `messages`/
  `pinnedMessages` сразу по ответу REST (свой self-echo по сокету не
  фильтруется отдельно, как у `message:new`/`message:edited` — повторное
  удаление уже отсутствующего id идемпотентно, см. `removeMessage`).
  `MessengerWidget.tsx` подтверждает удаление модалкой (тот же паттерн, что
  и подтверждения в админке).
- **Эмодзи и «стикеры»** — `features/send-message/ui/EmojiPicker.tsx`,
  куратированный статический список по категориям (без внешней
  emoji-зависимости), вставка в позицию курсора в поле ввода (не в конец
  строки). Открытие/закрытие пикера — контейнер оборачивает и кнопку-тумблер,
  и попап одним `ref` с общим pointerdown-слушателем в родителе
  (`MessageComposer.tsx`), а не самоуправляемый попап — тот же паттерн, что
  `AddParticipantDropdown`/`MessengerWidget` (иначе клик по самой кнопке
  открытия закрывает и тут же переоткрывает попап — гонка между
  pointerdown-слушателем закрытия и click-обработчиком тумблера). Сообщение
  из 1-3 эмодзи и больше ничего (`shared/lib/is-emoji-only-text.ts`,
  `Intl.Segmenter` с `granularity: 'grapheme'` — обычный `.length`/regex по
  эмодзи ненадёжен из-за составных эмодзи с ZWJ/тоном кожи) рендерится в
  `MessageBubble.tsx` как «стикер»: крупным шрифтом, без фона/паддинга
  пузыря.
- **Закрепление** — `Thread.pinnedMessages` (сортировка по `pinnedAt` desc),
  backend отдаёт весь `ThreadDto` заново при pin/unpin (`thread:pinned-changed`)
  вместо частичного патча — проще и достаточно при реалистичном числе
  закреплённых. `MessengerWidget.tsx` показывает тонкую плашку под шапкой
  чата с текстом (через тот же `threadPreviewText`, что и список диалогов) и
  маленькой квадратной миниатюрой (22px, кроп — это просто ориентир, что за
  сообщение, не полноразмерный просмотр) первого закреплённого — несколько
  переключаются счётчиком-стрелкой; клик скроллит к сообщению
  (`document.getElementById` по стабильному `id="message-{id}"` на бабле +
  `scrollIntoView`).
- **Поиск** — `features/search-messages` (`useThreadSearch`/
  `useAllThreadsSearch`, тот же debounce-приём, что
  `features/global-search/model/use-global-search.ts`: `loading` —
  производное от сравнения debounced-запроса с последним завершённым
  ответом, не отдельный `setState` в теле эффекта). В чате — узкая панель
  под шапкой (`ThreadSearchBar`); по всем диалогам — модалка
  (`AllThreadsSearchModal`, результаты сгруппированы по диалогу). Оба ведут
  на то же `scrollToMessage`, что и закреплённые сообщения; для
  кросс-чатового результата сначала переключает `activeThreadId`
  (`openThreadAndScrollTo`), затем ждёт коммита React через
  `requestAnimationFrame` перед скроллом — сообщения уже в сторе (весь
  список грузится один раз), но DOM-узел бабла появляется только после
  рендера.

### Real-time — Socket.IO

Единственное WS-соединение приложения создаётся один раз в
`app/home-app.tsx` (singleton — не в отдельных виджетах) и живёт, пока
смонтирован `HomeApp` (весь залогиненный сеанс); закрывается в cleanup
эффекта при размонтировании (logout → редирект на `/auth` → размонтирование).

- **Backend**: единственный шлюз — `RealtimeGateway`
  (`src/infrastructure/websocket/realtime.gateway.ts`), НЕ привязан к
  конкретному домену. Глобальный `RealtimeModule` экспортирует его, поэтому
  любой feature-модуль (сейчас — `threads`, `friends`) может внедрить его и
  вызвать `emitToUser(s)`, не создавая свой собственный gateway с
  дублированной логикой подключения/комнат. Аутентификация — одноразовый
  билет (`SocketTicketsService`, Redis, TTL 60с); после `handleConnection`
  сокет присоединяется к комнате `user:<id>`. Бизнес-логика (кто получит
  событие, что в нём) решается в `Controller`, ПОСЛЕ вызова `Service` — тот
  же паттерн, что и для REST (`Service` ничего не знает о сокетах).
- **Frontend**: `app/home-app.tsx` подписывается на события и диспатчит их в
  соответствующий domain-store — никогда напрямую в UI-компоненты.
- **События** (`domain:verb`, по аналогии с уже существовавшим `message:new`):
  - `message:new` → `useThreadStore.receiveMessage` (с self-echo-фильтром по
    `senderId`, и id-дедупом на случай повторной доставки после reconnect).
  - `friend-request:new` / `friend-request:accepted` → `useFriendStore.receiveNewRequest/receiveAccepted`
    - `useNotificationStore.receiveRealtimeUnread` + toast. Payload —
      `{ notificationId, actor: PublicProfile }`: `useFriendStore` всё равно
      просто перечитывает список из REST (не патчит вручную), но профиль
      актёра нужен сразу для toast'а — он одноразовый, не синхронизируемое
      состояние, поэтому здесь можно снэпшотить данные в payload (в отличие
      от персистентных store'ов).
  - `friend-request:removed` → `useFriendStore.receiveRemoved`. Остаётся
    минимальным сигналом `{ userId }` — молчаливое списочное событие, без
    toast'а и без записи в `Notification` (отклонённая/отменённая заявка не
    уведомление).
  - `notification:new` → `useNotificationStore.receiveRealtimeUnread` (если
    `payload.isNew`) + toast. Payload — `{ notificationId, type, actor,
actorCount, isNew, post: {id, text}, commentText? }`. См. «Уведомления»
    ниже.
- **Reconnect** — критично: `auth` в `io(...)` передаётся ФУНКЦИЕЙ, а не
  объектом. Билет одноразовый — если передать его один раз как статический
  объект, Socket.IO будет переиспользовать этот же (уже использованный)
  билет на каждой автоматической попытке reconnect, и после ЛЮБОГО разрыва
  соединения real-time молча и навсегда переставал бы работать (это была и
  есть найденная и исправленная причина «real-time не работает»). Функция
  вызывается заново перед каждой попыткой подключения и всегда запрашивает
  свежий билет через `getSocketTicket()`. На `connect` (срабатывает и на
  первом подключении, и на каждом reconnect) вызывается `loadThreads()` —
  Socket.IO не буферизует пропущенные события, поэтому это досинхронизация
  диалогов на случай пропусков во время разрыва.
- **Где WebSocket НЕ используется** (сознательно): счётчики самого поста
  (`likesCount`/`commentsCount`/`repostsCount`) не рассылаются живым
  зрителям поста — вступление в сообщество/группу, поиск, настройки тоже
  меняются только для самого вызвавшего пользователя. Исключение — лайк/
  комментарий/репост чужого поста и заявка в друзья **дополнительно**
  адресно уведомляют автора/получателя через `notification:new`/
  `friend-request:*` (см. «Уведомления» ниже) — это не синхронизация
  списка для всех, а одно целевое событие для одного человека.

### Уведомления — `entities/notification`, `widgets/notifications`, `widgets/notification-toaster`

Два независимых, но связанных механизма — не путать один с другим:

1. **Компактные toast-попапы** (`entities/notification/model/toast-store.ts`,
   `useToastStore`) — неблокирующая, одноразовая реакция на real-time событие:
   новое сообщение, заявка/принятие в друзья, лайк/комментарий/репост на
   своём посте. Максимум 3 одновременно видимых, остальные ждут в очереди
   (FIFO), автозакрытие через 5с, дедуп по `key` — повторное событие того же
   диалога/уведомления **обновляет** существующий toast на месте, а не
   добавляет ещё один (иначе быстрая серия лайков превращается в стопку
   одинаковых попапов). Сообщения в этот механизм не попадают как
   персистентные уведомления (см. ниже) — они уже честно хранятся в
   `Thread`/`Message`, toast для них строится прямо из `message:new` и уже
   загруженного `useThreadStore`.
2. **Персистентная лента уведомлений о контенте** — по-настоящему новая
   сущность backend, `Notification` (Prisma), только для типов, которые
   реально существуют в бизнес-логике: `friend_request`, `friend_accepted`,
   `post_like`, `post_comment`, `post_repost`. Никаких упоминаний/ответов на
   комментарии — их нет в приложении. `post_like`/`post_repost` **группируются**,
   пока непрочитаны: новый лайк того же поста обновляет существующую строку
   (`actorCount++`, до 3 последних `recentActorIds`), а не плодит новую —
   `post_comment` не группируется, у каждого комментария свой уникальный
   текст. Никогда нет самоуведомлений (лайк/комментарий/репост своего же
   поста не создаёт запись — проверка `authorId !== actorId` в
   `PostsController`).
   - Backend: `NotificationsModule` (`src/modules/notifications/`) —
     `NotificationsService` (единственное место, пишущее в таблицу),
     `GET /notifications` (курсорная пагинация), `GET /notifications/unread-count`,
     `PATCH /notifications/:id/read`, `PATCH /notifications/read-all`.
     Эмиссия `notification:new` — в `PostsController`/`FriendsController`,
     ПОСЛЕ вызова сервиса (тот же паттерн Controller-решает-emit, что и для
     сообщений/заявок). Payload включает флаг `isNew` — группированное
     обновление существующей непрочитанной строки не должно повторно
     увеличивать счётчик непрочитанных на frontend.
   - Frontend: `useNotificationStore` (`entities/notification/model/notification-store.ts`)
     хранит список + `nextCursor`/`status` + `unreadCount` отдельно — общий
     store, а не `useAsyncData`, потому что бейдж в шапке должен жить, даже
     когда страница уведомлений не смонтирована.
   - Страница `widgets/notifications` — свой `SectionId: 'notifications'`,
     достижима через колокольчик в шапке и через попап «Ещё» единого
     навигационного дока (`NAV_ITEMS`, в самом конце списка). Клиентская
     группировка по дню
     («Сегодня»/«Вчера»/дата), infinite scroll через `IntersectionObserver`
     на сентинел-див.
   - Колокольчик в `widgets/header` — бейдж непрочитанных + дропдаун с
     последними 5 уведомлениями (`NotificationsDropdown`, тот же паттерн
     позиционирования, что `SearchDropdown`) и «Посмотреть все».

### Друзья / Сообщества / Группы

Списочные разделы поверх `entities/friend` / `entities/community` /
`entities/group` — `Loader` во время загрузки, `ErrorState` с повтором при
ошибке, `EmptyState` при пустом списке. `friends` — курсорная пагинация
через `useFriendStore` (см. ниже), `communities` — свой курсорный
`useState` в `CommunitiesWidget` (потенциально длинный публичный каталог, но
без real-time-обновлений, поэтому не общий store, см. `AGENTS.md` §4),
`groups` — обычный `useAsyncData(getGroups)` без пагинации: список
ограничен собственными членствами пользователя (закрытые группы, не
публичный каталог), естественно небольшой. «Вступил в сообщество» —
локальный `useState` виджета `communities`, по умолчанию пусто (раньше был
захардкожен один «вступленный» демо-элемент).

`widgets/friends` — не список, а адаптивная сетка карточек (`.friends__grid`,
`repeat(auto-fit, minmax(240px, 320px))` — `auto-fit`, не `auto-fill`:
с `auto-fill` пустые «фантомные» колонки резервируются, даже когда реальных
карточек меньше, чем помещается в строку, и неполная последняя строка
оставалась у левого края шириной в минимум с пустым местом справа;
`auto-fit` схлопывает пустые колонки, и существующие карточки растягиваются
до общего максимума (320px) вместо того чтобы остаться на минимуме — вся
плитка, включая неполную последнюю строку, выглядит одинаково плотно
набранной): у `FriendCard` крупный аватар и имя по центру сверху, ниже слева
— о себе (обрезано до 3 строк), факты, теги (максимум 4 + бейдж `+N`),
кнопки прижаты к низу через `margin-top: auto` — так все карточки в ряду
выравниваются по кнопкам независимо от длины текста у соседей. Разрыв
дружбы — `removeFriend`
(`DELETE /friends/:userId`), кнопка-иконка рядом с «Написать» на карточке.
Написать можно и не другу — дружба не требует ни `FriendCard`, ни
`UserProfileView` (`openDirectThreadWith` в `entities/thread`, см.
«Мессенджер» выше — сам `Thread` при этом не требует существующей
`Friendship`, backend это никогда не проверял).

**Заявки в друзья.** Дружба заводится через заявку/подтверждение — backend
хранит отдельную `FriendRequest` до принятия/отклонения/отмены, `Friendship`
появляется только после принятия (см. `AGENTS.md` backend). Если получатель
уже сам отправил встречную заявку, backend не создаёт вторую, а сразу
принимает существующую. Данные живут в `useFriendStore`
(`entities/friend/model/friend-store.ts`) — не `useAsyncData`, потому что с
появлением real-time-доставки (см. «Real-time» ниже) список заявок должен
обновляться, даже пока `FriendsWidget` не смонтирован. `widgets/friends`
показывает блок «Заявки в друзья» (входящие — Принять/Отклонить, исходящие —
Отменить) над обычным списком друзей, только если такие заявки есть.
`UserProfileView` (профиль чужого пользователя) в этот store не пишет — его
кнопка «Добавить в друзья» отражает статус только по одному конкретному
профилю, вызывает `entities/friend/api/*` напрямую.

### Своя страница и чужой профиль — `widgets/profile`

Своя страница: обложка/аватар/имя — реальные данные текущего пользователя,
подпись падает на честный плейсхолдер «Ещё не рассказали о себе», если пусто.
Блоки «О себе» и «Фотографии» — `EmptyState` (собственная страница не
показывает `about`/`tags` — так было решено раньше; это отдельный
пре-существующий пробел, не тронутый при добавлении чужих профилей ниже).
Стена — те же посты из `entities/post` с `EmptyState`, если их ещё нет.

**Просмотр чужого профиля** (`UserProfileView`, тот же виджет) открывается
кликом на человека в результатах поиска (`goToUserProfile(userId)` в
`useNavigationStore` — поле `viewedUserId`, отдельного маршрута нет, как и
для остальных разделов; сбрасывается любым `goToSection`, чтобы не залипало
при переходе в свой профиль через аватар в шапке). Данные — `GET /users/:id`
(`entities/user/api/get-user-profile.ts`), включая статус дружбы. Кнопка
действия зависит от статуса: «Добавить в друзья» / «Заявка отправлена»
(отмена) / «Принять заявку» / «Вы друзья» — статус после действия
обновляется локальным `useState`-оверрайдом (тот же паттерн, что «Вступил в
сообщество» у `communities`), плюс всегда «Написать сообщение»
(`openDirectThreadWith` из `entities/thread`, как в `FriendsWidget`). «О
себе» здесь честно показывает `about`/`tags`/город, если есть. Стена —
только чтение, без композера.

### Настройки — `widgets/settings`

Имя/подпись здесь больше не редактируются (переехали в `ProfileEditForm` на
собственной странице, см. «Auth и защита маршрутов» выше) — только тумблеры
приватности и блок «Аккаунт». Тумблеры — демо-конфиг
(`config/settings-toggles.ts`), локальный `useState`: это UI-настройки, а не
серверные сущности, поэтому не подпадают под «убрать mock-данные» — но и не
персистятся (не подключено к сессии, это можно сделать позже тем же
паттерном, что и `updateProfile` в `entities/user`). Блок «Аккаунт» — выход
из сессии.

### Админка — `widgets/admin`, отдельный роут `/admin`

Не раздел SPA, а собственный маршрут (`app/(protected)/admin/page.tsx`) —
у него нет общего `Header`/`NavigationDock` из `HomeApp`. Навигация внутри
`/admin` — левый **сайдбар** (`AdminSidebar`, заменил собой более раннюю
горизонтальную шапку `AdminHeader` — та же навигация по вкладкам, просто
вертикально, как в WordPress): `position: fixed` (не `sticky` — у `/admin`
нет `.app`-скролл-контейнера, страница скроллится штатно на уровне `window`,
сайдбар должен оставаться на месте при любой длине контента), внутри —
ссылка назад, бренд-марка «Админка», сама навигация по вкладкам (иконка +
подпись, `role="tablist"`) и аватар текущего пользователя внизу.
`AdminWidget` балансирует фиксированную ширину сайдбара отступом
`margin-left` на контентной колонке (оба берут значение из
`admin-tokens.scss`). На узких экранах (`@include mobile`,
`AdminSidebar.module.scss`) подписи пунктов и текстовые ярлыки («Назад в
Таверну», «Админка», «Вы вошли как …») прячутся — сайдбар схлопывается в
иконочную рельсу, остаются только круглые иконки-кнопки с `title`/
`aria-label`, тот же паттерн, что и у дока, но без ellipsis-подписи. Ссылка
на `/admin` из дока (`widgets/navigation-dock`) — обычный `next/link`, не
`goToSection`.

**`AdminBar` — индикатор на основном сайте, не внутри `/admin`.** Отдельный
компонент (`widgets/admin/ui/AdminBar.tsx`), рендерится поверх `HomeApp` для
`role === 'admin'` (решение принимает вызывающий, `app/home-app.tsx` — сам
компонент роль не проверяет) — постоянная полоска-напоминание «вы
администратор» с быстрыми ссылками на `/admin#<таб>` (тот же приём, что
`#wpadminbar` в WordPress), чтобы не искать админку в доке («Ещё» →
«Админка»). Намеренно контрастная (`--tavern-ink` фон вместо
`--tavern-surface` у `Header`, `position: sticky` `top: 0`, `z-index: 30`) и
во всю ширину без центрирующего `max-width` — не сливается с `Header`
визуально, читается как отдельный системный слой поверх темы сайта, а не
ещё один ряд той же шапки. `Header` стыкуется под ней без наложения через
`top: var(--admin-bar-h, 0px)` (переменная выставляется классом
`.app--with-admin-bar` на корневом `<div>` в `home-app.tsx`, значение —
фактическая высота `AdminBar`, меняются оба вместе).

Два независимых рубежа защиты, оба обязательны:

1. **Сессия** — `app/(protected)/layout.tsx` (общий для `/` и `/admin`, см.
   AGENTS.md про auth: «если появится больше защищённых маршрутов, поднимите
   в `(protected)/layout.tsx`» — с появлением `/admin` это и произошло,
   `app/page.tsx` переехал в `app/(protected)/page.tsx`). Без сессии —
   `redirect('/auth/clear')`.
2. **Роль** — `app/(protected)/admin/page.tsx` отдельно проверяет
   `currentUser.role === 'admin'`, иначе тихий `redirect('/')` (страница как
   будто не существует для не-админа, без страницы «нет доступа»). Второй
   вызов `getSessionUser()` здесь не лишний запрос — DAL обёрнут в React
   `cache()`, дедуплицируется в рамках одного рендера.

Оба рубежа — только UX (не даёт зайти по прямой ссылке без сессии/роли).
Настоящая защита данных — backend: `AdminGuard`
(`common/guards/admin.guard.ts`) поверх `SessionAuthGuard`, который теперь
на **каждом** защищённом запросе (не только при логине) догружает
`role`/`isBanned` из базы — у `RequestUser` появилось поле `role`.
Self-service получения роли `admin` через `backend/prisma/promote-admin.ts`
(`npm run promote-admin -- email@example.com`) остаётся единственным способом
выдать её **первому** администратору (bootstrap с пустой базой) — после
этого дальнейшее управление ролью идёт уже через саму админку (см.
«Пользователи» ниже), CLI-скрипт для этого больше не нужен.

Пять вкладок, тот же локальный `useState`-таб-свитчер, что и `FeedWidget`:

- **Дашборд** (`AdminDashboard`) — агрегаты по существующим данным
  (`AdminService.getStats`): счётчики + два самодельных SVG-бар-чарта
  (регистрации/посты за 30 дней, один hue — см. `dataviz`) + топ авторов по
  числу постов + топ групп/сообществ по числу участников (тот же
  ранжированный ряд, переиспользует разметку/классы топ-авторов). Это **не**
  отдельная система трекинга посещений — специальной аналитики визитов в
  проекте нет и не запрашивалась, дашборд считает то, что уже есть в БД
  (`createdAt`/`membersCount`), а не новый event-pipeline.
- **Пользователи** (`AdminUsersPanel`) — поиск (по имени/email/**id**,
  `id` — `contains`, не точное совпадение) + фильтры по роли/статусу
  (чипы, тот же визуальный язык, что и табы) + курсорная пагинация (тот же
  безстор-приём, что `CommunitiesWidget`, см. AGENTS.md §4) + бан/разбан
  (`isBanned`/`bannedAt`/`bannedReason` на `User` — данные пользователя не
  трогаются, просто блокируется вход) + необратимое удаление аккаунта
  (каскад в схеме сам чистит связанные строки, отдельно чистятся только
  файлы аватара/обложки на диске) + **выдача/снятие роли `admin`**
  (`AdminService.setUserRole`, кнопка «Сделать админом»/«Снять админа» на
  каждой строке кроме своей собственной). Три инварианта на снятие роли и
  бан/удаление держит backend, а не UI: нельзя изменить/забанить/удалить
  самого себя, нельзя забанить/удалить другого админа, и в системе всегда
  должен остаться хотя бы один администратор (снятие роли у последнего
  админа — 400). `id` записи показан бейджем `IdBadge` (`Пользователь`) над
  каждой карточкой, не только в поиске.
  - **Супер-админ** (`User.isSuperAdmin`) — защищённый уровень поверх
    `role: 'admin'`, а не отдельное значение `role` (расширять сам enum не
    стали — пришлось бы находить и чинить каждую проверку `role === 'admin'`
    по всему проекту, вместо этого один явный флаг сверху). Инвариант:
    `isSuperAdmin: true` всегда подразумевает `role: 'admin'` — выдача
    (`AdminService.setSuperAdmin`) сама выставляет обе вещи разом, отдельно
    развести их через UI нельзя. Супер-админа не может забанить/удалить/
    понизить в роли НИКТО, включая другого супер-админа (только сам он —
    но и себе тоже нельзя, тот же принцип, что у обычного бана/удаления
    себя) — единственный способ перестать быть супер-админом отсюда — чтобы
    это сделал другой супер-админ. Выдавать/снимать супер-права может
    только уже существующий супер-админ (`SuperAdminGuard`, третий рубеж
    поверх `SessionAuthGuard`+`AdminGuard`, только на этом одном маршруте) —
    иначе любой обычный админ мог бы наделать себе неприкасаемых союзников.
    Кнопка «Сделать супер-админом»/«Снять супер-админа» в
    `AdminUsersPanel.tsx` видна только текущему супер-админу
    (`currentUser.isSuperAdmin`, тот же принцип UI-подсказки без реальной
    авторизации, что и у `role` в `MeProfile`); бан/удаление/снятие роли
    для супер-админа в UI не рендерятся вовсе (не просто задизейблены) — то
    же самое всё равно проверяет и backend, но так пользователь не видит
    кнопку, которая гарантированно ответит ошибкой. Первого супер-админа
    неоткуда взять через UI (курица-яйцо) — `npm run promote-super-admin --
email@example.com`, тот же bootstrap-приём, что и `promote-admin.ts`
    для самой первой роли `admin`.
- **Посты** (`AdminPostsPanel`) — тот же приём: поиск (текст записи, текст
  оригинала для репостов, или `id`) + фильтры тип/раздел (обычная/репост,
  стена/группа) + превью контента — бейджи «Фото ×N»/«Таблица»/«Ссылка» и
  сами миниатюры картинок (`extractImageUrls` на `Post.text`, тот же helper,
  что и `PostsService`), чтобы пустой `text` репоста фото не выглядел как
  «(без текста)». Удаление любого поста через `PostsService.removeAsAdmin`
  (без проверки авторства, но с той же бухгалтерией `repostsCount`/файлов,
  что и обычное удаление). Над карточкой — сразу два `IdBadge` рядом в
  `IdBadgeGroup` («Запись» + «Автор») — у поста два разных id одновременно
  важны для модерации (сама запись и кто её написал), раньше был виден
  только id записи.
- **Группы** (`AdminGroupsPanel`) и **Сообщества** (`AdminCommunitiesPanel`)
  — первая появившаяся в проекте возможность удалить группу/сообщество
  вообще (у `GroupsController`/`CommunitiesController` нет `remove` для
  обычных пользователей — группу не может удалить даже её владелец).
  Участники и заявки на вступление удаляются каскадом, а посты — нет:
  `Post.groupId`/`Post.communityId` в схеме `onDelete: SetNull` осознанно
  (см. комментарий в `schema.prisma`), чтобы удаление группы/сообщества не
  стирало молча чужой авторский контент — записи просто перестают быть
  привязаны. У группы дополнительно чистятся файлы `avatarUrl`/`coverUrl` на
  диске; у сообщества `cover` — не файл, а текстовая подпись (см.
  `prisma/seed.ts`), чистить нечего.

Общий для всех пяти вкладок markup-приём (`AdminTable.module.scss`,
переиспользуется `AdminUsersPanel`/`AdminPostsPanel`/`AdminGroupsPanel`/
`AdminCommunitiesPanel`) — каждая запись отдельной карточкой
(`.admin-table__record`: своя рамка/радиус/фон/hover, не строка плоского
списка с разделителями), с id записи **над** карточкой, а не в одной строке
с остальными метаданными — так он не теряется среди текста. Имя/название —
`.admin-table__name`, крупнее и в `--font-display` (тот же приём, что и
`FriendCard.module.scss`, `friend__name`), а не в общем `font-size`/
`font-family` строки — так самая важная часть записи считывается первой, до
бейджей роли/статуса рядом с ней.

**`IdBadge`/`IdBadgeGroup` (`shared/ui/IdBadge`)** — id сущности с подписью
(«Пользователь»/«Запись»/«Группа»/«Сообщество»/«Автор»), полным
(без обрезки — раньше был `max-width` с ellipsis) моноширинным значением и
кнопкой копирования (`navigator.clipboard.writeText`, иконка на секунду
меняется на галочку — состояние держит сам компонент, без стора: одноразовая
UI-обратная связь одного бейджа, а не персистентные данные). Подпись
обязательна в пропсах — без неё на экране, где одновременно видно два разных
id (например, `PostCard`/`AdminPostsPanel`: id записи и id её автора), не
понять, какой есть какой. `IdBadgeGroup` — тонкая обёртка `flex-wrap`, чтобы
несколько бейджей у одной записи держались друг рядом с другом одним
блоком, а не были раскиданы по карточке (раньше в `PostCard` id автора и id
записи стояли в разных местах разметки). Сам `IdBadge` тоже сам себе
`flex-wrap`: на широком экране — одна строка «подпись | id [copy]», на узкой
карточке (сетка друзей на планшете, `minmax(240px, 1fr)`) подпись и
значение переносятся на отдельные строки внутри той же рамки — полный id
всё равно виден целиком, просто в несколько строк, а не обрезается. Общий
компонент для мест основного сайта (`FriendCard`, `UserProfileView`,
`PostCard`, только для `currentUser.role === 'admin'`) и для самой админки
(`.admin-table__id` теперь — это только `align-self: flex-start`, сам вид
бейджа отдан общему компоненту, не дублируется своим CSS).

## Важные решения

- **Текущий пользователь — Context, не Zustand.** Zustand-store в этом
  проекте — модульный синглтон, общий для всех запросов на Node-сервере. Для
  данных, которые общие для всех пользователей (посты, диалоги — все видят
  один и тот же ответ backend), это не проблема. Но для _персональных_
  данных пользователя, приходящих из cookie конкретного запроса, синглтон
  рискует «перетечь» между параллельными запросами разных пользователей.
  Поэтому `entities/user` использует React Context, инициализированный
  пропом из Server Component (`page.tsx`) — так каждый рендер честно получает
  данные своего запроса. Если в будущем понадобится завести Zustand-store с
  персональными данными — сначала убедитесь, что он гидратируется так же
  (через проп из Server Component, не через чтение cookie/localStorage прямо
  в теле стора), иначе получите ту же уязвимость.
- **Один роут вместо множества страниц** (кроме `/auth`). Разделы
  переключаются в клиентском сторе, а не через `next/navigation` — так
  сохранено поведение исходного макета (мобильный UX «как в приложении»).
  Если понадобятся диплинки на разделы — повод завести настоящие маршруты.
- **Сессия — opaque-токен backend, а не локальный JSON.** Cookie
  `tavern_session` хранит только строку токена, выданную
  `POST /auth/login`/`/auth/register`; её смысл (какой userId, когда истекает)
  знает только backend (Redis, см. `AGENTS.md` backend). Frontend его не
  разбирает — только читает и подставляет как `Authorization: Bearer`.
- **`session.server.ts` не реэкспортируется из `features/auth/index.ts`** —
  server-only DAL импортируется по прямому пути только из Server Component,
  чтобы не сломать сборку клиентских бандлов. Единственное официальное
  исключение из правила «только через публичный API слайса».
- **Общие UI-примитивы вместо копирования стилей** — `shared/ui`:
  `MediaPlaceholder`, `PageHead`, `SectionContainer`, `Button`, а также
  `Loader`/`EmptyState`/`ErrorState` для унификации состояний загрузки данных.
  Прежде чем добавлять новый визуальный паттерн, проверьте, нет ли уже такого
  примитива.
- **Мок-данных в проекте нет.** Источники данных сущностей
  (`entities/*/api/get-*.ts`) вызывают реальный backend через `backendFetch` —
  честно пустой список означает, что backend ответил пустым списком, а не
  что данные придуманы на frontend.
- **Поиск/репост/комментарии показывают состояние inline, а не переходом на
  отдельную страницу сущности.** В приложении нет маршрутов вида
  «профиль пользователя X» или «страница группы Y» — один SPA-раздел на
  сущность (`profile` — только свой, `communities`/`groups` — списком).
  Результат поиска или репост поэтому раскрывают деталь на месте
  (`SearchDropdown`, «цитата» оригинала в `PostCard`), а не ведут на
  несуществующую страницу. Если такие страницы появятся — это архитектурное
  решение для отдельной задачи, не для точечного улучшения одной фичи.

## Известные пробелы

Ниже — то, что сознательно **не** реализовано, чтобы не придумывать
функциональность без запроса (см. `AGENTS.md`, раздел про поиск и репосты):

- **Сборы (фандрайзинг/события) как отдельная сущность не существуют** — ни в
  backend (нет модели/эндпоинтов), ни в frontend (нет `entities`/`api`).
  Вкладка «Сборы» в ленте — это просто фильтр существующих постов по
  `kind: 'events'`; сайдбар «Ближайшие сборы» на `widgets/feed` — честный
  `EmptyState` без источника данных. Поиск (см. выше) поэтому ищет только
  людей/сообщества/группы, не «сборы» — заявленных в задаче на поиск сборов
  возвращать нечего, пока эта сущность не появится.
- **Composer-чип «Опрос»** (`features/publish-post/ui/PostComposer.tsx`) —
  декоративный, без обработчика: назначение не подтверждено ни одной
  доменной моделью, реализовывать наугад не стали. Чип «Фото» и кнопка «···»
  (редактировать/удалить) на карточке поста — уже реальные, не заглушки (см.
  «Лента» выше).
- Входящие заявки дают бейдж (через общий колокольчик уведомлений, тип
  `friend_request`), но отдельного «только заявки» счётчика нет — не
  запрошено.
- **Стикеры — без отдельного набора картинок.** Реализованы как крупное
  эмодзи без пузыря (см. «Мессенджер: расширенные действия с сообщением»
  ниже) — осознанное решение, не заглушка: отдельного стикер-провайдера/
  своего набора изображений не заводили.
