# Правила проекта Tavern Frontend

Этот документ — основной источник правил для всех AI-агентов и разработчиков,
работающих с этим репозиторием. Правила выше (`nextjs-agent-rules`) генерируются
автоматически `next dev` и не редактируются вручную — всё, что ниже, поддерживается
людьми и агентами.

## Стек проекта

- **Next.js 16** (App Router, `src/app/**`)
- **React 19**, TypeScript 5 (`strict: true`)
- **Zustand** — клиентское состояние, общее для нескольких независимых виджетов/фич
- **Auth** — временный сессионный flow на Server Actions + httpOnly cookie,
  маршруты защищены `proxy.ts` (см. раздел 5)
- **Tailwind CSS 4** — для утилитарной/лейаутовой стилизации прямо в JSX
- **Sass (SCSS) + CSS Modules** — для компонентных блоков с собственной темой
- **ESLint 9** (flat config, `eslint.config.mjs`) на базе `eslint-config-next`
- **Prettier** — форматирование, **EditorConfig** — базовые настройки редактора

Актуальную карту фич/слайсов и принятые архитектурные решения см. в
[`PROJECT_CONTEXT.md`](./PROJECT_CONTEXT.md) — этот файл описывает _как устроен_
проект сейчас, тогда как `AGENTS.md` описывает _как с ним работать_.

## Папка `temp/`

`temp/` — это **не часть проекта**, а временное хранилище компонентов, которые
поочерёдно переносятся в `src/` и адаптируются под правила этого документа
(FSD-слои, BEM, Zustand, TypeScript-стиль). Она исключена из ESLint, Prettier,
TypeScript (`tsconfig.json` → `exclude`) и `.gitignore`. Не рефакторьте и не
проверяйте файлы внутри `temp/` — они здесь только как черновой источник для
копирования, и после переноса нужного кода в `src/` папка должна остаться пустой
или отсутствовать до следующей партии компонентов.

## 1. Общие принципы

- Пишите чистый, понятный и поддерживаемый код — код читают чаще, чем пишут.
- Избегайте преждевременной оптимизации: сначала корректность и ясность, потом
  профилирование и точечная оптимизация при реальной необходимости.
- Простое решение предпочтительнее сложного. Не создавайте абстракции, код,
  конфигурацию или сущности «про запас» — только под текущую задачу.
- Не дублируйте существующую бизнес-логику — сначала ищите переиспользуемый
  код в `shared/` и `entities/`, потом пишите новый.
- Перед изменением существующего кода изучите его контекст: кто его вызывает,
  какие у него побочные эффекты, какие тесты/сценарии на него завязаны.
- Не ломайте существующий функционал ради новой фичи. Если это неизбежно —
  явно предупредите об этом в описании изменений.

## 2. Принципы разработки

Применяются **не догматично**: если строгое следование принципу усложняет
простую задачу без реальной пользы — выбирайте более простое решение.

- **SOLID** — особенно принцип единственной ответственности (SRP) и явные
  зависимости (Dependency Inversion через пропсы/параметры, а не скрытые импорты
  синглтонов).
- **KISS** — самое простое решение, которое решает задачу, лучше «универсального».
- **DRY** — но только для реально повторяющейся логики; три похожие, но
  концептуально независимые строки — это не дублирование, а совпадение.
- **Композиция вместо наследования** — компонуйте компоненты/хуки/функции,
  наследование в React-коде практически не используется.
- **Явные зависимости** — параметры функций, пропсы компонентов, аргументы
  хуков вместо скрытых глобальных состояний и импортов с побочными эффектами.
- **Минимальная связанность** — модули не должны знать о внутренностях друг
  друга; общение только через публичные API (см. раздел «Архитектура»).

## 3. Архитектура — Feature-Sliced Design (FSD)

Файловая структура `src/` построена по FSD, адаптированной под Next.js App Router.

### Слои (сверху вниз — от конкретного к переиспользуемому)

| Слой       | Путь                   | Назначение                                                                                                                                                                 |
| ---------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `app`      | `src/app/**`           | Роутинг Next.js (page/layout/route-файлы), глобальные провайдеры, `globals.css`. Максимально тонкий: только композиция `widgets`/`features`/`entities`, без бизнес-логики. |
| `widgets`  | `src/widgets/{name}/`  | Самодостаточные композитные блоки интерфейса для страниц (шапка, сайдбар, «лента», целый экран вроде `TavernSocial`), собранные из `features`/`entities`.                  |
| `features` | `src/features/{name}/` | Пользовательские сценарии, приносящие бизнес-ценность (лайкнуть пост, отправить сообщение, вступить в сообщество). Названия — глаголом/действием.                          |
| `entities` | `src/entities/{name}/` | Бизнес-сущности домена (Post, Thread, Friend, Community, Group, User) — их UI-представление, модель и API-запросы.                                                         |
| `shared`   | `src/shared/`          | Код без бизнес-логики: UI-кит (Button, Avatar, Badge, Card, Tag…), общие хуки, утилиты (`lib`), стилевые токены/миксины, конфиг шрифтов, типы общего назначения.           |

Классический FSD-слой `pages` не используется — его роль выполняет App Router
(`src/app/**`). Слой `processes` не используется (устарел в FSD 2.0 и обычно
не нужен) — межстраничные сценарии решаются на уровне `app` или `widgets`.

### Переиспользуемые примитивы `shared/ui`

Перед тем как писать разметку и стили нового блока, **проверьте `src/shared/ui`** —
там уже есть переиспользуемые примитивы: `Button` (варианты `primary/outline/soft/
ghost/chip`), `Avatar` (размеры + индикатор «в зале»), `Badge`, `Card`, `Tag`,
`DateBadge`, `MediaPlaceholder` (заглушка изображения/обложки), `PageHead`
(заголовок раздела + подпись), `SectionContainer` (базовый `<main>` раздела),
`Loader`/`EmptyState`/`ErrorState` (см. раздел 4 про статусы загрузки).
Если визуальный паттерн повторяется в 2+ местах — это кандидат на новый примитив
в `shared/ui`, а не на копирование стилей.

### Правила зависимостей

- Слой может импортировать **только нижестоящие** слои:
  `app → widgets → features → entities → shared`.
- Никаких импортов «вбок» между слайсами одного слоя и никаких импортов «вверх».
- Это частично **проверяется автоматически** правилом `no-restricted-imports`
  в `eslint.config.mjs` (блоки `fsdBoundaryConfigs`) — нарушение направления
  зависимостей или обход публичного API даёт ошибку ESLint.

### Публичное API слайса

- У каждого слайса (`entities/post`, `features/like-post`, `widgets/feed`…)
  есть один файл `index.ts`, реэкспортирующий то, что нужно снаружи.
- Импортируйте слайс только по алиасу верхнего уровня: `@/entities/post`,
  никогда `@/entities/post/ui/PostCard` — глубокие импорты запрещены ESLint-правилом.
- Внутри своего слайса используйте относительные импорты (`./ui/PostCard`),
  а не алиас `@/...` — так внутренние файлы не попадают под правило
  «только публичный API».

### Сегменты слайса

Создавайте только те сегменты, которые реально нужны — не создавайте пустые
папки «на будущее»:

- `ui/` — компоненты
- `model/` — состояние, типы домена, бизнес-логика без UI
- `api/` — запросы к серверу/эндпоинтам, относящимся к этому слайсу
- `lib/` — вспомогательные утилиты, специфичные для слайса
- `config/` — константы/конфигурация слайса

### Создание новых слайсов/сегментов

- Новый слайс создаётся, когда появляется новая самостоятельная сущность или
  фича — не дробите произвольно и не создавайте слайс на 5 строк кода, если
  это можно оставить в существующем `shared`/`entities`.
- Прежде чем добавлять слайс, проверьте, не покрывает ли задачу существующий.
- Общие для нескольких слайсов вещи поднимаются в `shared`, а не копируются.

## 4. Zustand — управление состоянием

### Когда заводить store, а когда — `useState`

Store — только для состояния, которое реально общее для **нескольких независимых
widgets/features** (не связанных отношением родитель-потомок) или должно жить
независимо от того, смонтирован ли конкретный компонент. Примеры из проекта:
`section-navigation` (шапка, док, мобильная панель и лист «Ещё» — четыре разных
виджета читают/меняют текущий раздел), `entities/post` (лента и стена профиля
показывают одни и те же посты), `entities/thread` (шапка считает непрочитанные,
мессенджер их показывает), `entities/user` (текущий пользователь нужен шапке,
композеру, профилю и настройкам одновременно).

Если состояние нужно только одному компоненту/виджету (черновик текста, открыта
ли форма, какой таб выбран) — это `useState` внутри этого компонента, а не store.
**Не создавайте store для локального состояния** — так на проекте уже вводили в
заблуждение store в других местах, не делайте так же здесь.

### Где размещать store

- Store живёт в `model/<name>-store.ts` **того слайса, которому принадлежат
  данные** — `entities/post/model/post-store.ts`, `features/section-navigation/
model/navigation-store.ts`. Никакого общего `src/store.ts` или `src/stores/*` —
  состояние группируется по домену/фиче, а не собирается в одну свалку.
- Store сущности (`entities/*`) — для данных домена, которые могут понадобиться
  нескольким фичам/виджетам (посты, диалоги, текущий пользователь).
- Store фичи (`features/*`) — для состояния конкретного пользовательского сценария,
  которое тем не менее должно быть общим для нескольких виджетов (например,
  текущий раздел приложения в `section-navigation`).
- Виджеты (`widgets/*`) **не должны заводить свои Zustand-store**, которые читают
  другие виджеты — это создаёт запрещённую связь «виджет → виджет». Если состояние
  нужно двум виджетам, ему место в `entities` или `features`, ниже по иерархии.

### Структура store

- Разделяйте форму состояния (`interface XState`) и действия (`interface
XActions`), итоговый тип — `XState & XActions`, экспортируйте его.
- Хук называйте `use<Domain>Store` (`usePostStore`, `useUserStore`).
- Действия (`set`) описывайте инлайн внутри `create<Store>((set) => ({ ... }))` —
  без промежуточных классов/менеджеров.
- Для производных значений, которые нужны нескольким компонентам (например,
  «сколько всего непрочитанных сообщений»), заводите отдельную экспортируемую
  функцию-селектор (`selectUnreadThreadCount`) вместо повторения вычисления в
  каждом месте использования.
- В компонентах подписывайтесь на **конкретное поле/действие** через селектор
  (`usePostStore((state) => state.posts)`), а не деструктурируйте весь store —
  так компонент не перерендеривается на изменения полей, которые не использует.
- Полная типизация обязательна: без `any`, `unknown` без сужения, самодельных
  `Record<string, any>` для состояния.

### Загрузка данных: без mock-данных, с явным статусом

Backend пока не подключён, но это не повод хранить вымышленные списки —
**данные, которые в перспективе приходят с сервера, никогда не подставляются
захардкоженными массивами** («мок посты», «мок пользователь» и т. п.). Вместо
этого:

- Каждый источник данных сущности — функция `api/get-<entity>.ts`
  (`entities/post/api/get-posts.ts`, `entities/friend/api/get-friends.ts`),
  возвращающая `Promise<T[]>`. Пока нет backend, она честно резолвится в
  `[]` — не в придуманные записи. При подключении API меняется только тело
  этой функции; сигнатура и все вызовы остаются прежними.
- Статус запроса — всегда `'idle' | 'loading' | 'success' | 'error'`
  (`shared/lib/async-status.ts`, тип `AsyncStatus`). Не сокращайте до
  boolean-флагов (`isLoading`) — так легко перепутать «ещё грузится» с
  «загружено и пусто».
- Если данные общие для нескольких widgets/features — статус живёт в
  Zustand-сторе рядом с самими данными (`entities/post/model/post-store.ts`:
  поля `status`/`error`, экшен `loadPosts`), вызывается один раз при старте
  приложения (`src/app/home-app.tsx`).
- Если данные нужны только одному виджету — используйте хук
  `useAsyncData(fetcher)` (`shared/lib/use-async-data.ts`): сам управляет
  `status`/`data`/`error`/`refetch`, ничего вручную заводить не нужно.
- В UI обязательно разделяйте четыре состояния и не путайте их (пустой список
  — это не ошибка и не «ещё грузится»):
  - `loading` → `<Loader />` (`shared/ui/Loader`);
  - `error` → `<ErrorState message={error} onRetry={...} />`
    (`shared/ui/ErrorState`) — никогда не показывайте пустое состояние при
    ошибке запроса;
  - `success` и данных нет → `<EmptyState title=... description=... action=...
/>` (`shared/ui/EmptyState`) — только когда запрос точно завершился успехом;
  - `success` и данные есть → обычный рендер списка.
- Различайте **причину** пустоты в тексте `EmptyState`: «пользователь ещё
  ничего не создал» (`widgets/feed` — пустая лента), «ничего не найдено по
  фильтру» (`widgets/feed` — таб без совпадений, с кнопкой сброса фильтра),
  «раздела пока нет вообще» (`widgets/friends`/`communities`/`groups`) — не
  используйте один и тот же текст для разных причин.

## 5. Auth и защита маршрутов

Backend-аутентификация реальная (opaque-токены в Redis на стороне backend,
без JWT — см. `AGENTS.md` backend).

- **Где живёт auth-логика.** Вся механика — в `features/auth`:
  `api/session.server.ts` (DAL, `server-only`, читает cookie сессии,
  функция `getSessionUser()`), `api/actions.ts` (Server Actions:
  `loginToAccount`, `registerAccount`, `updateProfile`, `endSession`,
  `getSocketTicket`), `ui/AuthForm.tsx`. Профиль пользователя как данные (не
  механика входа) — в `entities/user`.
- **Хранение сессии.** Cookie `tavern_session` (имя — константа
  `shared/config/session.ts`, `SESSION_COOKIE_NAME`) хранит только opaque-
  токен, выданный backend'ом при `POST /auth/login`/`/auth/register` — не
  JSON с данными пользователя и не JWT. Смысл токена знает только backend;
  frontend его не разбирает, только подставляет как `Authorization: Bearer`
  в `backendFetch` (`shared/lib/backend-client.ts`).
- **Текущий пользователь — React Context, не Zustand.** `entities/user`
  хранит `currentUser` через `CurrentUserProvider`
  (`model/current-user-context.tsx`), а не через модульный Zustand-store.
  Причина: Zustand-store — синглтон на уровне модуля, общий для всех
  запросов на сервере; если положить туда персональные данные пользователя
  и заполнить их при рендере, в продакшене с несколькими одновременными
  запросами это может **утечь данные одного пользователя другому**. Context
  же создаётся заново на каждый рендер дерева, а начальное значение
  (`initialUser`) приходит пропом из Server Component — так каждый запрос
  честно получает только свои данные. Если когда-нибудь понадобится второй
  кусок персональных данных пользователя — добавляйте его в тот же Context,
  не заводите для этого Zustand-store.
- **`session.server.ts` не реэкспортируется из `features/auth/index.ts`.**
  Это единственное осознанное исключение из правила «только через
  публичный API»: барель может быть импортирован из клиентских
  компонентов, а `server-only`-код в его графе импортов сломает сборку.
  `getSessionUser` импортируется по прямому пути и только из Server
  Component (сейчас — `src/app/page.tsx`), с комментарием у
  `eslint-disable-next-line no-restricted-imports`, объясняющим причину.
- **Защита маршрутов — два рубежа, не один.** Визуальная проверка внутри
  компонента (`if (!user) return <Login />`) недостаточна, потому что не
  останавливает рендер самого защищённого сегмента маршрута. Вместо этого:
  1. `src/proxy.ts` — быстрая edge-проверка: есть ли cookie сессии.
     Разруливает оба направления редиректа (нет сессии + защищённый роут →
     `/auth`; есть сессия + `/auth` → `/`) — оба условия взаимоисключающие,
     поэтому redirect loop невозможен структурно.
  2. Серверная проверка в самом page-компоненте (`src/app/page.tsx`):
     `await getSessionUser()` + `redirect('/auth')`, если сессии нет — это
     авторитетный рубеж (proxy — только оптимистичная предпроверка).
     Если появится больше защищённых маршрутов, поднимите этот паттерн в
     `(protected)/layout.tsx` (route group), чтобы не дублировать проверку в
     каждой странице — сейчас защищённый маршрут один, поэтому проверка прямо
     в `page.tsx`.
- **Публичные маршруты** перечислены в `src/proxy.ts` (`PUBLIC_PATHS`) —
  сейчас только `/auth`. Всё остальное по умолчанию защищено.
- Не оставляйте захардкоженного `currentUser`/`mockUser` ни в сторах, ни в
  Context, ни в дефолтных значениях — до входа пользователя приложение
  обязано быть в честном неавторизованном состоянии.
- **Socket.IO не получает основной session-токен.** Отдельный одноразовый
  билет — `getSocketTicket()` (`features/auth`), backend меняет его на
  userId и сразу удаляет (см. `AGENTS.md` backend). При подключении `io(...)`
  передавайте `auth` **функцией**, а не статическим объектом — билет
  одноразовый, и Socket.IO переиспользует объект `auth` на каждой
  автоматической попытке reconnect; со статическим объектом первый же
  разрыв соединения ломает real-time навсегда (уже использованный билет
  отклоняется). Функция вызывается заново перед каждой попыткой подключения
  и должна каждый раз запрашивать новый билет — см. `app/home-app.tsx`.

## 5.1. Real-time — Socket.IO

Единственное соединение на всё приложение создаётся один раз в
`app/home-app.tsx` (`useEffect`, singleton) — не заводите второй `io(...)`
где-либо ещё. Добавляя новый real-time сценарий:

- **Нужен ли вообще Socket.IO?** Только если событие должно мгновенно
  появиться у _другого_ пользователя без перезагрузки страницы (новое
  сообщение, заявка в друзья). Обычные CRUD-действия, видимые только
  самому вызвавшему (лайк, вступление в сообщество, поиск, настройки) —
  просто REST, без событий.
- **Backend: Gateway — транспорт, не бизнес-логика.** Единственный шлюз —
  `RealtimeGateway` (`src/infrastructure/websocket/realtime.gateway.ts`,
  глобальный модуль `RealtimeModule`) — не создавайте новый gateway на
  фичу, он и так не привязан к домену: инжектируйте `RealtimeGateway` и
  зовите `emitToUser(s)`. Кто получит событие и когда — решает `Controller`
  **после** вызова `Service` (тот же порядок, что и в REST-хендлерах;
  `Service` не должен знать о сокетах вообще).
- **Именование событий** — `domain:verb`, нижний регистр
  (`message:new`, `friend-request:accepted`).
- **Payload — минимальный сигнал**, не слепок сущности (`{ senderId }`, не
  весь профиль). Frontend перечитывает актуальные данные через REST-экшены
  того же слайса, а не патчит state из payload'а — на этой частоте событий
  простота и согласованность с backend важнее оптимистичности.
  - **Исключение — одноразовые toast-попапы** (`entities/notification/model/toast-store.ts`).
    Toast должен появиться мгновенно с готовым текстом/аватаром, а не ждать
    ещё один REST-запрос — поэтому событиям, которые ведут к toast'у
    (`friend-request:new/accepted`, `notification:new`), можно положить в
    payload снэпшот нужных полей (`actor: PublicProfile`). Это осознанное
    исключение из правила выше: снэпшот допустим только для одноразового UI
    (`ToastItem` живёт секунды и не является источником истины), а любое
    **персистентное** состояние (`useFriendStore`, `useNotificationStore.items`)
    по-прежнему обязано перечитываться через REST, а не патчиться из payload'а.
- **Frontend: обработчик события живёт в `app/home-app.tsx`**, одна строка,
  диспатчащая в экшен domain-store'а (`entities/*`) — никогда не трогает UI
  напрямую и не живёт внутри компонента.
- **Нужен ли store для этих данных?** Если событие должно обновлять
  состояние, даже когда виджет, которому оно принадлежит, не смонтирован —
  да (см. `useFriendStore`, заведён именно по этой причине, раздел 4). Если
  данные нужны только пока конкретный виджет открыт — не заводите store
  ради одного real-time события, это тот же принцип, что и для обычного
  состояния.

## 6. CSS / стили — BEM + CSS Modules (SCSS) + Tailwind

В проекте используются оба инструмента с разной зоной ответственности:

- **Tailwind CSS 4** — быстрая утилитарная стилизация лейаутов и одноразовых
  элементов прямо в JSX (как сейчас в `src/app/page.tsx`, `layout.tsx`).
- **SCSS Modules + BEM** — для компонентов с собственной, содержательной темой
  и переиспользуемыми элементами (пример — `entities/post/ui/PostCard.module.scss`,
  `widgets/messenger/ui/MessengerWidget.module.scss`).

Не смешивайте зоны ответственности в одном узле: не переопределяйте Tailwind-утилиты
из SCSS и наоборот.

- **Скроллбар — два уровня, не переопределяйте ни один точечно.**
  1. Для настоящих прокручиваемых списков/областей контента (там, где
     пользователь реально скроллит — список сообщений, дропдаун, список
     диалогов и т. п.) используйте `shared/ui/ScrollArea` вместо голого
     `overflow: auto`. Это не CSS-стилизация нативного скролла (он по-
     разному выглядит в разных браузерах — `scrollbar-color` не поддержан в
     Safari, `::-webkit-scrollbar` не поддержан в Firefox), а свой JS-
     ползунок поверх спрятанного нативного скролла: сама прокрутка (колесо/
     тачпад/тач) остаётся штатной, но выглядит и ведёт себя одинаково во
     всех браузерах. Пример использования — `widgets/messenger/ui/MessengerWidget.tsx`.
  2. Для всего остального (текстовые области, случайные переполнения,
     что угодно, что не завели через `ScrollArea`) — CSS-фолбэк в
     `src/app/globals.css` (тонкий `scrollbar-color`/`::-webkit-scrollbar` в
     цветах Таверны, прозрачный в покое). Он работает автоматически на
     любом `overflow: auto/scroll` без дополнительной настройки, но выглядит
     чуть по-разному в Chrome/Safari и Firefox — поэтому для реально важных
     мест используйте `ScrollArea`, а не полагайтесь только на фолбэк.
     Не пишите свои `::-webkit-scrollbar`/`scrollbar-color` в `*.module.scss` —
     ни для замены `ScrollArea`, ни поверх глобального фолбэка.

### BEM-именование в `*.module.scss`

- **Блок** — независимая по смыслу UI-единица, называется по-английски в
  kebab-case существительным: `.card`, `.header`, `.dock`. Один файл модуля
  может содержать несколько блоков, если компонент рендерит несколько логически
  независимых групп (как в `MobileNavigation.module.scss`: `tab-bar` и `sheet` —
  разные блоки в одном файле, потому что лист «Ещё» существует только в контексте
  мобильной навигации).
- **Элемент** — часть блока, не имеющая смысла вне его:
  `block__element`, например `.header__inner`, `.dock__item`. Только один
  уровень вложенности элемента — `block__element__sub` запрещено; если у
  элемента появляются свои части, выносите его в отдельный блок.
- **Модификатор** — вариация блока/элемента: `block--modifier` или
  `block__element--modifier` (`.dock__item--active`). Модификатор всегда
  применяется вместе с базовым классом, никогда не используется отдельно:
  `className={[styles.dockItem, isActive && styles['dockItem--active']].filter(Boolean).join(' ')}`.
- Поскольку `__` и `--` — не валидные идентификаторы JS, обращайтесь к таким
  классам через `styles['block__element--modifier']`, а не через точечный доступ.
- Не пишите вложенные селекторы-потомки (`.block .element {}`) — у каждого
  значимого узла свой явный класс. Вложенность через `&` в SCSS допустима
  только для состояний (`&:hover`, `&.block--modifier`) и медиа-миксинов.
- Дизайн-токены (цвета, радиусы, шрифты, брейкпоинты) и миксины — переменными
  SCSS в начале файла, без «магических чисел» по всему файлу.
- Глобальные стили — только в `src/app/globals.css` (базовые токены Tailwind,
  сброс, шрифты). Стили конкретного компонента не должны просачиваться глобально.

## 7. TypeScript / JavaScript

- Строгая типизация (`tsconfig.json` уже в режиме `strict`) — не отключайте
  `strict`, `noImplicitAny` и другие флаги ради удобства.
- `any` — только с явным обоснованием в комментарии рядом с
  `eslint-disable-next-line @typescript-eslint/no-explicit-any -- почему`.
  Правило понижено до `error`, поэтому обход без причины будет падать в CI/линте.
- Предпочитайте точные типы: union-типы вместо `string`, `interface`/`type` с
  конкретными полями вместо `Record<string, unknown>` там, где форма известна.
- Не дублируйте типы — общие типы домена живут в `model/` соответствующего
  `entities`-слайса, общие технические типы — в `src/shared`.
- Разделяйте domain-типы (что такое `Post`, `Thread` — `entities/*/model`),
  application-типы (состояние фичи — `features/*/model`) и UI-типы (пропсы
  компонентов — рядом с компонентом в `ui/`).
- Не скрывайте ошибки типов через `as` без необходимости — сначала попробуйте
  сузить тип нормально (type guard, дискриминирующее объединение).
- Импортируйте типы через `import type` (правило `consistent-type-imports`).

## 8. React / UI

- Компонент делает одну вещь — если файл разрастается и смешивает несколько
  несвязанных сценариев, дробите его по `widgets` на отдельные секции (пример —
  `FeedWidget`, `MessengerWidget`, `ProfileWidget` — каждая страница-раздел
  приложения это отдельный widget, а не одна общая простыня).
- Разделяйте UI, состояние и бизнес-логику: тяжёлая логика — в `model/`
  (хуки, функции), компонент — только про рендер и обработчики UI-событий.
- Избегайте prop drilling там, где он действительно создаёт проблему (3+
  промежуточных компонента без собственного использования пропа) — тогда
  контекст или композиция через `children`.
- Соблюдайте Rules of Hooks: хуки только на верхнем уровне компонента/другого
  хука, без условий и циклов.
- Не добавляйте `useMemo`/`useCallback`/`memo` «на всякий случай» — только
  когда есть измеримая проблема с перерендером или зависимость требует
  стабильной ссылки (например, входит в массив зависимостей другого хука).
- Учитывайте accessibility: семантические теги, `aria-*`, `alt` для
  изображений, доступные имена для интерактивных элементов (частично уже
  проверяется `jsx-a11y` из `eslint-config-next`).
- Явно обрабатывайте состояния `loading` / `error` / `empty` для любых данных
  из API — не оставляйте «голый» happy path. Правила и готовые компоненты —
  раздел 4 («Загрузка данных: без mock-данных, с явным статусом»).

## 9. Обязательная проверка UX/UI после каждой фичи

Фича не считается завершённой только потому, что код компилируется и линтер
не ругается. После реализации проведите отдельный QA-проход.

### Functional QA

- [ ] Основной happy path
- [ ] Edge cases и граничные значения (пустые/очень длинные строки, 0, отрицательные числа)
- [ ] Loading state
- [ ] Error state
- [ ] Empty state
- [ ] Некорректные пользовательские действия (двойной клик, отправка пустой формы)
- [ ] Повторные действия пользователя (повторный сабмит, повторный лайк)
- [ ] Состояние после перезагрузки страницы
- [ ] Отсутствие регрессий в существующем функционале рядом

### UI/UX QA

- [ ] Визуальная консистентность с остальным интерфейсом
- [ ] Spacing и typography по токенам, без «на глаз» значений
- [ ] Responsive-поведение: mobile / tablet / desktop
- [ ] Состояния hover / focus / active / disabled
- [ ] Accessibility (клавиатурная навигация, видимый focus, контраст)
- [ ] Читаемость и переполнение текста при длинных значениях
- [ ] Ошибки валидации форм показаны понятно
- [ ] Нет layout shift при загрузке контента

## 11. Команды проекта

| Команда                | Назначение                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| `npm run dev`          | Запуск дев-сервера Next.js                                                                   |
| `npm run build`        | Продакшн-сборка                                                                              |
