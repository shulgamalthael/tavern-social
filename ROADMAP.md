## 0. Audit — what actually exists today

### 0.1 The one fact that reframes everything else

**Tavern is a social network, not a dedicated website-builder SaaS.** `Business` is one entity type among `Post`, `Community`, `Group`, `Thread`, owned by a `User`, with a 1:1 `Website`. There is no multi-tenant account system, no billing, no team/collaborator model, no per-business staff accounts — a Business belongs to exactly one `User.ownerId`, full stop.

This matters for every decision below. The mission (`AGENTS.md`) explicitly asks to turn this into "a full business platform," and I'm taking that at face value — but *how* it gets built has to respect that this lives inside a social app, not replace it. Concretely: a `Business` dashboard is a new surface *within* Tavern, not a separate product; a published business site is a small application of its own (§3.1), but the *owner's* experience of managing it stays inside Tavern's existing shell (header, session, nav).

I confirmed this isn't a hypothetical concern — `BusinessCategory` (the enum: `restaurant | retail | services | health | beauty | fitness | education | technology | creative | real_estate | hospitality | nonprofit | other`) already exists in the schema, but its own doc-comment says it plainly: *"влияет только на отображение... никакой другой бизнес-логики на ней не завязано"* — it's a filter icon, nothing more. That is the single highest-leverage gap: the taxonomy exists, the capability system that should hang off it does not.

### 0.2 What's good — keep it

- **The block-tree model** (`WebsiteBlock { id, type, props, style?, hidden?, children? }`) is exactly the "flat, declarative, AI-generatable" shape the mission asks for in §45/§49. It doesn't need a rewrite — it needs *more block types and a data-binding field*, not a new tree format.
- **One renderer, three consumers.** `BlockRenderer`/`WebsiteRenderer` are used identically by the public site, Preview, and (with editor chrome layered on top via `CanvasBlock`) the Builder canvas. This is precisely the "Builder preview → same renderer → different data/state" principle from §55. Don't touch this seam.
- **Registry pattern for block types** (`registerBlock<P>()`, `BlockDefinition<P>` with `fields: FieldSchema[]`) is a real metadata-driven schema, matching §49's `ComponentDefinition` almost field-for-field (`type, label, category, icon, isContainer, fields`). It's missing `allowedChildren`, `dataSchema`, `actionsSchema` — additive, not a rewrite.
- **Undo/redo, autosave, publish/draft split** are all real and — as of this session's stabilization pass — verified correct under stress (rapid undo/redo, autosave race conditions, refresh persistence, nested-delete edge cases). This is a solid foundation, not debt.
- **Multi-tenant domains** (`Domain` model, `DomainResolverService`, `proxy.ts` host rewriting) already exist and work. This is real infrastructure most MVP builders don't have yet.
- **FSD layering + Zustand conventions** (documented in `AGENTS.md`) are consistently followed and give a clean place to hang new entities (`entities/product`, `entities/booking`, etc.) without inventing new patterns.
- **`sanitize-html` is already a backend dependency** (used for `Post.text`) — the XSS-safety primitive the mission worries about in §58 already exists in the stack; it just needs to be applied to any new user-authored rich-text surface (block `richtext` fields, form descriptions, etc.).

### 0.3 What's broken or missing (confirmed, not assumed)

1. **There is no multi-page routing at all**, despite the data model half-supporting it. `WebsitePage.slug` exists in the type. `WebsiteDocument.pages` is an array. `activePageId` exists in the builder store. But: `/site/[businessId]/page.tsx` takes **no path segment beyond the business id** — it always renders `document.pages[0]`, and there is no UI anywhere to create a second page. This is §17/§18's "critically important" routing requirement, currently at 0%. It is also the single biggest blocker for Commerce/Content/Booking, since `/products/[slug]`, `/blog/[slug]`, `/services/[slug]` all need real per-entity routes.
2. **No relational tables for any business-domain entity.** There is no `Product`, `Order`, `Booking`, `Service`, `Post` (blog, distinct from the social `Post`), `Menu`, `Room`, `Property`, etc. Everything a future Commerce/Booking/Content capability needs would currently have nowhere to live except inside `Website.draft` JSON — which is exactly the anti-pattern §59/§60 warns against ("не складывай абсолютно всё в один огромный `Website.data` JSON"). This is the second-biggest blocker.
3. **Category is cosmetic** (§0.1). No capability gating exists — every business, regardless of category, sees the exact same Builder and the exact same (currently nonexistent) dashboard.
4. **No payments, no scheduling, no maps, no charts library** anywhere in `package.json` (checked both `frontend` and `backend`). Nothing to migrate away from — a clean slate, but also confirms zero infra for §6 (Marketplace), §7 (Services/Booking), §37 (Stripe) exists yet.
5. **No Business Dashboard.** `/business/[id]` is the social-network-facing profile (wall/about), `/business/[id]/edit` is the Builder, `/business/[id]/settings` is domain + metadata settings. There's no category-aware control center (§32) tying these together with future Products/Orders/Bookings.
6. **`updateWebsiteDocumentDto` validates only the top-level shape** (`pages: unknown[]`, `theme: object`, `settings: object`) — deliberately shallow so new block types never require a backend deploy. This is a *reasonable* MVP tradeoff today (few block types, single owner, low stakes), but it will need a second validation layer once dynamic-entity references start appearing inside block `props` (e.g., "this ProductGrid references category X" — that reference needs server-side existence/ownership checks somewhere, just not inside this generic DTO).
7. **No event/analytics plumbing whatsoever** — no `page_view`, no `product_viewed`, nothing. §34/§42 asks for this as a *foundation*, not a full analytics platform — currently there isn't even the foundation.
8. **No Media Library.** Image uploads (`ImageField.tsx`, `upload-website-asset.ts`) go straight to a block's `props` with no reuse, browsing, or dedup — every upload is a one-off file with no registry (§40 gap, mirrors the `GalleryImage` pattern already used for user photos, so precedent exists to copy).

### 0.4 Temporary/MVP decisions worth naming explicitly (not bugs — deliberate tradeoffs, revisit later)

- Whole-document PATCH for website drafts (no partial diffing) — fine at current JSON size, would need reconsideration if `draft` grows to include large embedded collections (it shouldn't, once Commerce/Content move to relational tables — see §3.1).
- `Website` is 1:1 with `Business` — correct for now (no multi-site-per-business need has appeared), keep.
- No collaborator/staff roles on a `Business` — out of scope for this roadmap; noted so nobody accidentally builds Dashboard permissions logic assuming multi-user businesses exist.

### 0.5 What to rewrite vs. what to keep

**Keep as-is:** block-tree shape, registry pattern, renderer, undo/redo, autosave, publish/draft, domains, FSD conventions, Zustand usage patterns.

**Extend (additive, no rewrite):** `BlockDefinition` schema (add `allowedChildren`, `dataSchema`, `actionsSchema`), `FieldSchema` (already has `responsive`; needs a `binding`/data-source variant), `BusinessCategory` (needs to drive a `capabilities` set instead of just an icon).

**Build new (currently doesn't exist in any form):** page routing, relational domain models per capability, capability registry, Business Dashboard, event/analytics table, Media Library, payments abstraction, forms-submission storage.

**Nothing needs to be deleted.** There is no legacy code fighting the new direction — this is a genuinely clean MVP to build on top of, which is the best possible starting position for this mission.

## 1. Product discovery — what a real Website Builder must do

Reframing the mission's own question for Tavern's actual users: a local restaurant owner, a freelance designer, a small clinic, a boutique shop owner — someone who currently has *no* other website — opens Tavern, creates a `Business`, and expects to walk away with something they can hand to a customer as "my website," not "my landing page." Concretely, that means, beyond blocks-on-a-page:

- **Pages that are real URLs**, not one long scroll (About, Contact, Services/Products/Menu, individual product/service/post pages).
- **A way to show a catalog of things** (products, services, menu items, posts, rooms, properties — whatever the business sells) that isn't hand-built block-by-block.
- **A way for a visitor to *do* something**: buy, book, submit an inquiry, subscribe, message the business — and the owner needs to see that happened somewhere.
- **A way to manage the *data* behind the site** (this week's menu, this month's promotion, new product) without re-entering the Builder and dragging blocks.
- **The site to look credible** — consistent theme, real SEO tags, a domain, not "obviously a builder demo."

None of that requires *every* vertical from the mission's list on day one. It requires the right *shape* of system so that adding "Restaurant" after "Commerce" is a capability module, not a rewrite.

The mission's category list is real and worth keeping as the long-term menu, but the **right unit of architecture is the capability, not the category** — this is §15/§33's point, and it's correct. A category is just a *default bundle of capabilities* plus a starter template. Below: the full taxonomy, mapped to the capabilities each one actually needs (not a full CRUD/page/widget matrix for all 20 — see §2.2 for why only four get that treatment now).

### 2.2 Full matrix for the four capabilities being built first

These are the ones explicitly worked out in the mission (§5–§8) and the ones that cover the overwhelming majority of Tavern's realistic business categories (retail, restaurants, services, creative/agency, health, beauty, fitness all reduce to Commerce and/or Booking and/or Content).

**Commerce**
- *Entities:* Product, ProductVariant (SKU, price, stock), Category, Collection, Brand, Order, OrderItem, Customer, Address, Discount, Review
- *Pages:* Catalog (`/products`), Category (`/products/category/[slug]`), Product (`/products/[slug]`), Cart, Checkout, Order success, Order tracking, Account/Orders, Wishlist
- *Widgets:* ProductGrid, ProductCard, ProductGallery, ProductFilters, PriceDisplay, AddToCartButton, CartDrawer, CheckoutForm, ReviewList
- *Actions:* `add_to_cart`, `remove_from_cart`, `checkout`, `apply_coupon`
- *Workflow:* browse → filter/sort → product detail → add to cart → checkout (guest or account) → payment → confirmation → order tracking
- *Data needs:* pagination (cursor, for large catalogs), search, inventory decrement on order, tax calc (flat rate to start — real tax engines are out of scope), shipping (flat/free to start)

**Booking**
- *Entities:* Service, ServiceCategory, Employee, Location, Availability, Appointment, Customer
- *Pages:* Services list, Service detail, Booking flow, Account/Appointments
- *Widgets:* ServiceGrid, ServiceCard, EmployeePicker, AvailabilityCalendar, BookingForm
- *Actions:* `book_appointment`, `cancel_appointment`, `reschedule`
- *Workflow:* `Service → Employee (optional) → Date → Time → Customer info → Confirm → Confirmation` (matches the mission's §7 flow exactly)
- *Data needs:* availability computed from Employee working hours minus existing Appointments — no external calendar sync in v1 (candidate integration later, not now)

**Content (Blog)**
- *Entities:* Post, Author, Category, Tag, Comment
- *Pages:* Blog list, Post detail, Category/Tag archive
- *Widgets:* BlogGrid, PostCard, AuthorBio, TagCloud, RelatedPosts
- *Actions:* none beyond navigation (comments optional, phase 2)
- *Data needs:* uses the *same* `richtext` field type the Builder already has via TipTap — no new editor needed

**Restaurant (Menu, built on Commerce + Booking primitives — not a new capability from scratch)**
- *Entities:* Menu, MenuCategory, Dish (reuses Product's price/image shape), Modifier, Allergen; Reservation reuses Booking's Appointment shape
- *Pages:* Menu, Dish detail (optional), Reservation
- *Widgets:* MenuList, DishCard, ModifierPicker, ReservationForm
- This is the concrete proof of §15: Restaurant isn't a fifth capability, it's Commerce + Booking with restaurant-flavored entities and templates on top.

### 2.3 Everything else — capability sketch, deliberately not fully designed yet

Marketplace, Hotel/Hospitality (Stay), Healthcare, Education, Real Estate, Events, Membership, Non-profit, SaaS/Technology, Personal — all get an entity list in §2.1, all fit the same Capability interface (§3.3), **none get full page/widget/workflow specs in this document.** Designing all fifteen matrices in full today, before a single real business in any of them exists on the platform, would be speculative work with no one to validate it against — exactly the over-engineering the mission itself warns against in §1 ("не делай рефакторинг только ради рефакторинга") and §56/§65's progressive-complexity principle. The architecture (§3.3) is built so adding one is additive, not a rewrite — that's the actual commitment being made now, not a pre-written spec for all fifteen.

**Marketplace specifically** (§6): full multi-vendor payment infrastructure (split payments, seller payouts, commission ledgers) is a genuinely hard problem (Stripe Connect or equivalent, KYC, tax forms per seller) that does not belong in this roadmap's near-term phases. The *right* MVP here, when it's prioritized, is: Marketplace = Commerce + a `Seller` entity + product ownership scoped to seller instead of business, with a manual/deferred payout process (no live split-payment integration) — correctly architected so Stripe Connect can be dropped in later without a data-model change. Not building this now; not blocking it either.

## 3. Target architecture

### 3.1 Website as an application, not a JSON blob

The mission's §16 framing is right and matches where the audit already points: a `Website` should own Pages, Navigation, Theme, Capabilities, and Settings as *first-class concepts*, with each Page holding a *block-tree* (JSON — genuinely appropriate here) and each Capability owning its *own relational tables* (genuinely inappropriate as JSON). Concretely:

- **Stays JSON** (inside `Website.draft`/`published`, or a new `WebsitePage` JSON column — see §3.2): block tree, per-block style/responsive overrides, theme tokens, navigation tree, page-level SEO overrides. All of this is *structure*, edited by the Builder, versioned as a whole snapshot on publish — exactly what JSON is for (§59/§60).
- **Becomes relational**: `Product`, `Order`, `Customer`, `Service`, `Appointment`, `Post` (blog), `FormSubmission`, `MediaAsset`, `AnalyticsEvent` — anything with real CRUD, real relationships, real query needs (search, filter, sort, pagination), and a lifecycle independent of "someone opened the Builder." Every one of these tables gets a `businessId` (or `websiteId`, chosen per-entity — see §3.6) foreign key, indexed, `onDelete: Cascade` from `Business`, mirroring the existing `Website`/`Domain` pattern exactly.

### 3.2 Page entity & routing (the top-priority build — everything else depends on it)

```prisma
model WebsitePage {
  id         String    @id @default(uuid())
  websiteId  String
  website    Website   @relation(fields: [websiteId], references: [id], onDelete: Cascade)
  slug       String    // "", "about", "contact" — "" reserved for home
  title      String
  /// 'custom' = user-built page (block tree in `content`).
  /// 'system' = capability-owned route (products list, product detail,
  /// cart, checkout, blog, booking...) — `content` is null, the page is
  /// rendered by that capability's own component, not the block renderer.
  type       PageType  @default(custom)
  /// Only for type = system — which system route this is
  /// ("products", "product-detail", "blog-post", "cart", ...).
  systemKey  String?
  content    Json?     // block tree — present only for type = custom
  seoTitle       String?
  seoDescription String?
  ogImage        String?
  isHidden       Boolean  @default(false) // e.g. custom 404, unlisted pages
  order          Int      @default(0)      // for nav ordering, see §3.3.5
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt

  @@unique([websiteId, slug])
  @@map("website_pages")
}

enum PageType {
  custom
  system
}
```

This replaces `WebsiteDocument.pages: WebsitePage[]` (frontend type, JSON-embedded) with a real table. It's the one place I'm recommending moving *something* out of the draft/published JSON blob and into its own model — because pages need their own URLs, their own SEO metadata, their own create/delete/reorder lifecycle independent of block-editing, and (critically) system pages need to exist *before* any content capability is even installed (an empty Products page still needs a slug reserved).

**Routing** (Next.js App Router, matches the existing `/site/[businessId]` convention exactly):

```
/site/[businessId]/[[...slug]]
```

One catch-all route. Resolution order at request time:
```
businessId + slug[]
    ↓
look up WebsitePage by (websiteId, slug.join('/'))
    ↓
found, type=custom  → render block tree through WebsiteRenderer (unchanged)
found, type=system  → dispatch to the owning capability's page component
                       (ProductDetailPage, BlogPostPage, CheckoutPage, ...)
not found            → 404 (with the site's own configured 404 page, §72)
empty slug           → the page with slug=""  (home)
```

Dynamic *entity* pages (`/products/[slug]`, `/blog/[slug]`) are **not** separate `WebsitePage` rows per product/post — they're a *single* system page (`systemKey: "product-detail"`) whose renderer receives the trailing slug segment and fetches the matching `Product`/`Post` from its own table. This is exactly §46's requirement and avoids ever creating a `WebsitePage` row per product.

`generateMetadata` for the catch-all reads the resolved page (custom SEO fields, or the entity's own for system detail pages) — satisfies §41/§75 without new plumbing beyond what `/site/[businessId]/page.tsx` already does for the single page today.

### 3.3 Capability system

This is the load-bearing decision the mission calls out (§33 in the roadmap prompt, and again explicitly in the "жёсткие принципы" addendum: *"Это, на мой взгляд, самое важное архитектурное решение для твоего проекта"*). Agreed — everything else in this document is built to make this one thing true:

```ts
interface Capability {
  key: string;                      // 'commerce' | 'booking' | 'content' | ...
  label: string;
  entities: EntityDefinition[];      // what tables/domain models it owns
  systemPages: SystemPageDefinition[]; // routes it registers (§3.2)
  widgets: BlockDefinition[];         // Builder blocks it contributes (uses the EXISTING registry — see below)
  dashboardSections: DashboardSection[]; // nav entries + pages under /business/[id]/dashboard
  events: string[];                  // analytics event names it can emit (§3.8)
}
```

- `Business.capabilities: BusinessCategory[]` category-to-default-capabilities mapping is a static lookup table (Restaurant → [Menu, Booking(reservations), Content]; Retail → [Commerce]; Services → [Booking]; etc.), stored as a `Business.capabilities String[]` column (Postgres array, same pattern already used for `User.tags`) so a business can *add* capabilities later (§33's explicit "Restaurant + Online ordering + Reservations + Blog" example) without a category change.
- A capability's `widgets` are just more calls to the **existing** `registerBlock()` — `ProductGrid`, `ServiceGrid`, `BlogGrid` etc. are ordinary blocks with one addition (§3.4). No parallel widget system, no `ShopBuilder`/`RestaurantBuilder` fork — this directly satisfies the "Universal Core + Capabilities, not vertical-specific builders" principle.
- The Component Library panel (`ComponentLibraryPanel.tsx`) filters `listVisibleBlockDefinitions()` by the active business's enabled capabilities — one filter added to an existing function, not a new panel.

### 3.4 Component schema evolution — data-driven widgets

The single most important addition to `BlockDefinition`/`FieldSchema` (currently: `type, label, category, icon, fields, isContainer, Renderer`) is a **data-source field type**, so `ProductGrid` never hardcodes products:

```ts
interface DataSourceFieldSchema extends FieldBase {
  control: 'dataSource';
  entity: 'product' | 'post' | 'service' | 'employee' | ...; // which capability entity
  // resulting value shape written into block.props:
  // { entity, filter: {...}, sort, limit, mode: 'auto' | 'manual' }
}
```

A block like `ProductGrid`'s `Renderer` receives `props.dataSource` and calls a small **DataSourceResolver** (one per entity, registered by the owning capability) that turns `{ entity: 'product', filter: { category: 'shoes' }, sort: 'price', limit: 12 }` into actual rows — server-side for the public renderer (data fetched in the page's server component, passed down), and via a lightweight client fetch for the Builder canvas's live preview. This is the literal implementation of §27/§28 ("Widget → Data Source → Products," never "Widget → hardcoded products").

Two more additive fields close out §49/§50:
- `allowedChildren?: string[]` on `BlockDefinition` — `Section`/`Container` allow anything; `Button` allows none; `ProductGrid` allows nothing (it's data-driven, not a manual container). Enforced in `insertBlock`/`moveBlock`/the DnD `onDragEnd` validator (`block-tree.ts`) — reject/redirect an invalid drop instead of silently corrupting the tree (§9's "invalid drop" requirement).
- `actionsSchema?: FieldSchema[]` on interactive blocks (`Button`, form submit) — resolves to one of a small fixed `Action` union (`navigate | openModal | submitForm | addToCart | bookAppointment | openUrl | callPhone | sendEmail`, per §35), dispatched by a single `useBlockAction()` hook shared by every interactive block, not reimplemented per block.

### 3.5 Theme system & design tokens

Already partially real: `WebsiteTheme { colors, fonts, radius, buttonStyle, containerWidth, sectionSpacing }` exists and already flows through `buildThemeCssVars()` into CSS custom properties (`--site-*`) consumed by every block renderer. What's missing against §22/§25's full list (spacing scale, shadows, borders, breakpoints as tokens) is additive to the same `WebsiteTheme` object and the same `buildThemeCssVars()` function — no new mechanism, just a bigger token set and a few more `ThemePanel.tsx` sections (following the exact `FieldGroup` compact/desktop pattern already built this session).

Per-property responsive overrides (§23/§24) already exist for the handful of fields marked `responsive: true` (`ResponsiveValue<T>`, `resolveResponsive()`) — this is proven, tested infrastructure from this session's work, not something to invent. The task is applying it to more of `BlockStyle`'s fields (padding, margin, sizing, display), gated behind a `Basic / Advanced` inspector split (§23's explicit warning against "a chaotic panel of hundreds of fields") rather than exposing all of it flat.

### 3.6 Data model ownership

```
User
 └── Business (ownerId)
      ├── Website (1:1)
      │    ├── WebsitePage[]        (§3.2)
      │    └── Domain[]              (exists today)
      ├── Product[]  / Service[] / Post[] / Room[] / Property[] / Event[]
      │    (whichever capabilities are active — all FK'd to businessId, NOT websiteId:
      │     these are business data, they should survive a hypothetical future
      │     "regenerate my website" without needing to be re-entered)
      ├── Order[] / Appointment[] / FormSubmission[] / AnalyticsEvent[]
      └── MediaAsset[]
```

Every capability table gets `@@index([businessId])` and `onDelete: Cascade` from `Business`, mirroring the existing `Website`/`Domain` relations exactly — this is the concrete implementation of §30's isolation requirement, and it's the same pattern already proven correct in this schema (checked: `Website A` and `Website B` cannot cross-reference today because `businessId` is a hard FK everywhere; new tables just continue that).

### 3.7 API / Server boundaries

One NestJS module per capability (`ProductsModule`, `OrdersModule`, `BookingsModule`, `PostsModule` — careful: **collides in name with the existing social `PostsModule`**, so the blog capability's module must be named e.g. `ContentModule`/`BlogPostsModule`), each with its own `Service`/`Controller`, matching the existing `WebsitesModule`/`DomainsModule` shape — never one `WebsiteService` accreting hundreds of methods (§62's explicit warning, and consistent with how `businesses`/`websites`/`domains` are already split today).

### 3.8 Events & analytics foundation

One table now, no dashboard yet:

```prisma
model AnalyticsEvent {
  id         String   @id @default(uuid())
  businessId String
  name       String   // 'page_view' | 'product_viewed' | 'checkout_started' | ...
  payload    Json      // small, event-specific — never a full entity snapshot
  sessionId  String?   // anonymous visitor correlation, not a User
  createdAt  DateTime  @default(now())

  @@index([businessId, name, createdAt])
  @@map("analytics_events")
}
```

Emitted server-side at the point of the real action (order created, form submitted, booking created) — never trusted from the client for anything that affects business data, only for `page_view`/`product_viewed`-style signals where client emission is acceptable (§42's explicit scope: foundation, not a platform). A dashboard reading these aggregates is a later phase.

### 3.9 Integrations — Stripe as the worked example

```
Checkout widget → PaymentProvider interface → StripeAdapter (backend, server-only)
```

`PaymentProvider` is a small backend interface (`createPaymentIntent`, `confirmPayment`, `refund`) with exactly one implementation (`StripeAdapter`) to start. Secret keys live in backend env vars, scoped per-environment (not per-business at first — per-business Stripe Connect accounts are the Marketplace-tier problem from §2.3, deliberately deferred). The frontend only ever sees a client secret / publishable key, matching §37's explicit "never store secret keys on the client." `stripe` (Node SDK) and `@stripe/stripe-js`/`@stripe/react-stripe-js` are the concrete dependencies to add when this phase starts — not installed yet, per §78's vetting requirement (real, maintained, right-sized for the job).

### 3.10 Forms & Media Library

**Forms**: a `FormDefinition` (JSON schema of fields, stored per-block or per-page) + `FormSubmission` table (businessId, formId, data: Json, createdAt) — the block itself (`FormBlock.tsx` already exists) gets a generic submit handler posting to one `FormsController` endpoint, with server-side validation against the field list (never trust client validation alone, §63). Spam protection architecture = honeypot field + rate limiting (`@nestjs/throttler` is already a backend dependency) — no external CAPTCHA vendor decided yet, left as a swap-in adapter.

**Media Library**: a `MediaAsset` table (businessId, url, mimeType, width/height, createdAt) that every upload flow (website assets, product images, future post images) writes into once, and the `ImageField` inspector control gets a "browse existing" tab alongside "upload new" — directly reusing the existing `GalleryImage` pattern from the social side of the app, just scoped to `businessId` instead of `userId`.

### 3.11 SEO

Already real at the `Website.settings` level (`seoTitle`, `seoDescription`) and at `Business` level (same fields, currently unused by the builder — worth wiring together, not duplicating). Extends to `WebsitePage` (§3.2's `seoTitle/seoDescription/ogImage`) and to dynamic entities (`Product.seoTitle` optional override, falling back to `Product.name`/`description`) — same `generateMetadata` pattern Next.js already uses today for the single public page, just fed by the resolved page/entity instead of the whole site.

### 3.12 Templates & starter experience

`entities/website/templates/*.ts` already exist (`restaurant.ts`, `agency.ts`, `local-business.ts`) and already generate an initial block tree via `StarterTemplatePicker.tsx` — this is real, working infrastructure, not a gap. It needs exactly one extension once capabilities land: a template can also declare which capabilities to enable and seed 1-2 example rows (a sample Product, a sample Service) so a new Commerce site isn't an empty catalog on day one — matching §44's flow (`Create Business → category → template → generate → customize`) which the app already implements up through "generate," just without capability/data seeding yet.

### 3.13 AI-readiness

No AI work in this roadmap. The block-tree's flat JSON shape and the capability/entity model's structured relational data are both already exactly what a future LLM-generation step would need to target (§45) — nothing in §3 above closes that door, and nothing needs to be added now to keep it open.

## 8. What actually shipped in Phases 1–7

Acted on the mission's "не спрашивай, реши сам" instruction and carried Phases 1–2 through to a tested, working state rather than stopping at the plan. Summary, for whoever picks up Phase 3 next:

**Data model.** `WebsitePage` is now a real table (`id, websiteId, slug, title, type, systemKey, content, seoTitle, seoDescription, isHidden, order`), not a JSON array embedded in `Website.draft`. `Website.draft`/`published` now hold only `{theme, settings}` — `WebsitesService` assembles the full `WebsiteDocument` (with `pages[]`) on read by joining the theme/settings JSON with the current `WebsitePage` rows, and `publish()` does the same to build the `published` snapshot. This is the exact mechanism described in §3.1/§3.2 of this document, not a simplified version of it. A one-off backfill script (`prisma/migrate-pages-to-table.ts`) moved the one pre-existing business's page into the new table; it's safe to re-run (idempotent per-website) if it's ever needed against another environment.

**Builder UI.** A new "Страницы" tab (same accordion pattern as the existing "Блоки"/"Настройки" tabs) lists all pages, and supports create/rename/reorder/delete — all routed through the same undo/redo history stack as block edits (`withDocumentHistory`, a sibling of the existing `withHistory`), so "I deleted the wrong page" is recoverable the same way "I deleted the wrong block" already was. Page slugs auto-follow the title (CMS-standard behavior) until a page gets a manual slug editor in a future pass — there isn't one yet, so in practice every slug is still auto-derived today.

**Public routing.** `/site/[businessId]/page.tsx` became `/site/[businessId]/[[...slug]]/page.tsx`. The first page by `order` is home (served with no path segment); everything else is served at `/[slug]`. An unmatched slug renders a friendly "Страница не найдена" state, not a crash. `proxy.ts`'s custom-domain rewrite was also fixed to forward the requested path (`coffee.com/about` → `/site/{id}/about`) — it was previously discarding everything past the hostname and rewriting every request to the bare site root, which would have made this whole feature invisible to anyone visiting through an actual connected domain rather than through Tavern's own internal preview route.

**Two bugs found and fixed along the way, not originally scoped but real:**
- `renamePage` updated a page's display title without ever updating its slug, so a page's URL stayed permanently pinned to whatever it was called at creation (e.g., "Новая страница" → `/novaya-stranitsa` forever, even after renaming it to "О нас"). Fixed by making the slug follow the title until it diverges from the auto-derived form.
- Confirmed by testing, not by inspection: navigating away from the Builder (via the in-app "back" link, or a hard refresh/tab close) within the ~1.5s autosave debounce window silently dropped the pending change — reproduced it directly (added a page, navigated away immediately, checked the database: the page was gone). This was a pre-existing gap flagged as a known limitation in an earlier session's stabilization pass, not something introduced here, but this work made it trivially easy to hit (one click after one click), so it was fixed rather than left as a footnote: a `beforeunload` guard now warns on hard navigation while dirty, and `WebsiteBuilderWidget`'s unmount cleanup now flushes a best-effort save before resetting the store, which covers the in-app-navigation case `beforeunload` structurally cannot.

**Verified, not assumed:** multi-page create/rename/delete/reorder in the Builder; real independent public rendering of two different pages of the same site at two different URLs; a non-existent slug's 404-equivalent state; `duplicate()` on a business with 2 pages correctly copying both pages (with fresh IDs, not reused ones — the earlier draft of the migration script had a latent bug here, reusing the literal `'home'` id from the seed template, which would have collided the moment a second business existed; caught and fixed before it could ship); cascade-delete of a business correctly removing its pages via the same FK cascade chain already used for `Website`/`Domain`. All four backend/frontend `npm run check` passes are clean; zero new console/server errors across the whole test session.

### Phase 3 — scope adjustment (deliberate, documented here rather than silently done)

The plan for Phase 3 (§5's table, before this edit) bundled two things together: a `Business.capabilities` data model + registry, and a Dashboard shell. Splitting them apart on purpose:

**Built now: the Dashboard shell.** `/business/[id]/dashboard` — a real, immediately useful consolidation of what was previously scattered across `/business/[id]` (social profile), `/business/[id]/edit` (Builder), and `/business/[id]/settings` (domains/metadata) with no unifying hub (§0.3's audit finding #5). It has two working sections today — **Overview** (publish status, page count, one-click publish without opening the Builder) and **Pages** — plus direct links out to the Builder, Settings, and the live public site. Both backend endpoints this reads from (`getBusiness`, `getWebsiteDraft`) already existed; nothing new was added server-side for this piece. Verified end-to-end via Playwright including the publish action and a mobile-width layout pass (nav collapses from a fixed sidebar to a horizontal scrollable bar below `mobileOrTablet`).

**Pages started read-only, then got delete added on direct request.** The first pass linked out to the Builder's `PagesPanel.tsx` for all editing rather than duplicating it. After using it, the request came back to at least allow deleting a page without opening the full Builder — reasonable: not every page-management action needs the weight of the editor. Added delete (with a confirm dialog, and disabled once only one page is left) directly to the Dashboard's Pages section. It does **not** go through the Builder's Zustand store or its undo history — the Dashboard is a separate screen that talks to the same `saveWebsiteDraft` endpoint the Builder's autosave already uses, so a delete here is immediate and has no undo, and the confirm dialog says so explicitly rather than implying a safety net that isn't there. Verified the deletion is real (checked the database directly, not just the UI state) and that the last remaining page correctly cannot be deleted.

**Deferred to bundle with Phase 5 instead: `Business.capabilities` + the capability registry.** Reasoning: every capability this column would reference (`commerce`, `booking`, `content`, ...) is still just an entity sketch in §2.1 — none has a single line of implementation yet. Adding a `capabilities: string[]` column and a filtering hook in the Component Library *today* would filter nothing (every existing block is a core Builder block, not capability-gated) and gate nothing in the Dashboard nav (there's no Products/Bookings section to show or hide) — it would be schema and code sitting unused for an unknown number of future sessions, which is exactly the speculative-infrastructure trap §1 and the "don't build for a hypothetical" principle warn against. Building it alongside the *first* real capability (Commerce, Phase 5) means the column and the registry pattern get proven against actual behavior from the day they're introduced, not before. The Dashboard shell built now is already structured so that capability-gated nav sections slot into the same list later without a rewrite — confirmed by design, not just asserted: `IN_PAGE_TABS` in `BusinessDashboardWidget.tsx` is exactly the array a future capability-gated section would extend.

### Phase 4 (in progress) — the link/navigation field system

**What shipped.** A `LinkTarget` structural type (`{type: 'external'|'page'|'anchor'|'phone'|'email', ...}`) replaced raw-string URLs on every block field that means "navigate somewhere" — button/link/CTA/banner URLs, nav-menu and footer links, breadcrumb items, pricing-plan buttons, card/article links, image click-through. A new `control: 'link'` inspector control (`LinkField.tsx`) lets the editor pick the target type and, for `page`, choose an actual page of the site from a dropdown — not type a URL by hand and hope it still matches after a future rename. `resolveLinkHref(target, pages)` (`entities/website/model/resolve-link.ts`) resolves this lazily at render time (page index 0 → `/`, others → `/{slug}`), so renaming or reordering pages never leaves a stale link behind the way a hand-typed URL would have. `BlockRendererProps.pages` was made a required field specifically to force a compile error at every call site that needed threading the pages array through — used deliberately as a checklist, not left as an oversight.

Left alone on purpose: three genuine embed/iframe `src` fields (`Video.embedUrl`, `Location.mapEmbedUrl`, and the utility embed block) — these are never "navigate to," so `control: 'url'` (raw string) stays correct for them. `business.socialLinks` hrefs are also untouched — sourced from the Business entity, not block props, out of scope here.

**A real regression found and fixed before it could ship: legacy raw-string link data.** The one pre-existing real business's site (a restaurant site, predating this feature) stores `buttonUrl: "#contact"`, `navLinks[].url: "#about"`, etc. as bare strings — that was the only shape that existed before `LinkTarget`. `resolveLinkHref` doesn't recognize a bare string as any `LinkTarget.type`, so without intervention every one of these previously-working anchor links would have silently resolved to `#` the moment this code shipped — not a crash, but a silent breakage of real content on a real site, which is worse (nobody gets an error to investigate). Caught this by directly querying the database for existing `website_pages.content` rows containing button/link-shaped props, rather than assuming a fresh feature only ever meets fresh data. Fixed with a one-off backfill (`backend/prisma/migrate-legacy-link-props.ts`, sibling to `migrate-pages-to-table.ts`, same idempotent-rerun convention) that walks every block's known link fields (hardcoded list mirrored from the `control: 'link'` grep, since backend doesn't import frontend's block registry) and converts a surviving raw string into the equivalent `LinkTarget` (`"#contact"` → `{type:'anchor', anchor:'contact'}`, `"tel:..."` → phone, `"mailto:..."` → email, anything else → external). Ran it against the real dev database; confirmed via direct SQL that the restaurant site's anchors now round-trip through the new structural form with their original targets intact, and confirmed a second run is a true no-op. **Anyone deploying this to another environment (staging/prod) with existing website content must run `npm run migrate-legacy-link-props` once, the same way `migrate-pages-to-table` was required — noting it here so it isn't missed.**

**Verified, not assumed:** end-to-end via a scripted flow (register → create business → save a draft with a page-link, external-link, and phone-link button → publish → fetch the real anonymous `/sites/:businessId` payload, the exact endpoint the public widget calls) confirming the `LinkTarget` objects round-trip through save/publish unchanged, and independently re-deriving `resolveLinkHref`'s output against that published data to confirm the resolved hrefs are correct (`/about` for the page link, the raw URL for external, `tel:+...` for phone). Also confirmed both `/site/{id}` (home) and `/site/{id}/about` return 200. **Not yet verified: an actual browser rendering pass of the `LinkField` UI itself** (the page-picker dropdown, live editing) — no headless browser or Playwright is available in this environment (checked: no `playwright`/`puppeteer` package installed, no Chromium binary present, and the Claude-in-Chrome extension isn't connected in this session). The data-level round-trip plus a direct read of `SiteButton`'s JSX (`<a href={resolveLinkHref(...)}>`) stands in for that pass; flagging the gap rather than silently treating it as fully covered.

**`allowedChildren` — shipped.** Added `allowedChildren?: string[]` to `BlockDefinition` (`registry.ts`) and enforced it at the one real choke point every insert/move already passes through, `insertBlock`/`moveBlock` in `model/block-tree.ts` — not duplicated in the DnD handler, the "add from library" modal, or the "insert beside" action, since all three already call into these two functions. Only `columns` gets a restriction (`allowedChildren: ['column']`) — it's the one container where arbitrary content actually corrupts a real assumption (`ColumnsRenderer`'s column count is derived from how many `column` children exist; a bare block dropped directly into `columns` would silently break that grid). `section`/`container`/`column` stay unrestricted (`allowedChildren` left `undefined`), matching their exact prior behavior — no regression for the common case. An invalid `insertBlock` now returns the tree completely unchanged rather than partially applying it; `moveBlock` specifically needed its own pre-check (not just delegating to `insertBlock`'s) because a naive delegation would have removed the dragged block via `removeBlock` and then silently failed to reinsert it, deleting it outright on a rejected drop — caught this while implementing, not after. Verified with a standalone script (`tsx`, minimal stand-in block definitions to route around the real blocks' `.module.scss` imports which have no loader outside the Next.js build) exercising the real `insertBlock`/`moveBlock` code: a bare block is rejected as a direct child of `columns` (tree unchanged, nothing deleted), a `column` is accepted into `columns`, `section` still accepts anything (no regression), and both an invalid and a valid `moveBlock` behave correctly.

**`actionsSchema`/`useBlockAction()` — deferred, not started, and not accidentally skipped.** The plan's action union (`navigate | openModal | submitForm | addToCart | bookAppointment | openUrl | callPhone | sendEmail`) is mostly already covered by this same phase's `LinkTarget`/`resolveLinkHref` work (`navigate`≈page target, `openUrl`≈external, `callPhone`≈phone, `sendEmail`≈email) — what's left over is exactly the set with no real backend behind it yet: `submitForm` has no submission endpoint (checked — the three form blocks are explicit MVP placeholders, see their own comment: "ни одна реально никуда не отправляет данные"), and `addToCart`/`bookAppointment` reference Commerce/Booking capabilities that don't exist as more than a §2.1 sketch. Building a generic `useBlockAction()` dispatcher now would mean writing real dispatch code for actions with nothing on the other end — the same speculative-infrastructure trap already named for `Business.capabilities` in the Phase 3 section above, for the identical underlying reason (no real capability to prove it against yet). Bundling this with Phase 5, when Commerce gives `addToCart` a real cart to add to, is the same call made consistently rather than a new one.

### Phase 5 (started) — Commerce foundation: product catalog, no checkout yet

Scoping this deliberately narrower than the full §2.2 Commerce matrix for the same reason every prior scope cut in this document was made: ship a real, verified, end-to-end slice first, then extend it, rather than build the full matrix (`ProductVariant`, `Category`/`Collection`, `Order`/`Cart`, Stripe) speculatively before a single real product exists on the platform to prove any of it against. What shipped this round is genuinely useful on its own — a small business can list products with prices and photos and manage them without opening the Builder — even before checkout exists (the same way a printed menu or a "call to order" catalog is useful without an online payment flow).

**Two deferred pieces of earlier phases landed here, on purpose.** `Business.capabilities` (deferred from Phase 3 — see its section above) is now real: a `String[]` column, validated against a `BUSINESS_CAPABILITIES` const (today: just `'commerce'`), toggled from the Dashboard. The `dataSource`/resolver field pattern (deferred from Phase 4 — see its section above) is now real too: `FieldSchema` gained a `control: 'dataSource'` variant, and `productgrid` is the first block that uses it — its `props` store only `{ limit, sort }`, never the products themselves, resolved fresh at every render via `getPublicProducts`. Both were reasoned as "build alongside the first real capability, not before" — Commerce landing is that moment for both.

**Data model.** A new `Product` model (`id, businessId, name, slug, description, priceCents, currency, images[], stock, isActive, order`), FK'd to `Business` with `onDelete: Cascade`, `@@unique([businessId, slug])`. Deliberately narrow: no `ProductVariant`/SKU, no `Category`/`Collection`, no `Discount`, no `Review` — none of them have a UI that would use them yet (the same reasoning as everywhere else in this document). Price is an integer in minor currency units (kopecks/cents), not `Float` — avoids float rounding on money, the same principle any payment code follows.

**Backend.** `ProductsModule` (`products.controller.ts`/`.service.ts`, owner-only CRUD under `/businesses/:businessId/products`, session-guarded, 404-not-403 on cross-owner access matching the existing `BusinessesService` convention) plus a genuinely anonymous read path (`GET /sites/:businessId/products` on the existing `PublicSitesController`, active products only, a separate minimal `PublicProductDto` with no `businessId`/`order` — mirrors the `WebsitePublicDto` owner/public split already established for websites). Slug uniqueness and de-duplication (`kofe`, `kofe-2`, ...) scoped per-business, reusing the businesses module's existing `slugify()` rather than duplicating it. `Business.capabilities` validated server-side against a fixed allow-list (`@IsIn(BUSINESS_CAPABILITIES)`) — a client cannot toggle on a capability that doesn't exist.

**Dashboard.** A new "Товары" tab, shown unconditionally (not gated behind the capability being already-enabled) — gating the tab itself would be a chicken-and-egg UX dead end: there'd be no way to discover the enable action if the entry point to it is hidden until it's enabled. Instead `ProductsSection` shows an `EmptyState` with an "Включить онлайн-магазин" CTA when the capability is off, and the real list/create/edit/delete UI once it's on. A `ProductFormModal` (name/price-in-rubles/description/stock/visibility/cover photo) reuses the existing `Modal` shared component and the existing upload-flow pattern (`ProductImageField`, same shape as the Builder's `ImageField`, its own backend upload endpoint).

**Builder.** `productgrid` is a new block (`entities/website/blocks/commerce`), gated in the Component Library behind a new `BlockDefinition.capability` field — filtered only at the "what can I add" layer (`ComponentLibraryPanel`/`AddBlockModal`), never at the render layer, so a block already placed on a page keeps rendering even if the capability is later switched off (same "don't break existing content" principle as everything else that touches already-saved data this session). Renders through the existing `RepeatableSimpleCards` shared card grid, fed by real fetched product data rather than static `props`. `BlockBusinessContext` gained a `businessId` field (threaded through all four places that construct it — public site, business profile page, Builder) specifically so a data-driven block can fetch its own capability data without every non-data-driven block needing to know a business's id.

**Verified, not assumed:** a backend-level scripted flow (register → create business → confirm capabilities start empty → create a product *before* enabling commerce, confirming products are intentionally NOT capability-gated server-side, only in the Builder's UI → enable the capability → reject an invalid capability value → create/update/delete products → confirm slug de-duplication → confirm the public endpoint excludes inactive products and strips owner-only fields → confirm a second user gets 403/404 on this business's products) — all passed. **Explicitly not built yet (the rest of Phase 5):** `Cart`/`Order`/`OrderItem`/`Customer` entities, an actual add-to-cart/checkout flow, the `PaymentProvider`/`StripeAdapter` integration (§3.9), and the `ProductVariant`/`Category`/`Discount`/`Review` entities from the full §2.2 matrix. This increment intentionally stops at "list and manage a catalog" — checkout is real, separable follow-up work, not an oversight.

### Phase 5 (continued) — cart, orders, and the full browse→order loop (still no live payment)

**Scope decision, made the same way as every prior one in this document:** built `Order`/`OrderItem` and a real cart→checkout flow *without* wiring up Stripe yet. Reasoning: an order today is a "request" the owner fulfills manually (phone/messenger) — the same honest MVP pattern the `FormBlock`s already established for contact forms, except this one actually writes to the database and shows up in a real Dashboard section, not a decorative success message. This is a genuinely usable feature on its own (many small storefronts *are* "message to confirm and pay" businesses), and — just as importantly — a live Stripe integration is not something this environment can responsibly ship unverified: there are no Stripe test keys configured and no way to exercise a real `PaymentIntent`/webhook round trip here, and shipping payment code that was never actually run against Stripe would violate the same "verify, don't assume" discipline this whole session has followed (see the Phase 4 section's identical reasoning about not having a browser to test in). Stripe is scoped as the next increment, explicitly gated on the user providing real test API keys.

**Data model.** `Order` (businessId, status enum `pending|confirmed|completed|cancelled`, customerName/Email/Phone/Note, totalCents, currency) and `OrderItem` (orderId, productId — nullable, `onDelete: SetNull` — name, priceCents, quantity). No `Customer` entity: the buyer is anonymous (no Tavern account involved in a storefront purchase), so their contact details are just fields on the order, not a row in a table with its own CRUD nobody would use yet — the same "don't build a entity with zero real UI" discipline applied everywhere else this session. `OrderItem.name`/`priceCents` are a **snapshot** taken at order time, not a live read of `Product` — renaming or repricing a product later must never rewrite the history of an order that already happened.

**Backend — price and stock integrity were the hard part, and got the most scrutiny.** `OrdersService.createFromCart` is the single path that creates an order, and it never trusts anything about price from the anonymous caller: only `{productId, quantity}` crosses the wire (enforced by `ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })` in `main.ts` — an extra `priceCents` field in the request body gets the *whole request* rejected with 400, not silently stripped, which is a stronger guarantee than "the server ignores it"). Every product referenced is re-fetched from the database scoped to `{id, businessId, isActive: true}` — the `businessId` scope specifically closes a cross-tenant injection: without it, a malicious request to Business B's order endpoint could reference Business A's `productId` and pull A's price/name into an order attributed to B. Stock decrement uses a conditional `updateMany({ where: { id, stock: { gte: quantity } } })` and checks the affected-row count, not a read-then-write on a previously-fetched `stock` value — closes a real race window (two customers ordering the last unit at the same moment) that a naive read/check/write would have missed. Duplicate line items for the same product in one request are aggregated before the stock check, not validated line-by-line against the same stale snapshot (caught this while writing the code, not after — a built-in test for it exists in the verification script). The anonymous order-creation endpoint carries its own tighter `@Throttle` than the rest of the public API, since it is the only anonymous endpoint anywhere in the project that writes to the database.

**Frontend.** A new `entities/cart` slice holds a Zustand store, `persist`-ed to `localStorage` (not `sessionStorage` — a cart should survive closing the tab, unlike the existing `navigation-store`'s "which tab was I on" state) and scoped by `businessId` inside the persisted state itself, so switching between two different Tavern-hosted storefronts in the same browser can't leak one merchant's cart into another's. `CartWidget` (`entities/cart/ui`) is a floating cart button + modal mounted once, globally, on the public site and the internal `/business/[id]` preview — deliberately *not* a draggable Builder block, because a cart icon that only appears on pages the owner remembered to drop it onto would be a real foot-gun (a customer on any other page of the same site simply couldn't check out). One non-obvious implementation detail: the shared `Modal` component renders through a React portal to `document.body`, which is outside the DOM subtree that `WebsiteRenderer` applies the site's `--site-*` theme CSS variables to — so the cart modal deliberately uses Tavern's own `--tavern-*` design tokens instead of the site's theme, not a copy-paste oversight (documented inline in `CartWidget.module.scss` so a future edit doesn't "fix" it by switching to the theme tokens and quietly breaking it).

**Builder.** `ProductGridRenderer` was upgraded from a read-only card grid (`RepeatableSimpleCards`) to its own card component with a real "В корзину" button, since `RepeatableSimpleCards` has no way to attach a per-card action. Respects the existing `isEditing` convention (`BlockRendererProps.isEditing`) the same way `FormBlock` already does — clicking "add to cart" while editing in the Builder canvas is a no-op, not a real cart mutation.

**Dashboard.** A fourth tab, "Заказы" (`OrdersSection`), lists orders with customer contact info, line items, total, and a status dropdown the owner uses to track fulfillment by hand. Unlike "Товары", this tab is **not** capability-gated at all — it shows order history unconditionally, because disabling the commerce capability later must not make previously-placed real orders disappear or become unreachable.

**Verified, not assumed:** a backend-level script covering the security-sensitive paths specifically — order total computed correctly from real product prices; stock decremented atomically; over-ordering beyond remaining stock rejected with stock left completely unchanged (not partially decremented); ordering an inactive product rejected; a request with a client-supplied `priceCents` rejected outright by the whitelist validator; a cross-business `productId` injection attempt rejected; owner-side listing and status updates working with correct cross-owner isolation (403/404); the rate limiter on the anonymous order endpoint actually engaging when hit repeatedly (confirmed by tripping it accidentally while re-running the test script, then correctly waiting out the window — see it actually fire is stronger evidence than reading the decorator). A second, separate end-to-end script exercised the full realistic path — enable commerce → create a stocked product → place a real `productgrid` block via save/publish → submit a real anonymous order against it → confirm the order appears in the owner's Dashboard data and stock reflects it → hit the live `/business/{id}/dashboard`, `/business/{id}/edit`, and `/site/{id}` Next.js routes with a real session cookie and got clean 200s. **Not verified: an actual browser/visual pass** — same standing environment gap as every prior phase this session (no Playwright/Chromium/Claude-in-Chrome here) — so the cart drawer's quantity steppers, the checkout form's actual on-screen layout, and the FAB's badge positioning were verified by reading the component code and its data flow, not by looking at rendered pixels. Flagging this consistently rather than letting it quietly become "assumed done" as the feature list grows.

**Explicitly deferred to the next increment:** the `PaymentProvider`/`StripeAdapter` integration (§3.9) — needs real Stripe test API keys from the user before it can be built *and* verified, not just built. Also still deferred from the original §2.2 matrix: `ProductVariant`, `Category`/`Collection`, `Discount`, `Review`, and a proper `Customer` account/order-history experience for repeat buyers.

### Phase 6 (shipped) — Booking v1: the second capability, proving the architecture generalizes

**Why now, and why this scope.** With Stripe blocked on the user providing real test API keys, the next highest-value, independently-shippable unit of work was a second capability — not a second attempt at Commerce's remaining pieces. Booking is valuable in its own right (services businesses — beauty, fitness, consulting, repair — are a huge share of the category taxonomy in §2.1) and, just as importantly, it is the first real test of whether the capability architecture built for Commerce (§3.3's core bet) actually generalizes or was accidentally Commerce-shaped. It mostly did: `Service`/`Appointment` mirror `Product`/`Order` closely enough that most of the same code shapes — owner CRUD module, public read-only endpoint, snapshot-on-write pricing, Dashboard section pattern, `dataSource`-driven Builder block — were copy-adapted rather than reinvented, which is itself evidence the earlier design decisions were the right ones, not merely convenient for one feature.

**Scope cut, made the same way as Commerce's every time:** no `Employee` entity. Multi-staff scheduling is real complexity (whose calendar, whose working hours, assigning a specific person) that nothing today would exercise — a solo service provider (the overwhelming common case: a hairdresser, a personal trainer, a freelance consultant) *is* their own only "employee," so `Service` belongs directly to `Business`, no join table. Also no `ServiceCategory`/`Location`, no availability engine (see below) — all the identical reasoning already applied to `ProductVariant`/`Category`/`Stripe` for Commerce, not a new argument invented for this phase.

**Data model.** `Service` (id, businessId, name, slug, description, durationMinutes, priceCents, currency, images[], isActive, order) — deliberately near-identical in shape to `Product`, with `stock` swapped for `durationMinutes` (the one thing a service has that a product doesn't: how long it takes). `Appointment` (businessId, serviceId — nullable, `onDelete: SetNull` — serviceName/priceCents/durationMinutes/currency as a snapshot, status enum, startsAt, customer contact fields) mirrors `Order`'s shape, simplified to one service per appointment rather than a cart of line items — a real appointment slot is inherently singular in a way a shopping cart isn't (you don't "add three haircuts to your cart" the way you add three t-shirts). Caught and fixed one modeling gap while writing the DTO: `Appointment` initially had no `currency` field even though `Service` does — added it as its own small follow-up migration rather than editing the just-applied migration in place, keeping to "always add a new migration, never rewrite an applied one" even for a same-session mistake with zero real data at stake.

**Backend.** `ServicesModule` and `AppointmentsModule` are close siblings of `ProductsModule`/`OrdersModule` — same owner/public split, same 404-not-403-on-cross-owner convention, same slug de-duplication reusing the businesses module's `slugify()`. `AppointmentsService.createFromRequest` carries over every price-integrity lesson from Commerce: service looked up scoped to `{id, businessId, isActive: true}` (closes the same cross-tenant injection Commerce closed), `serviceName`/`priceCents`/`durationMinutes` always read from the current `Service` row and never trusted from the anonymous request body (the same `ValidationPipe({ forbidNonWhitelisted: true })` rejects a client attempting to smuggle its own price outright), and a basic future-dated sanity check (`startsAt` must be later than now) rejects an obviously-invalid booking request. The anonymous `POST /sites/:businessId/appointments` carries the same tightened `@Throttle` as order creation — now the second (and, for the moment, last) anonymous endpoint in the whole project that writes to the database, both held to the same higher bar.

**No availability engine — the one deliberate simplification worth calling out on its own.** `CreateAppointmentDto` takes a bare `startsAt` the customer wants, not a slot chosen from a server-computed list of actually-free times. Building real availability (working hours, existing-appointment conflict detection, per-service duration blocking out a calendar range) is a legitimately hard scheduling problem, and — critically — nothing in this codebase could exercise or validate it correctly yet without an `Employee`/working-hours model to compute against. The honest MVP shape, matching Commerce orders exactly: the customer states what they want, the owner reviews and confirms or proposes a different time by phone/message. This is a real, common pattern for small service businesses today (most still take bookings this way), not a placeholder pretending to be a scheduler.

**Frontend.** `entities/service` and `entities/appointment` mirror `entities/product`/`entities/order` slice-for-slice (types, `formatDuration` alongside `formatPrice`, owner CRUD actions, a public anonymous read/write pair). `BookingModal` (`entities/appointment/ui`) is the Booking analogue of `CartWidget`, but structurally simpler: booking has no cart concept — a booking is always exactly one service, so the modal opens straight to the request form instead of a cart-then-checkout flow. Same `--tavern-*`-not-`--site-*` styling choice as `CartWidget`, for the identical reason (the shared `Modal` portals to `document.body`, outside the DOM subtree carrying the site's `--site-*` theme variables) — documented inline again so a future edit doesn't "helpfully" break it by switching to theme tokens.

**Builder.** `servicegrid` (`entities/website/blocks/booking`) is `productgrid`'s Booking counterpart — same `control: 'dataSource'` pattern (now widened from `entity: 'product'` to `entity: 'product' | 'service'`), same capability-gated visibility in the Component Library (`BlockDefinition.capability: 'booking'`), same "keeps rendering even if the capability is later disabled" guarantee. Its card's "Записаться" button opens `BookingModal` directly per-card, respecting the same `isEditing` no-op convention already established for `ProductCard`'s "В корзину" button.

**Dashboard.** Two more tabs, "Услуги" and "Записи," slotting into the exact same `IN_PAGE_TABS` array `BusinessDashboardWidget.tsx`'s own comment predicted a future capability would extend without a rewrite — confirmed by doing it, not just by the earlier comment asserting it would work. Same gating philosophy as Commerce: "Услуги" always visible with an enable-capability `EmptyState` when off, "Записи" never gated at all (appointment history must survive the capability being switched off later).

**Verified, not assumed:** a backend-level script mirroring the Commerce order-integrity script almost check-for-check — service creation and slug de-duplication; owner list vs. public list (active-only, minimal DTO shape); a booking request with correct data producing a snapshot that matches the service's current price/duration; a past-dated booking rejected; a booking against an inactive service rejected; a request smuggling an extra `priceCents` field rejected outright; a cross-business `serviceId` injection attempt rejected; owner-side listing/status-update working with correct cross-owner isolation on both `Service` and `Appointment` resources. A second end-to-end script drove the realistic path — enable booking → create a service → place a real `servicegrid` block via the same save/publish flow the Builder uses → submit a real anonymous booking request against it → confirm it appears in the owner's Dashboard data → hit the live `/business/{id}/dashboard`, `/business/{id}/edit`, and `/site/{id}` Next.js routes with a real session cookie and got clean 200s. **Not verified: an actual browser/visual pass** — the same standing environment gap noted in every phase this session (no Playwright/Chromium/Claude-in-Chrome available here) — so the booking form's date/time inputs, the service card layout, and the modal's success state were verified by reading the component code and its data contracts, not by looking at rendered pixels.

**Explicitly not built yet:** the availability/scheduling engine (`Employee`, working hours, conflict detection, real free-slot computation) — the one piece of the original §2.2 Booking matrix deliberately deferred, for the same "nothing to validate it against yet" reasoning applied everywhere else. Also deferred: `ServiceCategory`, `Location`, reschedule/cancel actions initiated by the customer (today only the owner changes status), and calendar-view UI in the Dashboard (appointments are listed, not shown on a calendar grid).

### Phase 5 (completed) — real Stripe payment, closing out the browse→cart→order→pay loop

**How this started, on the record.** The user provided Stripe keys directly in chat — the first pair were **live** keys (`pk_live_`/`sk_live_`), pasted in plaintext. Flagged this immediately before touching anything: a live secret key sitting in a chat log is an exposure regardless of what happens next (recommended rotating it in the dashboard), and — separately — building and testing a payment integration against live keys the way every other feature this session was tested (automated scripts hitting real endpoints repeatedly) would mean scripting against real money infrastructure, which isn't something to do without explicit sign-off. Asked the user to choose; they agreed test keys were the right call and supplied a real `pk_test_`/`sk_test_` pair. Neither the live nor the test secret key appears in this document or in git history — both live only in `.env` (gitignored).

**Verification tooling, not assumed.** Confirmed real outbound connectivity to `api.stripe.com` before writing any code (a bare unauthenticated request returned 401, proving the network path works, not just that a request *would* work). Downloaded the Stripe CLI directly from GitHub releases (not preinstalled in this environment) specifically so `stripe listen --forward-to localhost:4000/webhooks/stripe` could produce a **real** `whsec_...` signing secret and forward **real** Stripe test-mode webhook events to the local backend — the same bar as everything else this session: verify against the real system, not a mock of it.

**Architecture, per the plan already written in §3.9 before any of this started.** `PaymentProvider` (`modules/payments/payment-provider.ts`) is an abstract class used as an NestJS DI token — the same pattern already proven in this codebase by `DomainVerificationProvider`, not a new idiom invented for Stripe. `StripeAdapter` is the only implementation, and it's the only file in the entire backend that imports the `stripe` package — `OrdersService` and the webhook controller only ever see the provider-agnostic `PaymentIntentResult`/`PaymentWebhookEvent` shapes, never a `Stripe.*` type. One Stripe account for the whole platform (not per-business Connect), exactly as scoped in §3.9 — per-business payment accounts are a Marketplace-tier problem, explicitly out of scope here.

**Data model.** `Order` gained `paymentStatus` (`unpaid | paid | refunded`) and a unique `stripePaymentIntentId`, kept deliberately **separate** from the existing `status` (fulfillment: pending/confirmed/completed/cancelled) — orthogonal axes: an order can be `status: pending` (owner hasn't looked at it) and `paymentStatus: paid` (customer already paid) at the same time, and conflating them would make either state ungovernable on its own. Caught one modeling gap while wiring the DTO — `Appointment` had no `currency` field even though `Service` does — fixed with its own tiny follow-up migration rather than editing the just-applied one, keeping to "never rewrite an applied migration" even for a same-session, zero-data mistake.

**Backend flow.** `OrdersService.createFromCart` still does everything it did before (price/stock integrity, all unchanged) and, if `PaymentProvider.isConfigured()`, additionally creates a `PaymentIntent` for the order's already-server-computed total and returns its `clientSecret` to the caller. This call happens **after** the order-creation transaction commits, not inside it — holding a database transaction open for the duration of an external HTTP call is bad practice regardless of stakes, and if Stripe is slow or briefly down, the order should still exist as an honest unpaid request rather than being rolled back entirely over a transient payment-provider hiccup (caught and deliberately designed around this, not discovered by accident). `automatic_payment_methods: { enabled: true }` is what makes cards/Apple Pay/Google Pay all show up in the frontend's Payment Element automatically, per the user's explicit ask — Stripe decides what to display per visitor/device/domain, no separate integration needed per payment method. Apple Pay specifically still won't appear on `localhost`/system subdomains — it requires a domain registered with Stripe via a hosted verification file over real HTTPS, a constraint of Apple's, not something more code here can work around; it activates automatically the moment a business connects a real domain and that domain is registered in the Stripe dashboard.

**The webhook — the one piece that *must* be server-authoritative, and is.** `StripeWebhookController` (`POST /webhooks/stripe`) is the only place that ever flips an order to `paid` — the frontend's own payment-confirmation callback is deliberately never trusted for this, for the same reason nothing else in this project trusts the client for money (see every prior "never trust the client's price" note in this document). Getting this endpoint to work required `rawBody: true` on `NestFactory.create` — Stripe's signature check is an HMAC over the exact bytes it sent, and Nest's default JSON-parsed-then-`JSON.stringify`'d body is not byte-identical to that even when every field matches, so the naive approach would have failed signature verification 100% of the time. This is Nest's own documented mechanism for this exact problem, not a workaround.

**Verified, not assumed — and this is the highest-fidelity verification pass this whole session.** A scripted flow that: creates a business, enables commerce, creates a product, places an order through the real anonymous endpoint, confirms the returned `clientSecret` corresponds to a **real** `PaymentIntent` fetched back from `api.stripe.com` with the correct amount/currency/metadata, then — instead of stopping at "the API call succeeded" — actually **pays it**, using Stripe's built-in test payment method token (`pm_card_visa`) to confirm the PaymentIntent directly against Stripe's real test-mode API (the same call Stripe.js makes on a customer's behalf, just invoked directly instead of through a browser), and then polls the backend until the order's `paymentStatus` flips to `paid` — which only happens if the real webhook fired from Stripe's servers, was forwarded by the locally-running `stripe listen`, passed real HMAC signature verification, and was correctly matched back to the right order by `stripePaymentIntentId`. Every link in that chain is real; nothing in this pass was mocked or simulated. A second script drove the actual Next.js routes — confirmed importing `@stripe/react-stripe-js` into `CartWidget` (now mounted on every commerce-enabled public site) doesn't break SSR/hydration on the live `/site/{id}` route, confirmed the Dashboard's new payment badge renders without error, and confirmed the publishable key is actually present in the compiled client bundle (checked by grepping the built chunks directly) rather than assuming an env var "probably" made it through — a `.env.local` file added while a dev server is already running does **not** take effect until that server restarts, which is exactly the kind of assumption worth checking rather than trusting. **Not verified: an actual browser rendering pass of the Payment Element itself** — the same standing environment gap as every phase this session (no Playwright/Chromium/Claude-in-Chrome here), so the visual Payment Element UI, the Apple Pay/Google Pay button rendering, and the on-screen card-entry flow were not seen rendered, only proven correct at the API/data-contract level end-to-end.

**Explicitly not built yet:** refunds (`paymentStatus: 'refunded'` exists as a value but nothing sets it — no refund action in the Dashboard yet), a customer-facing "retry payment" flow for an order whose PaymentIntent failed, payment/deposits for Booking appointments (Booking still doesn't take money at all), and per-business Stripe Connect accounts (Marketplace-tier, per §2.3/§3.9, not attempted).

**A real bug found from a live user report, after this phase had already shipped: the payment step silently vanished for cheap orders.** The user reported "не вижу виджета оплаты" (don't see the payment widget) — reproduced it directly: a ₽10 test order failed `createPaymentIntent` with Stripe's own error, *"Amount must convert to at least 50 cents. 10.00 р. converts to approximately \$0.12"* — Stripe enforces a hard minimum (~\$0.50 USD-equivalent) per charge, and this project's own graceful-degradation design (a Stripe failure should never block a real order — see "Backend flow" above) was silently absorbing this completely predictable, non-exceptional case exactly the same way it absorbs a genuine outage: order still created, `clientSecret` just quietly absent, customer left to wonder why there's no payment step at all. Not a regression in the original design's *intent* (degrading gracefully is correct), but a real gap in its *execution* (one failure reason was being treated identically to every other, with zero explanation surfaced anywhere).

**Fix: a provider-agnostic reason, not a Stripe-specific leak.** `StripeAdapter.createPaymentIntent` now catches Stripe's own `StripeInvalidRequestError` with `code === 'amount_too_small'` and rethrows a new `PaymentAmountTooLowError` — a provider-agnostic type living in `payments.types.ts`, so `OrdersService` can distinguish "amount too low" from "some other provider error" without importing anything Stripe-specific (preserving the exact abstraction boundary `PaymentProvider` was built to hold — see "Architecture" above). `OrderDto` gained `paymentUnavailableReason?: 'not_configured' | 'amount_too_low' | 'provider_error'`, set whenever `clientSecret` isn't — `'not_configured'` when the business simply hasn't connected Stripe (a business-level fact, not a per-order error), the other two split out from what used to be one silent catch-all.

**Frontend: shown, not hidden, per the user's own explicit ask for how to handle it** ("отобразить зависимые виджеты выключенными и тултип" — show the dependent widget as disabled with an explanatory note, not just make it vanish). `CartWidget` gained a `payment-unavailable` step — reached whenever `clientSecret` is absent — showing a visually disabled-looking payment block (dashed border, muted "Оплата картой недоступна" badge) with the specific reason spelled out (`PAYMENT_UNAVAILABLE_REASON_LABELS`, one message per reason) before letting the customer continue to the success screen. The order was already honestly created either way; this only changes whether the customer understands why there's no payment button, instead of it silently not being there.

**Verified against the real bug, not just the fix in isolation.** Re-ran the exact repro (a ₽10 product) against the restarted backend and confirmed `paymentUnavailableReason: 'amount_too_low'` now comes back instead of a bare missing `clientSecret`, confirmed a normally-priced product still returns a real `clientSecret` (the fix didn't regress the working path), and re-ran the full real-money Stripe verification script (`verify-stripe.mjs` — genuine PaymentIntent creation, `pm_card_visa` confirmation against Stripe's live test API, and the real webhook flipping `paymentStatus` to `paid`) end-to-end to confirm the happy path through the newly-wrapped `try/catch` is byte-for-byte unchanged. `npm run check` clean on both `backend/` and `frontend/`.

### Phase 7 (shipped) — Content v1: a real blog, and the first capability that actually needed its own URLs

**Why this one is architecturally different from Commerce/Booking, not just a third copy of the same pattern.** A product or a service is *transactional* — the whole interaction (view price, add to cart / book a slot) happens on the card itself, no separate page needed. A blog post is *read*, and nobody reads a whole article inside a grid card. That single difference is why Content needed something Commerce and Booking never did: a real, permalink-able detail page per entity (`/blog/my-post`) — which immediately runs into the exact gap flagged and deliberately left open all the way back in the Phase 1/2 write-up: `PageType.system` and a system-page dispatch registry (§3.2) were designed on paper but never implemented, because nothing existed yet that needed them. Content is that something. The choice made here: **don't build the generic system-page framework now either** — two entities needing their own URL scheme is not yet enough signal that the *generic* version is worth its complexity (the same "second real case proves the abstraction, don't build it on spec" reasoning already applied to `Business.capabilities` and the `dataSource` pattern before their first real capability existed). Instead: two hand-written, blog-specific Next.js routes. If a second capability shows up needing detail pages, *that's* the point to generalize — not before.

**Data model and naming, the one genuine landmine in this phase.** The obvious model name, `Post`, was already taken — the social feed's wall/timeline posts are `model Post` in the same schema, added long before this Website Builder work began. Reusing it (or worse, extending it) would have quietly coupled two completely unrelated product surfaces — a business's public blog and a user's private social feed — sharing one table, one Prisma Client accessor (`prisma.post`), and eventually one set of assumptions neither surface actually wants. Named it `BlogPost` instead, flagged the exact collision risk with an explicit comment on the model (so a future edit doesn't "helpfully" rename it back), and used `blog-posts` as the URL/module/upload-subdirectory name throughout the stack for the same reason. Otherwise narrow by the same discipline as `Product`/`Service`: no `Author` (a solo business owner writes as the business itself — `BlockBusinessContext` already carries the business's name/logo, no separate author identity needed today), no `Category`/`Tag`/`Comment` (real complexity — moderation, spam, threading — with no screen that would use any of it yet).

**The rich-text gap, found and deliberately not "fixed" under time pressure.** The mission's own plan for Content assumed the Website Builder already had a working TipTap-based `richtext` field ("no new editor needed"). Checked, and it doesn't: `control: 'richtext'` exists in `FieldSchema`'s type and in `FieldControl.tsx`'s switch statement, but renders as a plain `<textarea>`, and — more tellingly — no registered block anywhere in `entities/website/blocks` actually uses `control: 'richtext'`. It's a declared-but-dead code path, not a working feature. The *real* TipTap editor in this codebase (`features/publish-post/ui/PostEditor.tsx`) exists only for the social feed, and is deeply coupled to that feature's own image-upload placeholder scheme (`PostsService`-specific attachment syntax) — adapting it for blog posts under this session's time budget would have meant either duplicating real complexity or hastily cross-wiring two independent upload pipelines, neither of which serves quality. Chose the same level of polish the Builder's own (unused) `richtext` field already implied it was fine with: post bodies are plain text with a blank line between paragraphs, rendered with `white-space: pre-wrap` — the identical technique the Builder's `richtext`-labeled typography block already uses for its own long-text content. Documented this as a real, named gap (not silently downgraded), with the actual upgrade path (adapt `PostEditor`'s TipTap setup, on its own, later) written down rather than implied.

**Security surface, smaller than Commerce/Booking by construction, not by oversight.** There is no anonymous *write* endpoint for blog posts at all — a visitor can only ever read. That single fact removes the entire category of concern that dominated the Commerce/Booking backend work (price integrity, cross-tenant injection into an order/appointment, stock races) — `BlogPostsService` doesn't need any of `OrdersService`/`AppointmentsService`'s defensive machinery, because there's no untrusted input path to defend. Worth stating plainly rather than leaving as an unremarked accident of scope: this phase is genuinely simpler because the domain is simpler, not because less care went into it.

**Data-driven widget, extended cleanly.** `bloggrid` reuses the exact `control: 'dataSource'` mechanism built for `productgrid` and widened for `servicegrid` — `entity` grew from `'product' | 'service'` to include `'post'`, and `capability: 'content'` gates it in the Component Library the same way. One real, if minor, bug surfaced and fixed while wiring it: the shared `DataSourceField` inspector control had been hardcoding the word "товаров" and always offering price-based sort options regardless of which entity it was actually configuring — harmless when only `product`/`service` existed (both have prices, and "товаров" was merely mislabeled for `servicegrid`), but actively wrong for `post`, which has no price at all. Fixed by threading `field.entity` through to `DataSourceField` and having it pick the correct noun and hide the price-sort options when they don't apply, rather than special-casing `bloggrid` around a control that quietly assumed the shape of the first thing it was built for.

**A second real, load-bearing bug — this one in `ScrollArea`, not in any of this phase's own new code — caught by trying to actually use it in a new way, and fixed at the source.** Reused the shared `ScrollArea` component for the new blog pages, tried to apply the site's theme CSS variables via `<ScrollArea style={themeVars}>` (the natural way to pass a `style` prop to any component), and it silently did nothing. `ScrollArea`'s own implementation spread `{...rest}` (which includes any passed-in `style`) and *then* set its own `style={{ '--scroll-fade-top': ..., '--scroll-fade-bottom': ... }}` later in the same JSX element — in JSX, the attribute that appears later in the tree wins, so any caller-supplied `style` had always been silently discarded by this component, for every one of its existing call sites too. Checked via `grep` that of 21 total `<ScrollArea>` usages in the codebase, only the 3 new blog-widget call sites pass a `style` prop — zero regression risk — so fixed it at the source instead of working around it locally: the component's internal style object now spreads `...rest.style` first, before its own `--scroll-fade-*` variables. `BlogListWidget`/`BlogPostWidget` were then simplified to pass `style={themeVars}` directly to `ScrollArea` instead of an inner wrapper `<div>`.

**A false alarm worth naming so it isn't mistaken for a real bug later.** Immediately after the `ScrollArea` fix and a dev-server restart, every frontend route started 500ing with `Тип блока "productgrid" уже зарегистрирован` (`registerBlock` throwing its own duplicate-registration guard). This looked like a real regression but wasn't one: it was Turbopack dev-mode HMR re-evaluating the block-registration modules (each block file calls `registerBlock` at module scope as a side effect) against a `registry.ts` `Map` instance that had survived the reload from before, across several `next dev` restarts earlier in the session. A clean restart of the dev server made it disappear and every check re-passed cleanly — confirming it was dev-server/HMR state, not a code defect. No code change was needed or made for this one.

**Verified, not assumed.** A backend script covering: capability enable, published-vs-draft visibility split (owner sees both, anonymous sees only published, minimal public DTO shape), slug de-duplication, fetch-by-slug for a published post (200) vs. a draft post (404, same shape as a genuinely nonexistent slug — no leak of "it exists but isn't published"), publish-a-draft-via-update actually flipping public visibility, delete, and cross-owner isolation. A second end-to-end script drove the real path — enabled Content, created a post, placed a real `bloggrid` block via the same save/publish flow the Builder uses, and hit all of: the live `/site/{id}` home route (with the new block mounted), the dedicated `/site/{id}/blog` list route, the dedicated `/site/{id}/blog/{slug}` detail route, a nonexistent slug on that same route (confirmed it degrades to a client-rendered empty state rather than a hard error), the Dashboard route (new "Блог" tab), and the Builder route (new block + widened `dataSource` inspector) — all returned clean 200s with no Next.js error markers, re-confirmed after the `ScrollArea` fix and the HMR false alarm above. `npm run check` (lint + format + typecheck) is clean on both `backend/` and `frontend/`. **Not verified: an actual browser/visual rendering pass** — the same standing gap noted in every phase this session (no Playwright/Chromium/Claude-in-Chrome here), so the blog list grid's card layout, the reading page's typography, and the theme-variable application fix were verified by reading the code and its data flow, not by looking at rendered pixels.

**Explicitly not built yet:** the generic system-page dispatch framework (§3.2) that this phase's two hand-written routes deliberately substitute for — a real limitation of this approach is that a business cannot have a custom page whose slug is literally `blog`, since the dedicated route always wins; a proper fix requires either the generic framework or slug-reservation logic, neither built yet. Also deferred: `Author`/`Category`/`Tag`/`Comment` entities and a real WYSIWYG editor for post bodies (see above — a real, named gap, not a silent one).

### Phase 8 (shipped) — Restaurant: the concrete proof that it isn't a fifth capability

**Verified the thesis before writing any product code.** §2.2 already claimed "Restaurant isn't a fifth capability, it's Commerce + Booking with restaurant-flavored entities and templates on top" — before building anything, wrote a throwaway script enabling `commerce` **and** `booking` on one business simultaneously, creating a product ("dish") and a service ("table booking") on it, and placing both a `productgrid` and a `servicegrid` block on the same home page. Everything worked with zero code changes — no capability conflict, no block-registry collision, no Dashboard tab clash (Products and Services sections coexist independently). That result is the actual finding of this phase: the capability architecture built across Phases 5–7 already generalizes to two capabilities active on one business at once, which nothing before this had actually exercised.

**So what was actually missing?** Not entities — `Menu`/`Dish`/`Modifier` from the original §2.1 sketch would have been pure duplication of `Product`'s existing price/image/description shape for zero new behavior. The real, named gap was in §3.12: the pre-existing `restaurant` starter template (`entities/website/templates/restaurant.ts`, built before Commerce/Booking existed) rendered a "Меню" section as three hardcoded static cards (icon + title + description, no real price, no real data) — a placeholder that was honest when written, and stale now that real Product/Service data exists. Fixed the actual gap: `StarterTemplate` (`templates/index.ts`) gained optional `capabilities`/`seedProducts`/`seedServices` fields, the restaurant template declares `['commerce', 'booking']` plus two example dishes and one example table-booking service, and its static "Меню" block was replaced with a real `productgrid` (dishes) plus a new `servicegrid` section (table reservation) — both wired through the same `dataSource` mechanism every other capability already uses, not a restaurant-specific rendering path.

**Where the seeding actually happens.** `StarterTemplatePicker.tsx` (shown on first entry into the Builder for an empty site) previously only called `applyTemplate()` — a pure client-side store mutation, no backend call. Picking a template with `capabilities`/`seedProducts`/`seedServices` now also calls `updateBusiness` (merging capabilities, not overwriting — a business could theoretically already have some enabled) and `createProduct`/`createService` for each seed row, all through the same server actions the Dashboard's own "Включить" buttons already use — no new backend endpoint. A seeding failure (e.g. a flaky request) doesn't block the user: the block tree still applies, just with an empty catalog until the owner adds real items themselves, the same state a template without seed data has always left them in. Templates without `capabilities` (`agency`, `local-business`) are completely unaffected — the seeding branch only runs when a template declares seed data at all.

**One typing note worth flagging, not a workaround.** `StarterTemplate.capabilities` is typed as plain `string[]`, not `BusinessCapability[]` — `entities/website` cannot import types from `entities/business` (lateral same-layer FSD import, forbidden), the identical reason `BlockDefinition.capability` in `registry.ts` was already a bare `string`. The cast back to `BusinessCapability[]` happens only at the one call site that legitimately has both concepts in scope (`StarterTemplatePicker.tsx`, a widget) with the real validation enforced server-side by `@IsIn(BUSINESS_CAPABILITIES)`, same as every other capability-enabling path.

**Verified, not assumed.** A backend script simulating the picker's exact sequence (merge capabilities → create 2 products → create 1 service → apply the real block tree → publish) confirmed: the merge lands correctly, both seed products and the seed service persist, the public anonymous data-source endpoints (`/sites/{id}/products`, `/sites/{id}/services`) return exactly the seeded rows, and the resulting `/site/{id}` home route (now carrying a real `productgrid` + `servicegrid` side by side) and the Dashboard route both return clean 200s with no error overlay. Re-ran the full existing Commerce/Booking/Content E2E suites (`verify-commerce-e2e`, `verify-cart-e2e`, `verify-booking-e2e`) afterward — all still pass, confirming the template change didn't regress either capability on its own. `npm run check` clean on both `backend/` and `frontend/` (unchanged — this phase touched no backend code at all, by design). **Not verified:** an actual browser pass watching the picker's pending state (button disables, "Настраиваем…" label, error banner on a simulated failure) — same standing Playwright/Chromium gap as every prior phase.

**Explicitly not built:** `Modifier`/`Allergen` entities (no screen would use them yet — same "second real case proves the abstraction" discipline as `Category`/`Author`/`Tag` before), a computed table-availability engine (the seeded "table booking" is a `Service`/`Appointment` like any other — still a *request*, not an automated slot reservation, matching Booking's own honest scope from Phase 6), and extending the same `capabilities`/seed-data mechanism to the `agency`/`local-business` templates (nothing in either currently needs it — the mechanism is generic and ready when one does).

### Phase 9 (complete) — the first capability-independent capability, plus Media Library

**The gap was smaller than it looked.** §3.10 sketched Forms as needing a new `FormDefinition` table (a JSON schema of fields) plus `FormSubmission`. Turned out half of that already existed and the other half didn't need building: `entities/website/blocks/shared/FormBlock.tsx` and its three presets (`contactform`/`newsletterform`/`simpleform`) were already a real, working UI — validation, field config, success state — going back to an earlier phase, with one honestly-documented gap: submit was a no-op (`setSubmitted(true)` and nothing else, explicitly commented as "MVP without a real backend recipient"). So there was no `FormDefinition` to build at all — the field schema already lives where it belongs, in the block's own props inside the Website document (the Builder's `fields: FormFieldConfig[]` control). Adding a separate backend table to mirror that would have been the exact duplicated-source-of-truth mistake the project avoids everywhere else. The only real gap was `FormSubmission` (where a real answer needs to land) and the wiring between the two.

**No capability gate — the first one.** Every prior capability (Commerce/Booking/Content) gates its blocks and its Dashboard tab behind `Business.capabilities`. Forms don't: per §2.1 ("Forms — cross-cutting, not vertical-specific"), `contactform`/`newsletterform`/`simpleform` are already ungated in the Component Library, so a personal/portfolio site with zero capabilities enabled can still take a contact form. The backend model's doc comment calls this out explicitly (`FormSubmission` is "the only capability-independent entity in the project") precisely so a future reader doesn't assume it needs a capability check it was deliberately never given. `FormsSection` in the Dashboard follows the same logic — no "enable this" screen like `ProductsSection`/`ServicesSection`/`BlogSection` have, because there's nothing to enable.

**Snapshot, not a live reference — for a reason specific to this domain.** `FormSubmission` has no foreign key to the block that produced it, and this isn't an oversight: blocks live inside the `Website.draft`/`published` JSON document, not as separate rows with stable IDs a foreign key could target. So `formType` and `formLabel` (the block's heading at the moment of submission) are captured as a snapshot, the same reasoning `Order`/`Appointment` already apply to price/name — a later edit or deletion of the block in the Builder must not retroactively change what a past submission shows the owner.

**Security shape, worked out from first principles since this is a new kind of anonymous write.** Unlike `Order`/`Appointment`, there's no price or real-world commitment to protect — the only real risk is spam/abuse of a write endpoint with no auth at all (the third one in the project, alongside `createOrder`/`createAppointment`, all now cross-referenced in each other's comments). Two independent layers, deliberately not just one: (a) the same `@Throttle({ limit: 10, ttl: 60_000 })` as the other two anonymous writes, and (b) a honeypot field (`CreateFormSubmissionDto.honeypot`) — invisible to a real visitor (`FormBlock.module.scss`'s `.form__honeypot` clips it off-screen rather than `display:none`, since some bots specifically skip hidden-by-display-none fields; `aria-hidden` keeps it out of screen readers), and a fill triggers a **silent fake-success** (`204`, nothing persisted) rather than a rejection — telling a bot its submission failed just teaches it to find and clear the field next time. Since `data` is a free-form field→value map with no fixed schema (the whole point — the owner defines arbitrary fields in the Builder) `class-validator` can't bound it declaratively, so `FormSubmissionsService.assertValidData` does it by hand: reject over 20 fields or any value over 5000 characters, closing off the one attack a free-form JSON column actually invites (an anonymous caller trying to balloon the table with an oversized payload).

**Verified, not assumed.** A backend script covering: submitting anonymously with zero capabilities enabled (confirming the "no gate" design actually holds), a honeypot-filled submission returning the same `204` as a real one while not persisting, oversized `data` and an unrecognized `formType` both rejected with `400`, the owner's list reflecting exactly the real submission (not the dropped bot one) with the snapshot fields intact, a non-owner getting `403`, and delete actually removing the row. A second pass hit the real Next.js routes — the home route with a live `contactform` block, the Dashboard's new "Заявки" tab, and the Builder — all clean `200`s. Also re-ran the full existing regression suite (`verify-blog-e2e`, `verify-booking-e2e`, `verify-cart-e2e`, `verify-commerce-e2e`, `verify-restaurant-template-seed`) after this phase's dev-server restart — all still pass. `npm run check` clean on both `backend/` and `frontend/`.

**A second HMR false alarm, same as Phase 7's — noted so the pattern is recognized faster next time.** Immediately after wiring `FormBlock` and restarting the dev server, every route 500'd with `Тип блока "button" уже зарегистрирован` — the identical class of error as Phase 7's `productgrid` incident, this time for a block (`button`, in `blocks/actions`) this phase never touched. Same cause, same fix: Turbopack's dev-mode module registry surviving across a restart while block-registration side effects re-run; a full `next dev` restart (this time also clearing `.next`) resolved it, and everything re-verified clean afterward. Two occurrences now — worth remembering as "restart (and if that doesn't clear it, wipe `.next`) before assuming a `registerBlock` collision is a real regression," rather than re-diagnosing from scratch a third time.

**Media Library, built as a follow-up increment of the same phase.** §3.10's other half — a `MediaAsset` table + a "browse existing" tab on `ImageField` — was deliberately split into its own pass after Forms shipped (a new table, a new upload path, and an inspector-control UI change are independent surface from Forms; bundling them would have doubled one phase's review surface for two unrelated features), then completed once Forms was stable. Its shape ended up narrower than §3.10's sketch in one respect and wider in another:

- **Narrower on the data model.** No `width`/`height` columns, even though the ROADMAP sketch mentioned them: the upload path has no image-decoding step (no `sharp`/`image-size` dependency), and a thumbnail grid doesn't need dimensions ahead of time (`object-fit: cover` handles any aspect ratio) — adding that infrastructure for a field nothing would read yet is exactly the speculative work avoided everywhere else this session. `MediaAsset` is just `{id, businessId, url, mimeType, createdAt}`.
- **Wider on where it hooks in.** Rather than one upload path, it hooks into *four* — `WebsitesController.uploadAsset` (Builder block images), and `ProductsController`/`ServicesController`/`BlogPostsController`'s `uploadImage` (Dashboard entity photos) — via one shared `MediaAssetsService.record()` call added to each, so a product photo uploaded from the Dashboard shows up as a reusable option when picking a Hero background in the Builder, and vice versa. Deliberately excludes the business logo/favicon upload (`BusinessesController`'s `'businesses'` subdir): that's a single mutable field with a direct replace flow, not a history of past values anyone would want to browse back through — recording it would mean a "logo" showing up in a general image picker with no real use case attached.
- **`record()` never fails the actual upload.** Wrapped in try/catch, logs and swallows on error — the same graceful-degradation shape as `OrdersService`'s Stripe `PaymentIntent` creation: landing in the Library is a bonus on top of a successful upload, not a precondition for it. A visitor/owner should never see an upload fail because a bookkeeping insert into `media_assets` had a transient problem.
- **No delete, deliberately.** The Library is append-only in this increment — read and pick, not manage/prune. Building deletion (and deciding whether it should also delete the underlying file, which might still be referenced by a product's `images` array or a block's props with no reference-counting in place) is real work with no identified screen asking for it yet — the same "second real case proves the need" reasoning applied throughout.
- **One consumer, not a rewrite of every image field.** `MediaLibraryModal` (new) is used only by the Website Builder's `ImageField.tsx` — the one place "pick from a shared library instead of uploading again" is unambiguously useful, since a Builder block can legitimately want to reuse any business photo. The Dashboard's per-entity image fields (`ProductImageField`/`ServiceImageField`/`BlogPostImageField`) were left untouched: their job is uploading *this entity's own* photo, not browsing a shared pool, so adding a library tab there would be scope without a use case.

**Verified, not assumed (Media Library).** A backend script confirming: the library starts empty for a new business, a website-asset upload and a product-image upload both land in it (proving the shared `record()` hook works across different controllers/subdirs), the recorded `mimeType` is correct, a logo upload does *not* appear (confirming the deliberate exclusion), and a non-owner is rejected with `403`. Separately confirmed the real Builder and Dashboard routes still render `200` with the new modal/button wired in. Re-ran the full existing regression suite (blog/booking/cart/forms E2E) afterward — all still pass. `npm run check` clean on both `backend/` and `frontend/`.

### Phase 10 (complete — SEO and Analytics)

**Started with an audit, because §3.11's own note turned out to be stale.** The plan said `WebsitePage.seoTitle`/`seoDescription` "already exist" and just needed extending to `ogImage`. Checking found the DB columns were real but every layer above them was missing: not in `WebsitePageDto`, not read in `WebsitesService.assembleDocument`, not accepted in `validatePages` (so even sending them would have been silently dropped on save), not in the frontend `WebsitePage` type. `Business.seoTitle`/`seoDescription` were the opposite problem — fully wired through the CRUD API end to end, but *zero* UI anywhere ever set them, and `generateMetadata` never read them either. Worth stating plainly: this phase was as much "finish work that was silently half-done" as it was new feature work.

**Deliberately did not add `seoTitle` to `Product`/`Service`.** §3.11 sketched a `Product.seoTitle` override "falling back to name/description" — checked first, and there is no route anywhere that renders a Product or Service as its own addressable page with its own `generateMetadata`; both only ever appear as cards inside a `productgrid`/`servicegrid` block on someone else's page. An SEO override field with no `generateMetadata` call site that could ever read it would be pure dead weight — the exact shape of speculative work avoided everywhere else this session. `BlogPost` got the override instead, because it's the one entity in the project with a real, addressable detail route (`/site/[businessId]/blog/[postSlug]`) that already has its own `generateMetadata`.

**Three-level fallback chain, and an explicit choice about how overrides compose.** Title resolution is now `WebsitePage.seoTitle` (or `BlogPost.seoTitle` on the post route) → `WebsiteDocument.settings.seoTitle` → `Business.seoTitle` → `Business.name`, description the same shape one level shallower (no bare-name floor needed). The one deliberate design call: when a page/post *does* set its own `seoTitle`, it's used **verbatim**, not concatenated with the site name the way the un-overridden case still is (`"{page title} — {site title}"`). Reasoning: a site-wide default benefits from consistent branding suffix, but an owner who explicitly typed an SEO title into a dedicated field almost certainly wants exactly what they typed to appear in a search result, not that plus a suffix we appended on top of their own judgment.

**`openGraph` metadata added for the first time anywhere in the project.** Grepped before starting — zero hits for `openGraph`/`og:image` in the whole frontend. All three `generateMetadata` functions (`/site/[businessId]/[[...slug]]`, `/blog`, `/blog/[postSlug]`) now set it, with the same fallback shape as everything else: `WebsitePage.ogImage` (new column) → `BlogPost.coverImage` on the post route → `Business.logoUrl` → nothing. The shared resolution logic (site settings → business fallback) was pulled into one function, `resolveSiteMetadataDefaults` (`entities/website/lib/resolve-site-metadata.ts`) — not premature abstraction, since the exact same three-way priority order was about to appear byte-for-byte in three separate route files, a real duplication risk (the three files silently drifting out of sync on ordering), not three superficially-similar lines.

**Where the new page-level fields are actually edited.** No existing UI had anywhere to put a page-settings form (`PagesPanel.tsx` only ever supported inline rename), so this phase added one: a small gear icon per page opening `PageSeoModal` (title/description/`ImageField`-backed OG image), saving into the same client-side document state and debounced-autosave path as every other Builder edit — no separate API call. `Business.seoTitle`/`seoDescription` got a symmetric fix on the other end of the same gap: a new `BusinessSeoSection` in `/business/[id]/settings` (the domains-only settings screen, until now), wired directly to the `updateBusiness` endpoint that already existed and had simply never been called from anywhere.

**Verified, not assumed.** A backend-driven script exercising the full chain in both directions: business-level fallback observed in isolation (by explicitly clearing the site-level `settings.seoTitle`, since `createDefaultWebsiteDocument` seeds it with the business name at creation — a real, if easy-to-miss, wrinkle: the "lowest priority" tier is rarely visible in practice unless an owner deliberately blanks the site-level field); a page-level override rendering verbatim (not concatenated) with its own `ogImage` in the real HTML `<title>`/`og:image` tags; a `BlogPost` SEO override doing the same on the post route; clearing an override round-tripping to `null` (not an empty string) and correctly falling back again; and all touched routes (public site, Dashboard, Builder, Settings) returning clean `200`s. Re-ran the full regression suite from every prior phase afterward (blog/booking/cart/forms/media-library E2E) — all still pass. `npm run check` clean on both `backend/` and `frontend/`.

**Explicitly not built in the SEO pass:** SEO for Product/Service (see above — no real consumer yet), and a sitemap/`robots.txt` (not sketched in §3.11 at all, and no page currently needs one crawled distinctly enough to justify it before real traffic exists). The analytics half of this phase — §10's other half — was deliberately built as a separate follow-up increment rather than bundled into the same pass, the same reasoning that split Forms and Media Library in Phase 9 (a new model + emission calls at real action sites is independent surface from SEO). Written up below.

**Analytics: the event table + emission, built as its own increment of the same phase.** `AnalyticsEvent` — `{id, businessId, type, metadata?, createdAt}`, `type` a free string (`'page_view'`/`'order_created'`/`'appointment_created'`/`'form_submission'` today) rather than an enum, the same reasoning as `Business.capabilities` — a new event type shouldn't need a schema migration. `AnalyticsService.record()` is called from the four places in the codebase where a real visitor action actually happens: `PublicSitesController.getPublicSite` (page view), `OrdersService.createFromCart` (after the order/stock transaction commits), `AppointmentsService.createFromRequest`, and `FormSubmissionsService.createFromRequest` (only for genuine submissions — the honeypot-dropped path returns before `record()` is ever reached, so a bot filling the hidden field doesn't inflate the count either).

**The one placement decision that mattered: where `page_view` actually gets recorded.** `WebsitesService.getPublic()` is shared by two callers — `PublicSitesController.getPublicSite` (genuinely anonymous, real visitors) and `WebsitesController.getPublic` (`/businesses/:businessId/website/public`, requires login, used for the owner's own in-app preview). Putting the `record()` call inside the shared service method would have counted every time an owner previews or edits their own site as a "visit" — a real, easy-to-miss bug that would have quietly inflated every business's own view count from day one. Recording happens in the anonymous controller method instead, one layer up, specifically where the caller is known for certain to be a real visitor.

**Never blocks the real action, same shape as `MediaAssetsService.record`.** Wrapped in try/catch, logs and swallows — an order, appointment, or form submission must never fail because an analytics insert had a transient problem, and a page must never fail to render because of it either.

**No dashboard UI, on purpose — but not zero UI either.** §6 already commits to deferring "a full analytics dashboard UI" until real event volume exists to make one worth building. Left the read side genuinely minimal: one owner-only endpoint (`AnalyticsService.summary`, grouped counts for the last 7 days and all-time) and exactly one number surfaced anywhere — "Просмотров за 7 дней" as a third stat card in the Dashboard's existing Overview section, next to the two that were already there. This is deliberately the smallest possible real consumer: enough to prove `record()` → `summary()` actually works end to end and that the table isn't just accumulating unread rows, without building the charts/breakdowns/time-series that `§6` already says should wait.

**Verified, not assumed.** A backend script driving all four action sites for one business and confirming: the summary starts empty, two real anonymous page loads produce `page_view: 2`, a subsequent internal owner preview via the *other* `getPublic` endpoint does **not** increment it (the exact bug the placement decision above was designed to avoid), a real order/appointment/form submission each produce exactly one event of their type, a honeypot-filled form submission produces zero, and a non-owner is rejected with `403`. Separately confirmed the Dashboard Overview route renders the new stat card cleanly. Re-ran the full regression suite from every prior phase afterward — all pass (a batch of transient failures mid-verification turned out to be either backend rate-limiting from heavy back-to-back test traffic, or, in two cases, test scripts still pointed at a stale port from earlier in the session rather than the current dev server — not real regressions, confirmed by re-running against the correct target). `npm run check` clean on both `backend/` and `frontend/`.

**Explicitly not built:** per-event-type breakdowns, time-series/graphs, or a dedicated Analytics tab — all covered by §6's existing deferral. Also no `path`/referrer capture on `page_view` beyond the bare event (the `metadata` column exists and is used for `order_created`/`appointment_created`'s ID, but `page_view` carries none yet) — nothing downstream reads a page path today, and the catch-all route doesn't cleanly expose one at the point `getPublicSite` is called without deeper plumbing that has no consumer yet.

### Phase 11 (narrowed — card border/shadow tokens shipped, the rest deliberately deferred)

**Audited the actual gap before touching anything, and found it smaller than §3.5's own description.** The section names two pieces: a bigger theme token set (spacing scale, shadows, borders, breakpoints) and extending the existing per-property responsive override machinery (`ResponsiveValue<T>`, `resolveResponsive()`) to more of `BlockStyle`'s fields, gated behind a "Basic/Advanced" inspector split. Checking first: a spacing *scale* already exists (`SPACING_PX`, four sizes, already used by every `BlockStyle` padding/margin field) — nothing to add there. A customizable *breakpoint* token would mean letting an owner redefine what counts as "mobile" per business — checked for any real demand signal for this and found none; it would only add a structural knob nobody in a comparable site builder exposes as a per-site setting, so it was cut rather than built speculatively. That leaves shadows and borders as the one real gap — and even there, checking `blocks/shared/primitives.module.scss` and `blocks/business/business.module.scss` found `box-shadow` used **nowhere** in any block today, while `border: 1px solid var(--site-border)` was hardcoded independently in six separate card-shaped classes (`.icon-card`, `.people-card`, `.simple-card`, `.service-card`, `.pricing-plan`, `.team-member`) — a real, concrete duplication, not a hypothetical one.

**Shipped: `ThemeCardBorder`/`ThemeCardShadow`, two new theme tokens wired into exactly the surfaces that needed them.** `WebsiteTheme.cardBorder: 'none'|'hairline'|'bold'` and `.cardShadow: 'none'|'sm'|'md'`, flowing through `buildThemeCssVars()` into two new CSS vars (`--site-card-border-width`, `--site-card-shadow`) the same way every existing theme token already does — no new mechanism, exactly as §3.5 predicted. All six card classes above now read `border: var(--site-card-border-width) solid var(--site-border)` and `box-shadow: var(--site-card-shadow)` instead of a hardcoded `1px`/nothing. A new "Карточки" section in `ThemePanel.tsx` exposes both as `select` fields, using the exact same `FieldGroup` pattern every other theme section already uses.

**Both fields are optional on the type, not required — a deliberate, precedented choice.** `cardBorder`/`cardShadow` were added to `WebsiteTheme` after real businesses' theme JSON already existed without them, the identical situation `WebsiteSettings.seoTitle`/`seoDescription` were in during Phase 10 — and given the same fix: optional fields, with `buildThemeCssVars()` falling back to `'hairline'`/`'none'` (exactly the old hardcoded look) when absent, so no already-published site's cards silently change appearance the moment this shipped.

**Deliberately NOT built: the Basic/Advanced inspector split and responsive `BlockStyle` overrides.** Checked the actual infrastructure before deciding: `ResponsiveValue<T>`/`resolveResponsive()`/`readResponsiveProp`/`writeResponsiveProp` are real and already proven — but exercised by exactly one field in the whole codebase (the Heading block's `size`), never by any `BlockStyle` field. Retyping `paddingY`/`paddingX`/`marginTop`/`marginBottom` from plain `SpacingSize` to `ResponsiveValue<SpacingSize>` is a real, if backward-compatible, type change (the read helper already treats a legacy flat value as "same on every viewport," so it wouldn't break old documents) — but it also means threading the canvas's active viewport into `computeBlockWrapperStyle` (which doesn't take one today) and touching every call site. That's a self-contained, non-trivial increment on its own, not a natural extension of the card-token work above, and bundling it in would have meant shipping a half-verified change to core block rendering alongside an unrelated, already-complete theme feature. Deferred to its own future increment rather than rushed — the same "don't double a phase's surface for two unrelated pieces" reasoning already applied to Forms/Media Library (Phase 9) and SEO/Analytics (Phase 10). The "Basic/Advanced" split has no reason to exist until that responsive work actually lands and the panel has enough new fields to warrant hiding some by default — building the grouping mechanism first, with nothing yet to group, would be exactly the speculative-infrastructure trap avoided everywhere else this session.

**Verified, not assumed — with one real limitation stated plainly.** A backend script confirmed: a new business's theme defaults to `cardBorder: 'hairline'`/`cardShadow: 'none'` (matching the pre-existing hardcoded look exactly), changing the theme persists both fields correctly through save/publish, and a *simulated old-shape document* (fields stripped out entirely, not just left at defaults) still round-trips and renders every touched route with a clean `200` — proving the optional-field/fallback design doesn't crash on genuinely old data. What this pass could **not** verify: the actual computed CSS variable values in a rendered page, because `/site/[businessId]` is a fully client-rendered widget (`useAsyncData` inside a `'use client'` tree) — a plain `fetch()` only ever sees the pre-hydration shell, never the post-hydration inline styles, so grepping raw HTTP responses for `--site-card-*` cannot work here (this was tried, confirmed empty, and removed from the verification script rather than left as a misleading always-fails-safely check). This is the same standing gap named in every UI-facing phase this session: no Playwright/Chromium/Claude-in-Chrome available, so the actual pixels — does `none` really remove the border, does `md` really look like a shadow — are unverified by tooling, only by reading the CSS and trusting the token maps (which are simple, direct lookups, reviewed by hand). `npm run check` clean on both `backend/` and `frontend/`; the full regression suite from every prior phase re-run and passing.

**Explicitly not built:** breakpoint tokens (see above — no real demand found), the Basic/Advanced split, and responsive overrides for `BlockStyle` fields (both deferred to their own future increment, not abandoned).

### Phase 16 (complete) — Currency System

**A user-specified task, not originally in this roadmap** — a full spec arrived mid-session asking for a proper Currency System (Business-level currency, Stripe-compatible codes, a `Money` abstraction, minor-unit-correct storage, Builder/Dashboard/Cart/Checkout/Stripe consistency) plus, separately, a full Pricing/Discounts/Coupons/Tax Engine. Both are treated below; the second is explicitly **not** attempted this pass (see the closing note).

**Audited first, three parallel research passes (Product/Service storage, Cart/Order/Stripe, Business/Settings/Dashboard), before writing a line of code.** The actual state turned out better than expected in one specific way: `Product`/`Service` already had their own `currency String @default("RUB")` column, but it was **never actually settable** through any DTO — every row in the entire system was already, silently, exactly `"RUB"`. That fact drove the whole migration strategy: there was no real multi-currency data anywhere to reconcile, so adding `Business.currency @default("RUB")` and dropping the two unused columns is a zero-data-loss, zero-behavior-change migration for every existing business. The audit also confirmed two concrete, pre-existing bugs worth naming precisely: `formatPrice` (`entities/product/model/format-price.ts`) hardcoded `priceCents / 100` for every currency — silently wrong for zero-decimal currencies like `JPY` — and `StripeAdapter.createPaymentIntent` passed `amountCents` straight through with the same unstated 2-decimal assumption. Neither had ever been exercised by a non-2-decimal currency, so neither had ever visibly failed.

**Central design call: `Product`/`Service` have NO currency field at all — not even a "set once, frozen" one.** The obvious naive fix (keep the column, just make it settable, copy `Business.currency` in at creation time) was rejected on inspection: it would silently reproduce the exact failure mode the task's own spec calls out by name — "Product A → USD, Product B → EUR" by accident of creation order, not by anyone's decision, the moment a business changed its currency after its first few products existed. Instead, `Product`/`Service` read currency by joining `Business.currency` at request time in `ProductsService`/`ServicesService` (`toDto`/`toPublicDto` now take `currency` as a parameter, not a column read) — structurally impossible for two products of the same business to disagree on currency, because there's no per-row value that could drift. `Order`/`Appointment` are the deliberate exception: they keep their own `currency` column, because they're not live catalog data — they're an immutable financial record of what currency a real transaction actually happened in, and must not silently change if the business later switches currencies (verified explicitly, see below).

**Money math lives in exactly one place per side, both newly built.** Backend: `modules/currencies/currencies.ts` — a curated (not exhaustively-135-currencies) `SUPPORTED_CURRENCIES` list with `{code, name, symbol, minorUnit}`, deliberately including at least one zero-decimal currency (`JPY`, plus `KRW`) so that code path is actually exercised, not just theoretically supported. Frontend: the identical list duplicated in `shared/config/currencies.ts` (same cross-project duplication convention as every other shared constant in this codebase, per `AGENTS.md`) plus `shared/lib/format-money.ts` — `formatMoney`/`toMinorUnits`/`fromMinorUnits`, the only functions in the project allowed to do currency arithmetic. `entities/product/model/format-price.ts` was deleted outright (not kept as a thin wrapper) and every call site (`ProductCard`, `ServiceCard`, `CartWidget`, `OrdersSection`, `AppointmentsSection`, `ProductsSection`, `ServicesSection`, `BookingModal`) now imports `formatMoney` directly — one source of truth, not a chain of wrappers.

**A real, checked-not-assumed bug found while writing the test suite: `Intl` cannot be trusted to pick the currency symbol.** Initial `formatMoney` used `Intl.NumberFormat('ru-RU', {style: 'currency', currency, currencyDisplay: 'symbol'})`, expecting `Intl` to always know the right symbol. Running the actual unit tests (not just reasoning about it) surfaced that `Intl.NumberFormat('ru-RU', {..., currency: 'PLN'})` returns `"1 299,99 PLN"` — the bare ISO code, not `"zł"` — because the `ru-RU` locale's CLDR data has no localized PLN symbol mapping, and `Intl` silently falls back to the code instead of throwing. Fixed by never letting `Intl` choose the symbol at all: `formatMoney` now uses `Intl.NumberFormat` in `style: 'decimal'` mode purely for correct grouping/decimal-separator behavior, then appends `CurrencyMetadata.symbol` manually — guaranteeing the symbol shown always matches the one curated in `SUPPORTED_CURRENCIES` (and shown in the currency picker), regardless of which locale's CLDR data happens to know which currency. This is exactly the kind of bug that "looks right" until a specific currency is actually tested — recorded here because it would have been very easy to ship un-caught, and because it changes the reasoning in `formatMoney`'s own doc comment (an earlier version of that comment explicitly justified trusting `Intl` for the symbol — now corrected in place, not left stale).

**Stripe integration needed almost no changes — because the fix belongs at the entry point, not the API boundary.** Grepped `payments/`/`orders/` before assuming `StripeAdapter` needed currency-aware amount conversion: zero `*100`/`/100` occurrences existed there. `StripeAdapter.createPaymentIntent` already just forwards `amountCents` unchanged, exactly matching what Stripe's API itself expects (a whole-number minor-unit amount, whatever that means for the given currency — see Stripe's own docs, fetched and checked live rather than assumed: zero-decimal currencies like `JPY` are charged as `amount: 500` meaning "500 yen," no multiplication). The one thing genuinely missing was defense-in-depth: a new `PaymentUnsupportedCurrencyError`, checked in `StripeAdapter` before ever calling Stripe, mapped into the existing `OrderDto.paymentUnavailableReason` machinery (the same mechanism built earlier this session for the "amount too low" bug) as `'provider_error'` — not because a real path to this error exists today (the architecture now makes a currency mismatch structurally impossible), but as the explicit "Stripe mismatch protection" the task's own spec asked for, should that invariant ever break in the future.

**Currency selection and change, with the required non-conversion warning.** `CreateBusinessForm` gained a required currency `<select>` (using the exact "US Dollar (USD) — $" label format the spec asked for, `CURRENCY_OPTIONS`), defaulting to `RUB` for continuity but always sending an explicit choice. A new `BusinessCurrencySection` in Business Settings is the *only* place `Business.currency` can be changed after creation — selecting a new value doesn't save immediately; it opens a confirmation modal (reusing the same `Modal`-based pattern already established for destructive domain deletion) spelling out exactly what does and doesn't happen: existing product/service prices keep their same *number* and simply render in the new currency's symbol (no conversion), while historical `Order`/`Appointment` rows are unaffected. `ProductFormModal`/`ServiceFormModal` now show the actual currency symbol and code next to "Цена" (previously hardcoded "Цена, ₽" regardless of the business's real setup) and convert entered text through `toMinorUnits`/`fromMinorUnits` instead of the old unconditional `/100`/`*100`.

**A real testing gap closed, deliberately narrow.** No test runner existed in this project before this phase (checked `package.json` — no `jest`/`vitest`, no `test` script). Added a minimal `vitest` setup — not because every future feature should get unit tests (this project's standing practice, and a deliberate choice reaffirmed here, is live E2E scripts against the real backend for anything touching a database or API), but because `formatMoney`/`toMinorUnits`/`fromMinorUnits` are the one piece of this whole phase that's pure, currency-math logic with zero I/O — exactly the shape unit tests are actually good at, and exactly where a silent precision bug (like the `Intl` symbol issue above, or the original `JPY`-divides-by-100 bug) is cheapest to catch this way. `npm run test` (`vitest run`) is now part of `npm run check`'s gate going forward, not a one-off script left to rot.

**Verified, not assumed — the full USD/EUR/JPY scenario the task's own spec asked for, plus the historical-snapshot case.** A backend script running the complete create→product→service→order→appointment→dashboard→currency-change flow for `USD`, `EUR`, and `JPY` (deliberately including one zero-decimal currency, not just two 2-decimal ones), confirming at every step: the entered price round-trips through storage as the exact correct minor-unit integer for that currency's precision (no drift), `Product`/`Service`/public-listing/`Order`/`Appointment` all report the same currency as the business, and — the case that actually exercises the "why not just copy currency onto Product" design decision — changing the business's currency *after* creating a product/order leaves the historical `Order`/`Appointment` currency exactly as it was, while the still-live `Product` immediately reflects the new currency. A separate check confirmed a real `PaymentIntent` created in `JPY` against Stripe's actual test API succeeds and returns a genuine `clientSecret` — proving the zero-decimal amount reaches Stripe correctly, not just that the local math looks right. Re-ran the full regression suite from every prior phase (Commerce/Booking/Restaurant-template E2E) afterward — all still pass. `npm run check` clean on both `backend/` and `frontend/`, including the new unit test suite.

**Explicitly not built:** the Basic/Advanced currency-precision configuration UI for currencies beyond the curated 14 (adding one is a one-line change to `SUPPORTED_CURRENCIES` on both sides, not a missing feature); a "browse historical exchange rates" or automatic price-conversion tool for the currency-change warning (the task explicitly asks for a clear warning instead of silent/automatic conversion, which is what was built); and currency support for the free-text "Тарифы" (`pricing`) block, which has no live `Product`/`Service` binding at all and isn't seeded by any current template — documented in place in `blocks/business/index.tsx` rather than silently left unremarked.

**The Pricing/Discounts/Coupons/Tax Engine requested alongside this was deliberately deferred to its own increment (Phase 17)** rather than attempted in the same pass — see `### Phase 17` below for what was actually built, and why its scope was narrowed relative to the original 69-section spec.

### Phase 17 (complete) — Pricing/Discounts/Coupons/Tax Engine

**A user-specified task** — the second half of the "Currency System + Pricing" request that arrived mid-session (see Phase 16 above), asking for a full rule-based discount system (percentage/fixed/product/category/order-level, stacking and priority rules), coupon codes with usage limits and expiration, a tax engine (inclusive/exclusive modes, multiple rates, regions, deterministic rounding), and a unifying Pricing Engine that Cart/Checkout/Stripe/Order/Builder would all defer to. Per the user's own explicit sequencing instruction ("Сначала создай PRICING_ARCHITECTURE.md... После этого проверь архитектуру на edge cases. И только потом начинай реализацию"), a full architecture document — [`PRICING_ARCHITECTURE.md`](./PRICING_ARCHITECTURE.md) — was written and reviewed against edge cases (§7 of that document) *before* any implementation began.

**Scope was deliberately narrowed relative to the original spec, and the document says why for each cut.** The full spec's per-product/category/collection discounts, customer-segment discounts, multi-region/multi-rate tax, and shipping-cost calculation were all left out — not from oversight, but because each one requires an entity or a piece of checkout UI that doesn't exist anywhere in this app today (no `Category` on `Product`, no `Customer` account — checkout is anonymous by design, no address field anywhere in checkout at all). Building any of those now would be the same speculative-infrastructure trap this entire roadmap has avoided everywhere else (`ProductVariant`/`Category`/`Review` never built for the same reason). What *was* built is a complete, coherent MVP: order-level discounts, either automatic or code-gated; a single flat tax rate per business; and one unified pricing calculation used identically by the coupon-preview endpoint and real order creation, so a discount shown to the customer can never diverge from what's actually charged.

**One entity instead of the spec's suggested two.** The spec asked to split "Discount" (the rule) from "Coupon" (the code that activates it), reasoning that a rule could exist with zero or several codes. Since the only discount scope built here is "the whole order" (no per-product/category dimension), a rule and its at-most-one code collapse cleanly into a single `Discount` row: `code: null` means automatic (applied to every qualifying order without the customer entering anything), a non-null `code` means it requires that exact text at checkout. Documented in `PRICING_ARCHITECTURE.md` §2 as a deliberate simplification, not a misreading of the spec — the shape still extends to a real many-to-many `Coupon` table later without migrating existing data, if that ever becomes a real requirement.

**The Pricing Engine — one function, every caller.** `backend/src/modules/pricing/pricing.ts` exports `calculateOrderPricing` (pure, no DB/DI — same shape as `currencies.ts`): subtotal → discount (clamped so it never exceeds the subtotal) → tax on the post-discount amount (the standard convention — a percentage discount should reduce what gets taxed, not just shrink an already-taxed total) → total. `OrdersService.createFromCart` (the sole order-creation path) and the new coupon-preview endpoint both call this exact function with the exact same inputs — nothing resembling the anti-pattern the original spec explicitly warned against (separate `calculateCart`/`calculateCheckout`/`calculateOrder` implementations that could silently drift apart). A second pure function, `checkDiscountEligibility`, is the single place dates/usage-limit/minimum-order-amount are checked, called by both the preview and the real order path for the same reason.

**Automatic discounts, coupon codes, and their interaction — a real gap caught by the E2E script, not assumed correct.** The first implementation only wired up code-gated discounts (`dto.couponCode` → `findByCode`); the E2E script below caught that an automatic (`code: null`) discount created via the Dashboard was never actually being applied to a plain checkout — `resolveBestAutomaticDiscount` was added to close that gap: when no code is entered, every active automatic discount for the business is checked for eligibility, and if more than one qualifies, the one yielding the larger `discountCents` wins (a deterministic tie-break, not an arbitrary "first match"). An explicitly entered coupon code always wins over any automatic discount — a customer who typed a code expects that specific offer, not a surprise stack of two.

**Tax — one flat rate per business, not a table.** `Business` gained `taxRateBps` (basis points — `2000` = 20.00%, an integer for the same float-avoidance reason as money) and `taxMode` (`none`/`inclusive`/`exclusive`, defaulting to `none` so every existing business is unaffected by the migration). Set from a new "Налог" sub-section in `BusinessCurrencySection` (Business Settings) — saved immediately via its own button, unlike the currency `<select>` above it, because changing the tax rate doesn't rewrite historical orders (each `Order` snapshots its own `taxCents` at creation, exactly like it already snapshots `currency`) — there's nothing irreversible to warn about.

**Order pricing snapshot.** `Order` gained `subtotalCents`/`discountCents`/`discountName`/`couponCode`/`taxCents` alongside the pre-existing `totalCents` — all filled once at creation from the Pricing Engine's result and never recomputed, so a later edit to a `Discount`'s value, a business's tax rate, or even deleting the `Discount` entirely leaves every past order's receipt exactly as the customer actually paid it (verified directly: changing a business's `taxMode` back to `none` after orders exist leaves their stored `taxCents`/`totalCents` untouched). The Dashboard's "Заказы" list and the customer-facing cart both show the same subtotal/discount/tax/total breakdown, sourced from the same `OrderDto` fields — no separate display-side recomputation.

**A new Dashboard section and a cart-side coupon field, both gated the same way as Commerce.** "Скидки" is a new capability-gated Dashboard tab (same `commerce` gate as "Товары" — Booking has no pricing engine in this phase, see the deferral list) for creating/editing/deleting discounts, showing usage count against any configured limit. `CartWidget` gained a promo-code input that calls the new `POST /sites/:businessId/coupons/preview` endpoint for instant "Применён ✓ / Промокод не найден" feedback before the customer commits to checkout — a preview only, never trusted for the real charge: `createOrder` re-validates the code from scratch against the server-computed subtotal, and the payment/payment-unavailable screens display the real returned `Order.totalCents`, not the client's pre-discount cart total.

**Verified, not assumed — a dedicated E2E script covering the harder edge cases, not just the happy path.** 30 checks against the real running backend: plain order with exclusive tax; an automatic discount actually applying without a code; a coupon-gated discount with a minimum order amount and a usage limit of 1 (confirming the *second* attempt to use it is rejected with the whole order failing, not silently charged without the discount); case-insensitive code matching; an oversized fixed discount clamping to the subtotal without going negative and correctly charging zero tax on a fully-discounted order; an unknown coupon code rejecting the whole order; the owner Dashboard showing the identical breakdown the anonymous checkout response returned; and the historical-snapshot guarantee (changing `taxMode` after orders exist leaves their stored breakdown unchanged). Re-ran the pre-existing `verify-orders`/`verify-cart-e2e`/`verify-currency-system`/`verify-commerce-e2e` regression scripts afterward — all still pass (the schema changes to `Order` are additive with safe defaults, and the migration backfills `subtotalCents` for pre-existing rows from their existing `totalCents` rather than leaving it at the column default of `0`). Also added a `pricing.test.ts` Vitest suite (15 cases) for the pure `calculateOrderPricing`/`checkDiscountEligibility` functions — the same "unit tests only for pure, I/O-free logic" carve-out established for `formatMoney` in Phase 16, now applied on the backend for the first time (`backend/vitest.config.mts`, `npm run test` added to `backend`'s `npm run check` gate). While setting this up, found and fixed a real, pre-existing gap: `tsconfig.build.json` had no exclusion for test files at all (unlike the Nest CLI default, which excludes `*.spec.ts`), so the container's `tsc -w` dev-build was failing on `pricing.test.ts` importing `vitest` types until `src/**/*.test.ts` was added to its `exclude`.

**Explicitly and deliberately NOT built — named here per the same discipline as every other phase's cuts (see `PRICING_ARCHITECTURE.md` §8 for the full reasoning on each):** per-product/category/collection-specific discounts (no `Category` entity on `Product` to scope them against); customer-segment or first-order discounts (checkout is anonymous — there is no `Customer` identity to segment); discount stacking beyond the single deterministic automatic-vs-coupon tie-break above (moot while only one discount scope and at most one discount per order exist at all); multi-region/multi-rate tax and tax-exempt products (no address field anywhere in checkout to key a region off of); and shipping-cost calculation (no shipping address or method selection exists in the current checkout form for a shipping cost to attach to). Each is additive once its prerequisite entity or UI is eventually built, not a reshape of what exists now.

### Phase 13 (ongoing) — Testing pass, extended to Discounts/Coupons/Tax this increment

Phase 13 is cross-cutting by design (§5: "run incrementally per-phase, not saved for the end") — each capability gets its own crash-testing pass as it lands, not one giant sweep at the end. This increment extended that matrix to Phase 17 (the newest, least-tested surface at the time), rather than re-sweeping every older capability.

**A dedicated crash-testing script (`verify-discounts-crash.mjs`, 26 checks), separate from Phase 17's own correctness script (`verify-pricing-engine.mjs`)** — deliberately split: the pricing script proves the *math* is right (discount → tax → total), this one proves the *API surface* rejects what it should. Covered: malformed input on every `CreateDiscountDto` field (missing name, over-length name, too-short/invalid-character codes, an unknown `type`, zero/negative `value`, negative `minOrderAmountCents`, an unparseable `startsAt`, `usageLimit: 0`); duplicate codes on create and on update (case-insensitively — `dupetest` collides with `DUPETEST`); clearing a discount's code back to `null` (automatic) via an explicit update; nonexistent discount/business ids (404, not a crash); full cross-owner isolation (list/create/update/delete all rejected 403 for a business the caller doesn't own — the same `assertOwnership` pattern already proven for `Product`/`Service`, now proven for `Discount` specifically rather than assumed to work by analogy); coupon-preview edge cases (negative `subtotalCents`, empty code, and confirming whitespace/case are both normalized before lookup); and cascade delete (removing a `Business` removes its `Discount` rows — a coupon preview against the deleted business's old code returns a clean `not_found`, not a 500).

**A real, confirmed gap found and fixed by writing this script, not by inspection alone.** `CreateDiscountDto.value` only enforced an absolute ceiling (`@Max(1_000_000_000)`, sized for `fixed`-type minor-unit amounts) — nothing stopped a `percentage`-type discount from being created with `value: 500`. It wasn't exploitable (`calculateOrderPricing` already clamps `discountCents` to the subtotal, so the actual charge was always safe), but the stored, displayed value would have been a nonsensical "500%" discount sitting in the Dashboard's discount list — exactly the kind of DTO-shape-is-fine-but-business-rule-is-missing gap this crash-testing pass exists to catch. Fixed with `DiscountsService.assertPercentageBound`, called from both `create` and `update` (the `update` case is the more interesting one: it validates the *resulting* `type`/`value` pair, falling back to the existing stored value when only one of the two fields is being changed in a given `PATCH`) — a service-layer check, not a class-validator decorator, because it depends on another field of the same DTO, the same reasoning already applied to this service's code-uniqueness check. Re-ran `verify-pricing-engine.mjs` and both projects' `npm run check` afterward to confirm the fix didn't regress the correctness script or the gates.

**A second, previously-missing gap closed in the same increment: Phase 17's own frontend had only ever been typechecked/linted, never hit through a live server.** Every other capability's rollout this session ends with a `verify-*-e2e.mjs` script hitting the real Next.js routes and checking for a 200 plus the absence of an error-overlay marker (see `verify-forms-e2e.mjs`'s step 8, for one example) — Phase 17's original verification script (`verify-pricing-engine.mjs`) never did this, only the backend API. A new `verify-pricing-frontend-smoke.mjs` closes that: against the already-running dev server on port 3000 (found already up, presumably the user's own session — used read-only rather than started a second instance), it creates a business with an automatic discount, a coupon, exclusive tax, and a published `productgrid` page, then confirms four routes all return 200 with no `__next_error__`/"Internal Server Error"/"Unhandled Runtime Error" marker: the public site (mounts `CartWidget`, including its new coupon field), the Dashboard (mounts the new "Скидки" tab — `DiscountsSection`/`DiscountFormModal`), Business Settings (mounts the new "Налог" sub-section in `BusinessCurrencySection`), and the Builder (unaffected, checked for a regression anyway). All four passed clean on first run — no compile-time or first-render errors in any of the new UI, closing the "typechecks but was never actually loaded" gap this same discipline has already caught real bugs through elsewhere in this project (e.g. the Turbopack HMR false-alarms earlier in this session were only ever visible by actually running the dev server).

**Not yet re-swept this pass (still open under Phase 13):** Commerce/Booking/Content/Forms/Media Library/SEO/Analytics/Currency — all shipped with their own QA pass at the time (see their own §8 write-ups), but haven't been re-run against this same crash-testing checklist (malformed input / cross-owner isolation / cascade-delete / boundary values) as a dedicated, later pass. The rest of Phase 13's older capabilities remain open.

### Phase 14 (first measurement) — Performance pass on the Products catalog

§5 explicitly calls for "measure first" rather than assuming a scale problem exists — this is the first actual measurement taken against this codebase, on `Product` (Commerce), the capability with the most obviously catalog-shaped growth. Seeded directly via SQL against the running Postgres container (bypassing the anonymous-write throttler entirely, which exists specifically to rate-limit HTTP requests, not raw inserts) — 200 rows, then 800 more to reach 1000, under one business.

**Backend list queries scale linearly, comfortably, well past any realistic MVP catalog size.** `GET /businesses/:id/products` (owner, all rows) and `GET /sites/:id/products` (public, active-only): at 200 rows, 5-13ms and 32-64KB; at 1000 rows, 14-23ms and 165-322KB — consistent linear growth with `businessId` (indexed), no N+1 pattern, no quadratic blowup. Cascade-deleting a business with 1000 products (removing all of them via the FK's `onDelete: Cascade`) completed in 19ms. None of this is surprising for a straightforward indexed `findMany`, but it was measured, not assumed — the roadmap's own standard.

**A real, existing design decision confirmed sound under measurement, not a new fix:** the `productgrid` Builder block (`ProductGridRenderer`, `entities/website/blocks/commerce/index.tsx`) already caps how many product cards actually render on the public page — `dataSource.limit` is UI-capped at 24 (`DataSourceField.tsx`, `max={24}` on the number input) regardless of total catalog size, so a business with 1000 products never renders an unbounded single page. Confirmed this is a real, load-bearing constraint, not just a UI hint: `ProductGridRenderer` does `sortProducts(data, sort).slice(0, props.dataSource.limit)` after fetching, so raising the ceiling would require a code change here too, not just moving an HTML `max` attribute.

**A real, bounded scaling ceiling identified (not fixed — flagged, per this document's own "measure, then decide if it's worth fixing" standard):** the block above still fetches the *entire* active product list (`getPublicProducts`) to sort and slice client-side down to the visible 24 — payload size for that one block scales with total catalog size, not with how many cards are actually shown. At 1000 products this is 165KB and 14ms, still negligible; it would become a real problem only at a scale (many thousands of products) nothing in this app targets today. Not fixed this pass — the fix (a `limit`/`sort` query param on the public products endpoint, doing the slicing in the database instead of after the fetch) is a small, clearly-scoped follow-up whenever a real catalog approaches that size, not urgent today.

**Explicitly not measured — the actual gap that matters most and that this session cannot close:** real browser paint/reconciliation time for the Dashboard's "Товары" list (`ProductsSection`) rendering 1000 plain `<li>` rows with no virtualization, or of `ProductGridRenderer`'s up-to-24 cards. The code itself has no algorithmic red flag (a single `.map()`, O(1) work per row, no nested loops) but "no obvious algorithmic problem in the source" is not the same claim as "renders acceptably in a real browser at N=1000" — that requires an actual browser, which remains the standing environment gap for this entire session (no Playwright/Chromium access). `Service`/`BlogPost` catalogs weren't separately measured either — both share the identical list-rendering shape as `Product` (confirmed by `ServicesSection`'s own comment reusing `ProductsSection.module.scss` because "разметка списка идентична"), so the backend-query conclusion above almost certainly transfers, but wasn't independently re-measured.

### Critical fix — real customer-facing checkout crash, caught live by the user

While the above was in progress, the user reported a real crash via a screenshot: attempting to place a real order on their own live "I luve Coffee" business (Restaurant template, `UAH`, 20% exclusive tax — real production data, not a test fixture) showed **"Minified React error #441"** instead of a real error message, right where the checkout form's validation error normally renders.

**Root cause, found by direct reproduction against the real business, not guessed from the screenshot alone:** the backend correctly rejected the order with 400 `"Некорректный номер телефона"` — the customer had typed their phone in plain local format (`380958887722`), and `CreateOrderDto.customerPhone` used `@IsPhoneNumber(undefined)`, which requires strict E.164 formatting with a `+` country-code prefix to even attempt validation. That 400 was correct behavior, but it never reached the customer as readable text: `createOrder` (the `'use server'` action) let the thrown `BackendError` cross the Server Action boundary, and the frontend was running a **production build** (`next start`, not `next dev` — confirmed by inspecting the running process directly). Next.js's own documented behavior for Server Actions ([Error Handling](https://nextjs.org/docs/app/getting-started/error-handling): *"For these errors, avoid using try/catch blocks and throw errors. Instead, model expected errors as return values"*) redacts any thrown error's message to a generic digest in production, specifically to avoid leaking server internals — so the customer saw gibberish instead of "введите номер с кодом страны."

**Two fixes, both real, both scoped to what was actually broken — not a rewrite:**

1. **The validation itself was needlessly strict.** `customerPhone`/`Business.phone` are never used for any telephony/SMS integration in this app — they're free-text contact info a business owner reads and dials themselves. Strict E.164 country-code validation was the wrong tool for that job. Replaced `@IsPhoneNumber(undefined)` with a shared `LOOSE_PHONE_PATTERN` (`backend/src/common/lib/phone-validation.ts`) — accepts digits/spaces/dashes/parens with an optional leading `+`, requires at least 5 digits total, length 5-20 — across all three places it was used: `CreateOrderDto`, `CreateAppointmentDto`, `UpdateBusinessDto`. A dedicated regression script (`verify-phone-validation-fix.mjs`, 9 checks) confirmed real-world formats now pass (plain Ukrainian, E.164, spaced Russian, US-dashed, short local) while garbage is still rejected (too few digits, no digits, too long, letters).

2. **The redaction issue itself, fixed for the two paths a real end-customer can actually hit.** `createOrder` and `createAppointment` (the only two anonymous, customer-facing Server Actions that can fail on ordinary validation) no longer throw at all — each catches its own `BackendError` internally and returns a discriminated result (`CreateOrderOutcome`/`CreateAppointmentOutcome`: `{ ok: true, order }` or `{ ok: false, error }`), exactly the pattern Next.js's own docs recommend for expected errors. `CartWidget.onSubmit`/`BookingModal.onSubmit` check `outcome.ok` instead of wrapping the call in `try/catch`. **Deliberately not extended to every other Server Action in the app** (there are dozens — `createProduct`, `updateBusiness`, auth, discounts, forms, etc., all built on the same `backendFetch`-throws contract) — those are owner-facing Dashboard actions, not anonymous end-customer checkout paths; a garbled error there is a worse experience but not a lost sale on someone else's real business, and rewriting every action's contract project-wide is a large, separate, cross-cutting change that deserves its own explicit scoping conversation rather than a drive-by fix bundled into this bug report. Named here so it isn't lost, not silently left unremarked.

**Verified by direct reproduction against the real business, and the fix confirmed live, not just unit-level:** re-created the user's exact failing request (`380958887722`, no `+`) directly against the backend both before the fix (400, confirming the real root cause) and after (201, with the correct `UAH`/20%-exclusive-tax breakdown: subtotal 10000, tax 2000, total 12000). The production frontend server the user was actually testing against was stale relative to the fix (`next start` serves a static build, not live-reloaded like `next dev`) — rebuilt (`npm run build`) and restarted it on the same port so the user's next retry, through the same tunnel URL, runs the fixed code. Both `npm run check` gates (backend and frontend) remained clean throughout. The two stray test orders created during reproduction against the user's real business were deleted afterward — nothing else in their real data was touched.
