# Правила проекта Tavern Backend

Этот документ — основной источник правил для всех AI-агентов и разработчиков,
работающих с backend этого репозитория. Frontend ведёт свою собственную пару
`frontend/AGENTS.md` (правила) + `frontend/PROJECT_CONTEXT.md` (состояние) —
этот файл и `backend/PROJECT_CONTEXT.md` делают то же самое для backend.
Планы по конкретным инициативам живут в корневых `*_ROADMAP.md`
(`ROADMAP.md` — платформенные возможности, `AI_PLATFORM_ROADMAP.md` — AI-слой)
и не дублируются здесь.

Этот файл появился позже самого backend (флагуется как отсутствующий с
AI-1 в `AI_PLATFORM_ROADMAP.md` §0.3.7/§5.2) — часть правил ниже уже
соблюдалась де-факто во всех модулях задолго до того, как была записана.

## Стек проекта

- **NestJS 11** (модули/контроллеры/сервисы, Express-адаптер)
- **TypeScript 5** (`strict: true`), CommonJS (`sourceType: 'commonjs'` в
  `eslint.config.mjs` — Nest DI полагается на `emitDecoratorMetadata`,
  которая надёжнее работает в CommonJS-режиме компиляции)
- **Prisma 6** + PostgreSQL — единственный источник схемы данных
- **Redis** — сессии (`SessionsService`), одноразовые Socket.IO-билеты,
  presence, Gemini RPM/RPD-квоты (`GeminiQuotaService`)
- **Socket.IO** (через `@nestjs/platform-socket.io` + `RedisIoAdapter`) —
  единственный realtime-канал
- **class-validator/class-transformer** — DTO-валидация на границе HTTP
- **Vitest** — только юнит-тесты чистых функций (см. «Тестирование» ниже)
- **ESLint 9** (flat config, `eslint.config.mjs`, `typescript-eslint`
  `recommendedTypeChecked`) + **Prettier**
- Алиас `@/*` → `src/*` (`tsconfig.json`, `tsconfig-paths`/`tsc-alias` в
  сборке) — импорты внутри `src/` через `@/modules/...`, не относительные
  пути через несколько уровней папок

## 1. Общие принципы

Те же, что и во frontend (`frontend/AGENTS.md` §1) — не дублируем формулировки
здесь, они универсальны: понятный код важнее лаконичного, без преждевременной
оптимизации, без абстракций и сущностей "про запас", переиспользуем
существующие сервисы/паттерны прежде чем писать новые.

## 2. Архитектура — модуль на домен

`src/modules/{domain}/` — один модуль на бизнес-домен (`businesses`,
`orders`, `products`, `billing`, `ai`, ...), не по техническому слою.
Внутри модуля:

- `{domain}.module.ts` — `@Module({ controllers, providers, exports })`.
  Экспортируется только то, что реально нужно другим модулям (см.
  `BusinessesModule` — `BusinessesService` экспортирован ради AI-4
  onboarding, `DomainsModule` — ради `BusinessesService`'s собственных
  нужд), не всё подряд "на всякий случай".
- `{domain}.controller.ts` — HTTP-слой: guards, `@CurrentUser()`, DTO,
  вызов сервиса, ничего больше. Контроллер решает, кому что показать
  (например, отправлять ли Socket.IO-событие или в какой feed попадёт
  уведомление) — **сервис не должен знать о вызывающем контексте**, тот же
  принцип "Controller decides, Service doesn't know", что и на frontend
  для realtime-событий (`frontend/PROJECT_CONTEXT.md`).
- `{domain}.service.ts` — бизнес-логика и обращения к Prisma.
- `{domain}.types.ts` — DTO-типы ответов (`XxxDto`), не Prisma-модели
  напрходую наружу.
- `dto/*.dto.ts` — входные DTO с `class-validator` декораторами, по одному
  файлу на операцию (`create-x.dto.ts`, `update-x.dto.ts`).
- `lib/*.ts` — чистые функции без NestJS DI/Prisma/сети, вынесенные ради
  юнит-тестов (см. «Тестирование» ниже) — не каждый модуль в этом нуждается,
  заводится только когда есть реальная чистая логика стоит вынести
  (`pricing.ts`, `rule-condition.lib.ts`, `add-block-schemas.ts`).

Двух-контроллерная схема на один сервис — осознанный паттерн, не
дублирование, когда у модуля есть два структурно разных потребителя одной
логики под разными URL-префиксами (пример: `OrdersController` +
`StripeWebhookController`, оба используют `OrdersService`; `RulesController`
владелец-CRUD + `PublicSitesController` вызывает `RulesService.evaluate`
для анонимного трафика).

## 3. Авторизация и владение (tenant isolation)

Нет модели "workspace"/"team" — **`Business.ownerId === request.user.id`**
это единственная граница мультитенантности во всём проекте
(`AI_PLATFORM_ROADMAP.md` §0.1). Из этого следуют два обязательных правила:

- **`SessionAuthGuard`** (`common/guards/session-auth.guard.ts`) — единственный
  рубеж аутентификации. Резолвит opaque Redis-токен (`Authorization: Bearer
<token>`, НЕ JWT) в `userId`, попутно грузит `role`/`isSuperAdmin`/`isBanned`
  и кладёт всё в `request.user` (`RequestUser`) — так `AdminGuard`/
  `SuperAdminGuard` не бьют по базе второй раз, а забаненный пользователь
  получает 403 на каждом защищённом запросе, не только на входе. Навешивается
  явно (`@UseGuards(SessionAuthGuard)`) на каждый защищённый контроллер, не
  глобально — публичные роуты (`auth/*`, `sites/*`, `webhooks/*`) должны
  оставаться читаемо публичными.
- **Каждый write/read-по-id эндпоинт обязан сам перепроверить владение** —
  `findOwned(id, ownerId)`/`assertOwnership(businessId, ownerId)`: находит
  запись, бросает `NotFoundException` если её нет и `ForbiddenException` если
  `ownerId` не совпадает (403, не 404, — "это не ваш бизнес", не "бизнес не
  найден", осознанная разница в сообщении, но не в HTTP-семантике: обе ветки
  не раскрывают, существует ли чужая запись, тем что 404 для
  несуществующего id выглядит идентично). Никогда не доверяем
  клиентскому `businessId` без этой проверки — тот же принцип действует
  и внутри AI tool-слоя (`AiOwnershipGuard`), не только в обычных REST-
  контроллерах.
- Простой модуль (одна проверка, без вложенных owned-сущностей) держит эту
  проверку приватным методом прямо в своём сервисе, инлайн через
  `prisma.business.findUnique({ where: { id }, select: { ownerId: true } })`
  (см. `DiscountsService`/`BillingService`) — не через отдельный shared
  helper и не через чужой сервис (billing не должен зависеть от
  `BusinessesModule` ради одной проверки). Модуль с собственной вложенной
  owned-сущностью (скидка/страница/правило внутри бизнеса) добавляет второй
  метод (`findOwnedDiscount`/`findOwnedRule`) поверх той же проверки бизнеса.

## 4. Провайдер-абстракция — один и тот же паттерн для всего внешнего

Каждая интеграция с внешним сервисом — **абстрактный класс** (не
`interface`: интерфейсы стираются при компиляции TS, у NestJS DI нет для
них рантайм-токена) с одной реальной реализацией сегодня и явным
`isConfigured()`, который никогда не бросает — вызывающий код сам решает,
что делать при отсутствии конфигурации (обычно: показать "недоступно",
не уронить остальной запрос). Уже четыре независимых экземпляра одного и
того же паттерна:

- `PaymentProvider` / `StripeAdapter` (`modules/payments`) — разовые платежи заказов.
- `StripeSubscriptionProvider` / `StripeSubscriptionAdapter` (`modules/billing`) — подписки; **намеренно отдельный класс от `PaymentProvider`**, не общий базовый — Checkout Sessions в режиме `subscription` устроены иначе, чем `PaymentIntent`, и `BillingModule` не должен зависеть от `PaymentsModule` ради пары общих строк.
- `DomainVerificationProvider` (`modules/domains`).
- `LlmProvider` / `GeminiAdapter` (`modules/ai`).

Добавляя новую внешнюю интеграцию — копируйте эту форму, не изобретайте
новую. Секреты — всегда `string | undefined` в `AppConfig`, никогда
обязательное поле; `env.validation.ts` держит соответствующий env var
`@IsOptional()`, чтобы разработчик без ключа мог поднять backend без падения
при старте (см. `STRIPE_SECRET_KEY`/`GEMINI_API_KEY`).

## 5. AI-инструменты — свой под-паттерн поверх модуля 3

`modules/ai/` — оркестрация LLM поверх остального backend, подробный статус
и история решений — в `AI_PLATFORM_ROADMAP.md`, здесь только устойчивые
конвенции:

- **Инструмент — новый вызывающий существующего кода, не новый код-путь.**
  Каждый tool (`modules/ai/tools/*.tool.ts`, `modules/ai/onboarding/tools/*.tool.ts`)
  — тонкая обёртка вокруг уже существующего сервисного метода
  (`WebsitesService.saveDraft`, `BusinessesService.create`,
  `CustomWidgetsService.create`...). Никогда не дублируйте бизнес-логику
  внутри tool-хендлера.
- **Самостоятельная регистрация, не центральный файл-реестр.** Каждый tool
  сам регистрирует себя в `ToolRegistryService`/`OnboardingToolRegistryService`
  через `OnModuleInit` — добавление нового инструмента не требует правки
  общего списка.
- **Risk level на каждом инструменте** (`ToolRiskLevel`: `low`/`medium`/
  `high`/`critical`) — `low` только для чтения, `medium` для обычных
  обратимых мутаций (то, что построено на сегодня). `high`/`critical`
  формально существуют в типах, но ни один инструмент их пока не
  использует — конфирм-флоу перед выполнением (`AI_PLATFORM_ROADMAP.md`,
  фаза AI-9) не реализован, потому что реализовывать нечего подтверждать.
- **Каждый вызов инструмента пишет строку в `AuditLog`** (`AuditLogService`,
  единственный писатель) — успех и провал одинаково, без исключений.
- **Валидация непроверенного AI-инпута — на уровне tool-слоя, до вызова
  существующего (сознательно неглубоко провалидированного) save-эндпоинта.**
  `UpdateWebsiteDocumentDto` не проверяет форму блоков по дизайну (человек
  в Builder физически не может прислать невалидный `props` — инспектор
  сам это гарантирует); AI может. Отсюда — курируемый allowlist типов
  блоков (`tools/lib/add-block-schemas.ts`, 4 типа сегодня:
  `heading`/`text`/`quote`/`spacer`) вместо полного порта фронтенд-реестра
  `BlockDefinition.fields` на backend — сознательно узкий v1, расширяется
  по мере необходимости, не превентивно.
- **Свой изолированный tool-registry на сценарий, когда контекст
  структурно другой**, не общий с параметризацией. `OnboardingToolContext`
  не несёт `businessId` (бизнеса ещё нет — это то, что создаёт разговор) —
  сделан отдельным `Map`-реестром от основного `ToolRegistryService`, а не
  общим generic-типом с опциональным полем: инструменты, редактирующие сайт
  (`add_block`, `set_style`...), должны быть структурно недостижимы из
  onboarding-разговора, не просто "не перечислены по соглашению".
- **Оркестрационный цикл — async generator, общий для стрима и синхронного
  ответа.** `AiService`/`AiOnboardingService` строят цикл "спросить модель →
  получить tool_call(ы) → выполнить → отдать результат обратно → повторить
  до финального текстового ответа" как приватный async generator,
  разделяемый между SSE (`chatStream`) и обычным JSON-ответом (`chat`,
  который просто дренирует тот же generator) — не два независимых цикла.
- **Guard'ы разделены по тому, что реально нужно каждому роуту**, не
  собраны в один "AI-guard на всё". `AiOwnershipGuard` (проверка бизнеса) —
  на весь AI-контроллер, `AiConfiguredGuard` (провайдер настроен) — только
  на методы, которые реально зовут LLM (`chat`/`chat/stream`), не на чтение
  истории (`GET .../activity`), которое не должно падать 503 только
  потому, что ключ сейчас не задан.
- **Проверки владения/конфигурации — на уровне Guard, не внутри тела метода,
  если эндпоинт использует `@Sse()`.** Nest коммитит HTTP-заголовки ответа
  (`200`, `text/event-stream`) на `setTimeout(fn, 0)` сразу после подписки на
  `Observable`, не дожидаясь резолва промиса самого метода-контроллера —
  проверка внутри тела метода почти всегда проигрывает гонку реальному
  Prisma-запросу и попадает в уже закоммиченный `200`-стрим как
  `event: error` вместо чистого `403`/`404`/`503`. Верифицировано живым curl
  против бага и после фикса — см. `AI_PLATFORM_ROADMAP.md` §10.2 для полного
  разбора; относится к любому будущему `@Sse()`-эндпоинту в проекте, не
  только к текущим двум.

## 6. Валидация входных данных — DTO для форм, ручной парсер для JSON-blob

`class-validator` DTO — для эндпоинтов, где вход это плоская форма с
известными полями (`CreateDiscountDto`, `SelectPlanDto`). Для входов,
которые по природе — вложенный JSON произвольной формы (`Rule.condition`,
`CustomWidget.schema`, AI tool args) — ручной парсер, возвращающий типизированный
результат или бросающий с точным путём ошибки (`condition[0].any[1].field
должен быть...`), не class-validator с `@IsObject()` на верхнем уровне,
который ничего не проверяет вглубь. Оба подхода — не взаимозаменяемые
альтернативы "на вкус", выбор зависит от формы входа.

Никогда не добавляйте новую библиотеку-интерпретатор произвольных выражений
(JsonLogic и подобные) под один сценарий использования — `rule-condition.lib.ts`
сознательно написан вручную вместо такой зависимости именно по этой причине
(см. его собственный комментарий).

## 7. Realtime — Socket.IO, тонкий шлюз

Один `RealtimeGateway` (`infrastructure/websocket/`, глобальный модуль) на
весь проект — не заводите новый gateway на фичу. Инжектируйте
`RealtimeGateway` и зовите `emitToUser(s)` из **контроллера**, после того как
сервис уже отработал — сервис не должен знать о сокетах. Тот же принцип,
что и в §2 про разделение ответственности контроллер/сервис, просто более
явный кейс.

## 8. Тестирование — юнит-тесты только для чистых функций

Vitest покрывает **только** чистые функции без Prisma/DI/сети —
`pricing.ts`, `rule-condition.lib.ts`, `add-block-schemas.ts`,
`gemini-quota.lib.ts`, `ai-capacity.lib.ts` и т. п. Если в модуле есть
нетривиальная чистая логика — выносите её в `lib/*.ts` именно ради
тестируемости без моков (`частая причина завести `lib/`-файл, см. §2).
Всё остальное (контроллеры, сервисы с реальными Prisma-запросами, guard'ы,
AI-оркестрация) проверяется **живыми E2E-прогонами против реально
запущенного dev-стека** (`docker compose up`: backend+postgres+redis) —
curl/`psql` напрямую, тестовые пользователи/бизнесы создаются через
настоящий REST API и удаляются после проверки, не оставляя мусора в dev-БД.
Это не временная замена нормальных e2e-тестов — осознанная практика проекта,
задокументированная изначально в `vitest.config.mts`'s собственном
комментарии. `AI_PLATFORM_ROADMAP.md` — большая коллекция примеров этого
стиля верификации для AI-модуля specifically.

## 9. Миграции Prisma

`npm run migration:create` (`prisma migrate dev --create-only`) для новой
миграции в обычном случае. **Известная проблема**: `prisma migrate dev`
(и `--create-only`) реплеит всю историю миграций в shadow-БД с нуля для
вычисления диффа — эта история содержит хотя бы одну более старую миграцию
(`20260821000000_add_post_images_and_link_previews`), которая падает при
replay "с нуля" (`P3006`), хотя реально применённая история в dev-БД
корректна и актуальна (`prisma migrate status` подтверждает "up to date").
Причина не найдена и не исправлена — если `migrate dev`/`--create-only`
падает с `P3006`, это не ваша новая миграция сломала историю. Обходной
путь, использованный не раз в этом проекте: сгенерировать SQL-дифф вручную
(`prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel
prisma/schema.prisma --script`), записать его в
`prisma/migrations/<timestamp>_<name>/migration.sql` руками, применить
через `prisma migrate deploy` (не трогает shadow-БД вообще, накатывает SQL
напрямую). Не обходите миграции руками через `prisma db push` — это ломает
`_prisma_migrations`-историю, которую `migrate deploy` (используется в
проде) читает.

## 10. Команды проекта

| Команда | Назначение |
|---|---|
| `npm run dev` | Полная сборка + watch-режим (`tsc -w` + `nodemon`) — обычно уже поднято в `docker compose up` |
| `npm run build` | Продакшн-сборка (`nest build` + `tsc-alias`) |
| `npm run lint` / `lint:fix` | ESLint |
| `npm run format` / `format:check` | Prettier |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run test` | Vitest (только чистые функции, см. §8) |
| `npm run check` | lint + format:check + typecheck + test — обязателен перед завершением задачи |
| `npm run fix` | Автоисправление, затем `check` |
| `npm run migration:create` / `migration:deploy` | См. §9 |
| `npm run seed` / `promote-admin` / `promote-super-admin` | Скрипты обслуживания dev-БД |

**Перед завершением любой backend-задачи — `npm run check`**, а для фич,
пересекающих границу с frontend (новый эндпоинт, который сразу же
используется Server Action/Client Component) — ещё и **реальный
`npm run build` на фронтенде**, не только `tsc --noEmit`: `next build`
ловит ошибки уровня бандлера (`server-only` в клиентском бандле и
подобное), которые тайпчек не видит в принципе (см. `AI_PLATFORM_ROADMAP.md`
§9.5 для разбора реального такого случая).

## 11. Git / изменения

Те же правила, что во frontend (`frontend/AGENTS.md` §12) — не трогать
файлы вне задачи, не рефакторить массово ради соответствия новым правилам,
отделять случайно найденные нарушения от изменений текущей задачи.

## 12. Обновление документации

После существенного изменения — обновляйте `backend/PROJECT_CONTEXT.md`
(что есть сейчас), не переписывайте `AI_PLATFORM_ROADMAP.md`/`ROADMAP.md`
задним числом (те — журнал решений по конкретной инициативе, не текущее
состояние). Этот файл (`AGENTS.md`) — только при появлении нового
устойчивого паттерна/соглашения, не деталей конкретной фичи.
